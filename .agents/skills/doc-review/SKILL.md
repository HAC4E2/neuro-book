# 文档审查

`$ARGUMENTS` 是审查范围：文档路径（文件或目录），或自然语言描述（如"ui/ 下新写的规范"）；缺省时由 leader 根据当前未提交改动判断涉及哪些文档。

## 步骤

1. 确定对象：`$ARGUMENTS` 给出路径或描述时，据此列出待审 Markdown 文件并确认可读；缺省时用 `git status --short` 找未提交改动涉及的文档。
2. 派发审查：派发子代理，选择低性能的模型（如 smol、haiku 级别），一个文档一z`个任务，任务文本内联下方"审查协议"，给出文档绝对路径，要求完整读取后输出疑问清单。多文档并行派发。
3. 简单报告：给出结论（疑问为空 → 通过；非空 → 不合格）与疑问清单。不展开修复方案。
4. 停止并等待：报告后停下，等用户明确同意后才进入修复。
5. 修复与复核（仅用户同意后）

## 审查协议（内联进每个 task 文本）

- 你是首次接触该项目的读者，没有任何背景、术语表或上下文。
- 读取完整文档，逐节记录任何无法继续理解的地方。
- 疑问类型：
  - 主题偏离
  - 术语未定义：术语或缩写没有解释；
  - 概念悬空：概念被引用但从未介绍；
  - 句子不可读：语法或指代导致含义无法确定；
  - 缺示例：抽象规则没有实例可验证理解；
  - 前后矛盾：两处说法冲突；
  - 链接悬空：引用的文件、章节或字段不存在。
- 输出：判定（`通过`/`不合格`，读完仍有任何疑问即不合格）+ 疑问清单（每条含位置、原文摘录、类型、为什么看不懂）

## 完成条件

每个文档都得到一次独立模型审查；报告含结论与疑问清单；未经用户同意不进入修复。
