# 文生图插件化与压缩包分发施工计划

## 1. 目标

把当前 `new-text-to-picture` 分支中的文生图能力收敛为一个自包含 NeuroBook 扩展包。目标用户使用带扩展宿主的官方 `master` 源码工作区时，只需把 ZIP 解压到仓库根目录并重启开发服务或重新构建，即可启用文生图；删除扩展目录并重启即可卸载代码，不需要切换到另一个长期分支。

本计划中的“解压即安装”只承诺 **源码工作区**。已经构建完成的 Product Application Root 是只读且代码已经被 Nuxt/Nitro 打包，不能靠事后放入 `.ts/.vue` 文件动态获得新路由和界面；支持已安装 Product 的热插拔属于后续独立目标。

## 2. 基线审计与结论

审计基线是 2026-08-16 的官方 `master` 提交 `5e55c54e13cd67f6e19c5361931fca1fe9ae4241`。

- 官方基线没有 NeuroBook 通用扩展清单、Nuxt 扩展扫描器、Novel IDE UI 插槽或可扩展的 Project Module 名称空间。
- 当前工作区有 `224` 个路径名直接包含 `text-to-image` / `TextToImage` 的文件；这些文件大多可以迁入独立扩展目录。
- 除文生图专属目录外，当前实现还修改了 `21` 个非生成的既有核心文件，主要位于 `app/pages/index.vue`、Activity Bar、Markdown Studio / TipTap、i18n、配置系统、Project 初始化和两套 Prisma schema。
- 当前实现还新增或修改了 Prisma 生成代码。只删除文生图源码无法卸载这些类型与 schema 改动。
- 当前根依赖新增 `@huggingface/transformers`；如果扩展仍依赖宿主根 `package.json`，就不能满足单纯解压安装。

因此，直接制作覆盖仓库同名文件的 ZIP 只能称为“补丁包”，不是可卸载插件。真正的目录级安装需要先在官方 `master` 合入一次通用扩展宿主；之后文生图 ZIP 只能新增 `extensions/text-to-image/`，不能覆盖任何既有宿主文件。

## 3. 最终安装形态

发布 ZIP 的根目录结构固定为：

```text
neuro-book-text-to-image-<version>.zip
├── INSTALL.md
├── SHA256SUMS
└── extensions/
    └── text-to-image/
        ├── neurobook.extension.json
        ├── module.mjs
        ├── app/
        ├── server/
        ├── shared/
        ├── migrations/
        ├── assets/
        ├── LICENSES/
        └── package-content.json
```

用户把 ZIP 解压到 NeuroBook 仓库根目录后，唯一新增的业务目录必须是 `extensions/text-to-image/`。扩展发现发生在 Nuxt 构建启动阶段，因此安装、升级和卸载后都要求重启 `bun run dev`；这不等于运行时热插拔。

## 4. 扩展清单合同

`neurobook.extension.json` 第一版至少包含：

```json
{
  "schema": "nbook.extension/v1",
  "id": "text-to-image",
  "displayName": "文生图",
  "version": "0.1.0",
  "hostApiVersion": "1",
  "module": "./module.mjs",
  "requiresRestart": true,
  "capabilities": [
    "novel-activity",
    "novel-workspace",
    "markdown-editor",
    "server-routes",
    "project-data"
  ]
}
```

规则：

- `id` 必须是 ASCII kebab-case，目录名必须与 `id` 一致。
- `module` 必须解析在扩展目录内，拒绝绝对路径、`..`、符号链接越界和远程 URL。
- `hostApiVersion` 不匹配时拒绝加载整个扩展并给出单条可理解诊断，不能只加载一半前端或后端。
- 同一 `id` 只能存在一个目录；重复 ID、清单损坏或内容哈希不匹配时 fail closed。
- 扩展清单、模块和包内容不允许声明或携带 API Key、小说正文、Project Workspace、用户配置、数据库、日志、Trace 或生成图片。

## 5. 官方 master 需要的一次性通用扩展宿主

### 5.1 构建期发现

在根 `nuxt.config.ts` 只增加通用扩展扫描，不写任何 `text-to-image` 特判：

1. 扫描 `extensions/*/neurobook.extension.json`；
2. 校验清单与路径 containment；
3. 按扩展 ID 排序，得到稳定的 Nuxt module 路径；
4. 把 module 加入 Nuxt `modules`；
5. 生成只包含公开元数据和加载诊断的虚拟 manifest，供前端设置页与错误提示读取。

扩展的 `module.mjs` 使用当前 Nuxt Kit 已提供的 `addServerScanDir`、`addComponentsDir`、`addPlugin`、`addServerPlugin` 和类型模板能力，把扩展自己的路由、组件和插件接入宿主。宿主不逐文件枚举文生图路由。

### 5.2 Novel IDE 前端插槽

宿主新增稳定、通用的贡献注册表，不允许扩展直接修改 DOM 或 monkey patch Vue 实例。第一批插槽：

- `novel.activityItems`：Activity Bar 图标、标题、可见条件与激活动作；
- `novel.workspaceRoots`：挂载扩展根组件，根组件拥有自己的 Dialog 和局部状态；
- `markdown.extensions`：TipTap / Markdown 方言扩展；
- `markdown.toolbarActions`：正文工具栏动作与可用性判断；
- `markdown.imageActions`：标准 Markdown 图片的扩展动作；
- `novel.fileContextActions`：角色等特定文件类型的扩展动作。

`app/pages/index.vue` 只提供一个稳定的 `NovelWorkspaceExtensionContext`，包含当前 Project、文件、正文、保存、刷新、版本接纳、确认框和通知能力。文生图扩展通过该上下文完成现有流程，不再导入或复制页面内部 ref。

### 5.3 服务端与路由

扩展服务端代码只由扩展 Nuxt module 注册：

- `/api/text-to-image/**` 路由随扩展存在而存在；删除扩展并重新构建后全部消失；
- 队列启动、HMR 和 shutdown 收口通过扩展自己的 Nitro plugin；
- 宿主只公开认证、路径解析、Project Session、通知错误格式等稳定能力，不反向导入文生图模块。

### 5.4 i18n 与主题

- 扩展在自己的 app plugin 中向现有 i18n 实例合并 `zh-CN` / `en-US` 文案，不修改宿主 locale 文件。
- 扩展 UI 只消费宿主已登记主题变量；需要的新通用变量先进入宿主合同，文生图私有样式留在扩展目录。

## 6. 存储去耦

### 6.1 禁止继续修改 Prisma schema 和生成代码

扩展不能要求用户在解压后运行 Prisma generate，也不能改写：

- `prisma/schema.sqlite.prisma`；
- `prisma/project.schema.prisma`；
- `server/generated/prisma/**`；
- `server/generated/project-prisma/**`。

文生图表改为由扩展迁移器用参数化原生 SQL 创建和访问。表仍放在宿主既有 App SQLite 与 Project SQLite 中，以继续获得现有备份、Project archive、删除保护和并发边界；Prisma 对未知附加表保持透明。

表名必须带稳定命名空间，例如 `ExtensionTextToImageProvider`、`ExtensionTextToImageJob`、`ExtensionTextToImageAsset`。扩展服务内建立 typed repository，不在业务层散落 SQL。

### 6.2 配置

文生图 Provider、凭据密文、预设和替换规则改由扩展表持有，不再修改核心 `config.dto`、registry、normalizer 或 config service。凭据继续使用 State Root 内的 AES-GCM 主密钥，卸载代码时不导出明文。

### 6.3 当前分支数据迁移

首次加载扩展时执行幂等迁移：

1. 检测现有 `TextToImageProvider` / `TextToImageJob` / `TextToImageAsset`；
2. 在事务内复制到扩展命名空间表；
3. 校验记录数、外键和关键字段；
4. 写入扩展 migration ledger；
5. 首版不自动删除旧表，避免迁移失败后无法回退；确认稳定后再提供显式清理。

迁移不得读取或写入小说正文内容；Project 资产文件继续位于 `assets/tti/`，引用路径不改变。

## 7. 依赖自包含

安装目标不允许修改宿主 `package.json` 或 `bun.lock`。扩展发布构建必须把新增运行时依赖打进自己的分发产物，或替换为扩展内实现。

当前唯一明确新增的运行时依赖是 `@huggingface/transformers`。施工时二选一并以体积、跨平台和离线测试决定：

1. 将 token 估算器及其必要 tokenizer 资产打成浏览器侧自包含 chunk；
2. 用扩展内轻量 tokenizer 实现替代，但必须保持现有 T5 估算合同和测试，不得静默退化成字符数估算。

不能把整个根 `node_modules`、平台专属 ONNX/Sharp 二进制或开发测试依赖塞进 ZIP。

## 8. 卸载语义

默认卸载只删除代码，不删除作者数据：

- 删除 `extensions/text-to-image/` 并重启后，文生图入口、API、队列消费者和自定义编辑器卡片消失；
- 标准 Markdown 图片继续正常显示；
- `assets/tti/` 图片、角色视觉 JSON、Provider 密文表、Job/Asset 历史表默认保留，便于重装恢复；
- 未生成的 `<text-to-image-prompt>` 由官方 master 既有 `HtmlFallback` 作为未知 HTML 原样保存，不能在无扩展时被 TipTap 静默删除。

后续可提供两个显式清理级别：

- `purge-runtime`：删除 Provider 凭据、队列和扩展配置，保留正文和图片文件；
- `purge-project-data`：逐 Project 清理元数据和未引用资产。任何仍被 Markdown 引用的图片都必须拒绝自动删除并列出路径。

“删除目录即卸载”只对应代码卸载；删除作者内容必须是独立、可审计、需要确认的破坏性动作。

## 9. 分批施工

### Batch A：通用扩展宿主

- 新增清单 schema、路径校验、扫描器和 Nuxt module 装载；
- 新增前端贡献注册表、Activity Bar 动态项和 Novel Workspace 扩展根插槽；
- 新增 Markdown 扩展与工具栏贡献插槽；
- 使用一个无业务逻辑的 `hello-extension` fixture 验证安装、禁用和卸载。

退出条件：官方 master 加 fixture 时出现入口和测试 API，删除 fixture 后重新生成 Nuxt，入口、路由和生成类型全部消失；核心源文件不残留 fixture ID。

### Batch B：文生图 UI 抽离

- 把工作台、资产对话框和页面状态迁入扩展根组件；
- 把 Activity Bar、正文按钮、角色按钮和图片动作改成贡献；
- 把 TipTap 节点与 Markdown helpers 迁入扩展；
- 运行关闭扩展后的 Markdown round-trip，证明占位符仍原样保存。

退出条件：宿主核心文件中不再出现 `text-to-image`、`TextToImage`、`NovelAI` 或 `assets/tti` 业务标识；只允许通用扩展 API 和 fixture 测试出现扩展概念。

### Batch C：服务端、配置和数据库抽离

- 迁移 `/api/text-to-image/**`、领域服务、队列和 LLM/NovelAI 代码；
- 用扩展 repository + 原生 SQL 取代两套 Prisma model；
- 把文生图配置移出核心 config schema；
- 实现旧分支数据的幂等复制迁移和回滚诊断。

退出条件：干净官方 master 的 Prisma schema / generated client 与未安装扩展时逐字一致；安装扩展后能创建 Provider、生成 Job、保存资产并重启恢复。

### Batch D：自包含发布包

- 构建 `module.mjs` 和新增依赖 chunk；
- 生成 `package-content.json`、SHA256SUMS、安装说明和许可证清单；
- 打包脚本使用文件 allowlist，主动拒绝 `.env`、`workspace/`、数据库、图片资产、日志、Trace、API Key 模式和本地小说路径；
- ZIP 内容按路径排序、时间戳归一化，保证同一源码重复构建哈希一致。

退出条件：ZIP 解压后没有执行代码就不会改写任何宿主文件；启动时由宿主发现并加载扩展。

### Batch E：干净 master 安装/升级/卸载验收

在临时目录使用固定官方 master commit 验证：

1. 未安装扩展：typecheck、build、核心测试通过；
2. 解压 ZIP：typecheck、build、扩展聚焦测试通过；
3. 浏览器：入口、Provider、正文规划、单图队列、写回、后处理可用；
4. 覆盖升级：旧配置和历史资产可读，不残留已删除代码；
5. 删除扩展目录：typecheck、build 通过，文生图入口/API 消失；
6. 打开含占位符和图片的旧章节并保存：Markdown 不丢失；
7. 重装同版本：保留的数据重新可见；
8. ZIP 隐私扫描和跨平台路径检查通过。

## 10. 明确不做

- 不把当前 21 个核心文件的修改原样覆盖进发布 ZIP；
- 不通过 DOM 注入、Vue monkey patch 或运行时字符串替换接入界面；
- 不让扩展修改根 `package.json`、`bun.lock`、Prisma schema 或生成代码；
- 不把 API Key、用户预设、小说、Project Workspace、生成图片或数据库打入发布包；
- 不把“删除扩展目录”解释为授权删除作者正文和图片；
- 本阶段不支持已经构建完成的官方 Product 热插拔，也不建设面向任意第三方代码的安全沙箱或在线插件市场。

## 11. 当前决策与可逆性

- 默认目标是官方 `master` **源码工作区**，不是已安装 Product；以后可以在相同清单之上增加预编译 Product 扩展宿主。
- 默认卸载保留作者数据；用户之后可以显式 purge。这个选择可逆，反过来默认删除数据则不可逆。
- 数据表先保留在既有 App / Project SQLite 内并使用命名空间表，不建立第三个数据库；这样复用现有备份和 Project archive。若后续宿主提供扩展数据库快照钩子，再迁移到独立 DB 仍可通过 ledger 完成。
- 通用扩展宿主必须先进入官方 `master`。在完全不修改当前官方 master 的前提下，无法同时满足完整 IDE 集成、只新增一个目录和删除目录即可卸载三个条件。
