# 菜单贡献点：调研与设计稿

开发者在 t83 验收反馈第 7 条问“菜单系统做了没有，记得有些视图能贡献菜单”。本稿先列旧应用与新应用的菜单各从哪里来，再给推荐设计与要开发者定的事。代码路径以实现分支 `refactor/w00017-runtime-foundation` 为准。

## 旧应用：有哪些菜单，谁往里加

| 位置 | 内容从哪来 | 视图或插件能不能往里加 |
|---|---|---|
| 标题栏应用菜单（文件、编辑、视图、帮助） | `app/utils/workbench-chrome.ts` 的 `resolveTitleBarMenuGroups`：按宿主能力生成的固定表 | 不能 |
| 视图标题动作 | 视图描述里的 `titleActions`（`app/utils/workbench/view-title-actions.ts`）：`primary` 画成图标按钮，`secondary` 收进“更多”下拉（一层子菜单、勾选与单选）；`when` 控制显隐；按住 Alt 换成另一条命令；可用、原因、勾选、忙碌由视图实例上报 | 能。产品里只有资源管理器用了一个 `primary`（刷新），`secondary` 没有使用者 |
| 编辑组工具栏的菜单 | `app/composables/useEditorWorkbench.ts` 的 `menusOf`：“文件”（保存、关闭、重载配置）、“打开方式”（编辑器注册表，勾选当前的）、“视图动作”（当前编辑器视图实例上报的动作，例如 Markdown 编辑器的“批注”开关） | 编辑器视图能往“视图动作”里加。“有些视图能贡献菜单”最可能指这里 |
| 编辑器标签右键 | `EditorTabBar.vue` 的固定列表：固定或取消固定、保留、左移右移、关闭等 | 不能 |
| 资源管理器右键 | 固定列表 | 不能 |
| 视图自己画的下拉（Agent 会话头的新建菜单等） | 视图组件内部 | 不算贡献，是视图自己的界面 |

## 新应用现在

| 位置 | 现状 |
|---|---|
| 标题栏应用菜单 | 工作台 `web/titlebar/menu-model.ts` 写死四组菜单，按字符串写着别的插件的命令 id（`nbook.editor.save`、`nbook.settings.switch-theme` 等）。命令不在目录里就不画，勾选读工作台的公开键。别的插件加不进来，工作台还要认识别的插件的命令 |
| 视图标题动作 | `ViewDeclaration.actions`（实现分支上 `docs/specs/workbench/views.md` 输出 10）：至多 8 个图标按钮，带命令、图标、标题、`args: "instance"` 与 `toggled` 公开键；没有“更多”菜单 |
| 资源管理器右键 | 资源管理器自己的固定菜单（`explorer/web/menu.ts`）；`files-explorer.md` 写明开放的 `explorer/context` 随第一个使用者做 |
| 编辑器 | 没有标签右键菜单，也没有工具栏菜单；“重新以…打开”在标题栏的视图菜单里 |

已定的方向：平台设计稿（`docs/proposals/extensible-application-platform.md`，accepted）写明“菜单位置由拥有者定义，并规定菜单项收到的参数与局部上下文，例如 Files 定义 `explorer/context`；`when` 由 workbench 求值”。贡献点由拥有者插件定义也已是现行做法（t33）。

## 推荐设计

1. **菜单位置就是拥有者定义的贡献点**。每个位置一个贡献点，拥有者规定菜单项执行时收到的参数（例如资源管理器给选中的资源地址）。菜单项用同一个形状，放在命令插件的共享合同里，各拥有者复用：

   ```ts
   interface MenuItemDeclaration {
       readonly command: string;
       readonly section: string;          // 同节连在一起、节之间画分隔线；节按名字排序，例如 "1_save"
       readonly order?: number;           // 节内顺序，同值按贡献 id
       readonly label?: LocalizedText;    // 省略时用命令标题
       readonly toggled?: string;         // 布尔公开键：画成勾选项
       readonly when?: WhenPredicate;     // 不满足时不显示；可用与否另看命令自己的 when
   }
   ```

   可用、禁用原因与快捷键照旧取命令（与现在的标题栏菜单同一规则）。画成按钮的位置（视图标题、编辑区标题）另带图标与 `placement: "inline" | "menu"`。

   **局部条件**：`when` 只能读布尔公开键，写不出“当前文件是 Markdown”。有“当前文件”的位置由拥有者给出局部上下文，菜单项可以声明 `extensions`（例如 `[".md"]`），只在那个文件的后缀匹配时显示；以后有语言登记再加按语言过滤。

2. **第一版的菜单位置**：
   - **标题栏应用菜单**：工作台定义四个组（文件、编辑、视图、帮助），条目由各插件贡献。现在写死在工作台的条目搬回各自插件（编辑器贡献保存与关闭，设置贡献主题、明暗与语言，作品插件贡献打开项目等），工作台不再认识别的插件的命令 id。只属于桌面的条目（退出）照旧只在桌面宿主里显示。
   - **视图标题的“更多”**：`ViewDeclaration.actions` 加 `placement: "inline" | "menu"`，缺省 `inline`；`menu` 的条目进标题行末尾的“⋯”下拉。
   - **资源管理器右键**：开放为贡献点，菜单项收到选中的资源；现有固定项改为资源管理器自己的贡献，外观与行为不变。可用 `extensions` 过滤（按右键的那一项）。
   - **编辑区标题**：编辑区标签栏右侧的按钮与“⋯”，由编辑器插件定义，菜单项执行时收到活动标签的文件地址，可用 `extensions` 过滤。第一批使用者是编辑器自己的命令（向右分屏、以…重新打开）；按后缀过滤用测试插件验收。例如以后的 Markdown 预览插件贡献一个眼睛按钮、`extensions: [".md"]`，活动标签是 `.md` 时出现，点了收到这个文件的地址。

3. **不做**：子菜单（标题栏收拢后的 ≡ 已经按组分级，别处第一版不分级）；按住 Alt 换命令；视图实例上报的忙碌态。

## 开发者的决定（2026-10-13）

开发者问能否做到“文件视图有新建文件、文件夹的按钮，以后编辑器里 Markdown 文件显示预览按钮”。前者资源管理器现在就有（标题行五个按钮），菜单贡献点补的是别的插件也能往里加、按钮多了收进“⋯”；后者要加“编辑区标题”这一处与按后缀的局部条件。开发者同意第一版做四处：标题栏菜单、视图标题的“更多”、资源管理器右键、编辑区标题。编辑器标签右键与正文右键等第一个使用者再做；Markdown 预览本身是新功能，打磨阶段之后再做。
