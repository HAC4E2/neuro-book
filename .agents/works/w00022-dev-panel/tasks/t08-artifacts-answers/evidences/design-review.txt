## 重要

### 1. 答复 id 用取锁前的时间，按 `through` 判断“已确认”会漏掉答复（并发，失败路径）
- **位置**：“目录与文件”里答复 id 那一条；“答复与确认”里的 `answersAfter`。
- **现象**：答复 id 是“毫秒时间加随机后缀”，按字典序就当作时间顺序；`--unacked` 的游标是最近一次确认的 `through`。可是写事务在第 301 行先读时钟（`const now = …`），第 308 行才去取锁，等锁最长 30 秒（`DEFAULT_LOCK_WAIT_MS = 30_000`）；锁丢了重来时也沿用这个 `now`。目录锁靠轮询，不保证先来先得。
- **为什么是问题**：编码者用 `tx.now` 生成 id 是最顺手的写法，这样会出现下面的顺序：
  1. 答复 X 在 T0 读了时钟，开始等锁；
  2. 答复 Y 在 T1（晚于 T0）读了时钟，先拿到锁，落位；
  3. `answers ack` 拿到锁，只看到 Y，记 `through = Y`；
  4. X 最后落位，但它的 id 小于 Y。

  结果是 `answersAfter(…, through)` 永远不返回 X：X 被当成“已采纳”，`--unacked`、`--wait` 和 t11 的通知游标都不会再提到它。确认文件是入库的，这个错会留在记录里。
- **核实**：读 `src/core/transaction.ts` 第 301、308 行；锁的实现见 `lock.ts`。
- **改法**：
  - 答复 id 和确认 id 在锁内重新读时钟生成，并保证单调：取 `max(now, 目录里最大的 id + 1ms)`；`submittedAt` 另记开发者按提交的时刻，与 id 分开。
  - “未确认”改成集合差：答复 id 不在任何一份确认的 `answers[]` 里就算未确认（确认里本来就有 `answers` 字段）。`through` 只用于显示。

### 2. `artifact close` 时题怎么处理没写，重新打开后又和“不复活”冲突（与已定设计不一致，遗漏）
- **位置**：“命令合同”与“结局与状态现算”；`nextQuestions` 的表里没有关闭这一情形。
- **现象**：Proposal 第三节写明“关闭产物等于撤回它所有未答的题”。计划只说 close 写一份 `closed` 的发布记录，没说未答的题记成 `withdrawn`。
- **为什么是问题**：
  - 如果照字面不撤回，已关闭产物里 `open` 的必答题会一直留在收件箱，又回到“待答数虚高”的老问题。
  - 如果撤回，按决定点 3“已撤回的题号不复活”，之后再发布会让它重新打开（计划写了 `artifact_reopened`），页面上全部旧题都会报 `retired_question_in_page`，只能整体换题号。
- **改法**：写明 close 把 `open` 的题记成 `{kind: "withdrawn", in: N, reason: "closed"}`；重新打开时，只恢复因关闭而撤回、且页面里还在的题，其余结局不变。补一条 L1 测试和一条 L3 测试。

### 3. 判定 `answered` 时按哪一版的题目定义校验没定（接口合同）
- **位置**：“结局与状态现算”第 2 条，以及 `nextQuestions` 表的第一行。
- **现象**：第 2 条只说“答复里有这道题的合法取值”就算 `answered`，没说按答复针对的那一版校验还是按最新一版。同一题号改了选项后，旧取值在最新一版下不合法，只说“标 `stale_value`”。
- **为什么是问题**：
  - 按答复那一版校验：这道题算 `answered`，从收件箱消失，开发者不会被提醒重答。
  - 按最新一版校验：这道题回到 `open`。
  - t09 的侧栏、t10 的表单和收件箱计数会各自猜一种。
- **改法**：二选一写进 `file-formats.md`。推荐按最新一版校验：最新取值不合法就回到 `open`，同时列出那份旧答复并标 `stale_value`。

### 4. 发布、答复、确认改不改 `updated` 没有写（与已定设计不一致）
- **位置**：“Context”里“`updated` 由 nbdev 写（t06 已实现）”一句；验收场景 9。
- **现象**：
  - Proposal 第二节写的是“写入某个 Task 的文件时，同时把它 frontmatter 里的 `updated` 改成当天日期”，待决问题 4 已按这个做法采纳。
  - t06 只在 `setRecordStatus` 里改 `updated`（见 `operations.ts`）。
  - 计划没说发布、登记、代录、确认会不会改 Task README 的 `updated`。
- **为什么是问题**：
  - 如果要改：每次提交都会带上 README，与场景 9“只含产物目录与 `--include`”冲突；会话正在改的 README 也会被一起提交，或者像 `task status` 那样报 `uncommitted_changes`。
  - 如果不改：`updated` 的优先级高于提交日期，一个 Task 只收到答复和发布时，面板上的“最近更新”会一直停在旧日期。
- **改法**：明确选一种并写进文档。推荐不改 README，但让“最近更新”取 `max(updated, 产物目录最后一次提交的日期)`；或者只在 `answers ack --include <README>` 时顺带改。

### 5. 写入前置照字面会拒掉 t80（接口合同）
- **位置**：“写入的公共前置”第 2 条。
- **现象**：原文是“Task 不在还在分支上维护的 Work 里，否则报 `branch_maintained_record`”。实测：
  - 真实仓库的 `status --json` 里，w00017 的来源是 `branch`（`refactor/w00017-runtime-foundation`）；
  - t80、t81 的来源是 `master`；
  - w00017 那份 worktree 的 `tasks/` 下只有 t82、t83，没有 t80。

  计划自己拿 t80 的 `report.md` 当 Markdown 入口的例子，但照字面实现，t80 无法发布、登记、代录或确认。`setRecordStatus` 的现有逻辑是按 Task 判断的，只在 Task 在分支上存在、又没经 nbdev 领号时才拒，t80 是能写的。
- **改法**：改成“Task 的来源必须是 `master`（与 `setRecordStatus` 的判定相同）”，并加一条 L2 测试：来自分支的 Work 里只在 master 上的 Task 可以发布。

### 6. `answers --pending` 没有定义（接口合同）
- **位置**：“命令合同”中 `answers` 那一行，以及 `--wait` 一节。
- **现象**：计划和 Proposal 都列了 `--pending|--unacked`，但通篇只定义了 `--unacked`。`--pending` 选什么（有 `open` 题的产物？还是没有答复的题？），以及 `--wait --pending` 等什么，都没写。
- **改法**：给出定义。推荐：`--pending` 列有 `open` 必答题的产物与题，与 `--wait` 互斥；也可以干脆删掉这个参数。

### 7. S6 证明不了“空闲会话被唤醒”（验收映射）
- **位置**：切片表 S6；验收映射场景 4。
- **现象**：S6 由编码子代理用“本会话的 `run_in_background`”挂上 `--wait`，再自己写一份答复。
- **为什么是问题**：
  - 子代理写答复时自己正在工作，这只能证明命令退出了，不能证明一个空闲会话被叫醒。
  - 子代理结束本轮就等于交回结果，它没有“空闲等待”这种状态。
  - 如果另起一个延时写答复的后台任务，它自己结束时也会唤醒会话，结果说明不了问题。
- **改法**：S6 交给主会话做。用一个后台命令把延时写答复的进程和 `--wait` 放在一起，例如：

  ```
  sh -c '(sleep 20; bun 写答复脚本) & exec nbdev answers … --wait'
  ```

  启动后主会话结束本轮，看约 20 秒后会不会被这个任务叫醒，并在输出里拿到这份答复。

## 建议

### 8. 题目与选项名的取法对现有评审板不好写（标记写法）
- **位置**：“提问标记”表的“题目”“选项”两行。
- **核实**：
  - 两块现有评审板的题目 `h2` 全部带徽标：t03 是 `<span class="badge">`，t80 是 `<span class="tag done">`。parse5 取出来是“已定首页（Work 视角）…”。
  - 把 `data-nb-option` 放在 t03 的选项容器 `div.cand` 上，选项名会是整段文字，分别有 138 和 155 个字，开头是按钮文字“打开”。
  - t80 的板是 `h2` 后面跟兄弟元素的扁平结构，要先给每道题包一层 `section` 才能加标记。
- **改法**：
  - 选项名按 `data-nb-label`、范围内第一个标题、自身文字的顺序取，超过约 80 字就报错；
  - 题目要么规定 `data-nb-label` 必填，要么在取文字时跳过带 `data-nb-skip` 的元素；
  - Skill 写明扁平板要先包 `section`。

### 9. 漏写闭合标签可以直接查出来（失败路径）
- **位置**：“验证”里“未验证的边界”第 4 条。
- **核实**：parse5 在元素被隐式闭合时，`sourceCodeLocation.endTag` 不存在。我实测了三种情况：未闭合的 `section`、未闭合的 `li`、`<p>` 里放 `<div>` 导致 `p` 被提前闭合，三种都是 `MISSING`，有显式结束标签的都有行号。parse5 的 `onParseError` 不报这类树构建错误，实测 0 条。
- **改法**：题的范围元素没有显式结束标签时，报 `question_not_closed` 并带行号。`p` 里放块级选项这类“题外选项”的错误，报错文字里提示是 HTML 自动闭合造成的。

### 10. 写在脚本或模板里的标记会被悄悄忽略（标记解析）
- **现象**：t03 评审板的题都是静态 HTML，能正常解析；`r1/` 到 `r3/` 的子页由 `assets/data*.js` 渲染。parse5 不进入 `<template>` 和 `<noscript>` 的内容（实测）。Agent 如果把题写在 JS 模板字符串里，页面会被当成纯讲解页，不进收件箱，也没有任何提示。
- **改法**：产物目录里的 `.js` 文件或内联 `<script>` 中出现 `data-nb-question` 时，给 `questions_in_script` 警告。

### 11. 已答的题从页面删掉也被记成“被取代”（结局）
- **位置**：`nextQuestions` 表第三行。
- **现象**：“活题”包括已答的题。审查报告进入下一轮时删掉已处理的条目，这些条目会从 `answered` 变成 `superseded`，每条还报一次 `questions_dropped`。按状态规则第 1 条结局优先，面板会把它们折叠成“被取代”。
- **改法**：页面里消失时只取代 `open` 的题；已答的题保留 `answered`，记 `page: null`，不发警告。

### 12. 解析、哈希与生成题表要在锁内完成（并发）
- **现象**：计划没写页面解析、`contentHash`、列出页面文件和 `nextQuestions` 在什么时候算。如果在取锁前算，两个发布同时进行时，后拿到锁的一方会写出内容更旧的版本。新版本里没有的题会被永久取代，按决定点 3 又不能复活。
- **改法**：写明这几步都在事务内执行。实测 t03 评审板 16 个 HTML 共 235K 字，全部解析 Node 约 53 毫秒、Bun 约 62 毫秒，放在锁内没问题。

### 13. 非发布动作产生的版本沿用哪些字段没写；`title` 缺省规则不一致；提交失败后补救走不通（接口合同）
- `ask`、`withdraw`、`supersede`、`close` 生成的新版本：
  - 没写 `contentHash`、`entry`、`title` 是否沿用上一版；
  - 没写页面不重新解析、页面改动不提交。
- `kind` 缺省沿用上一版，但 `title` 缺省重新读页面的 `<title>`。v1 用 `--title` 指定的标题，下一次发布会被悄悄换掉，“内容与题都没变就不出新版本”的判断也因此失效。
- 发布提交失败（`committed: false`）后再发布一次，会被判成 `unchanged: true`，`vN.json` 和页面文件始终不会提交。`cli.md` 要写明补救办法是手动提交 `writtenPaths`。

### 14. 几条 Git 命令的参数要写定（依赖的机制）
- Task 图片合计写的是“一次 `git ls-files` 列出”。这个命令只列已跟踪的文件，本次要提交的新图不在里面，正是把合计推过 5 MiB 的那次发布不会报警。要用 `--cached --others --exclude-standard -z`。
- 发布时用 `git status --porcelain -uall` 列页面改动，要加 `-z --no-renames`。不加 `-z` 时，中文文件名会被加引号转义。
- `contentHash` 写明：路径相对产物目录、按 UTF-8 字节序排序、遇到符号链接就拒绝。t09 要用同一算法复算。

### 15. provenance 按路径对应的两个隐患，以及给 t11 的备注
- `vN.json` 如果被删掉（提交失败后手工清理或 revert）再由别的会话重建，旧的 provenance 还在：要么沿用旧的提问者，要么独占创建失败。`askerOf` 会把通知发错会话。建议 provenance 记下入库文件的 sha256，`askerOf` 读时核对。
- 在别的机器上，或删掉 `.local` 之后，`askerOf` 返回 `null`，这时降级为“列出其它持有租约的会话”，要在文档里写明。
- Task 已经 `done` 时照常写入，但 t07 的租约会现算成 `task_closed`，t11 永远不会通知提问者。要写进“给 t09 到 t11 的备注”。

### 16. 给 t09、t10 的字段有缺口（接口合同）
- `TaskView.artifacts[]` 没有 `publishedAt`，首页的“最近的产物”排不了序。
- 计划说 Work 级产物“只在读取时索引”，但 `WorkView` 只加了 `documents[]`，没有 `artifacts[]`。
- 被取代时的 `by` 存什么格式没定。建议存规范化的 `{workId, taskId, artifactId, questionId}`，不存 `w00022` 这类简写引用。
- `readArtifact` 要能读指定版本：t10 按开发者打开的那一版校验取值。
- 答复只有一份 `note`。审查条目选“要讨论”时，开发者没法逐条写理由。建议现在就加可选的 `comments: {题号: 文字}`，免得 t10 再升级格式。
- `file-formats.md` 里“不递归 `artifacts/`”那句要改。

### 17. `--wait` 的轮询范围和重挂规则（性能，失败路径）
- 写明每秒只读主工作区里产物目录的 `answers/`，不跑 Git，也不做过渡期判定。读一遍完整状态要一秒左右（见下文“已核实没有问题的方面”），每秒跑一次就等于一直占着 CPU。答复只会写在 master 上，不需要看各 worktree。
- 按缺省的“未确认”语义：退出码 0 之后、还没确认就按原参数重挂，会立刻返回，会话会被反复叫醒。文档要分开写：退出码 4 时按原参数重挂；退出码 0 时先确认，或者带 `--since <cursor>` 重挂。
- 读答复与读版本不是同一时刻，可能读到 `artifactVersion` 大于自己看到的最新版的答复，要能容忍并重读一次。

### 18. `--about` 与 `--include` 的路径（边界）
- `--about` 要求文件在主工作区存在，但 Spec 草稿通常在实现分支上。计划自己的例子“批准 Spec 晋升”正好是这种情况，会被拒。建议只校验相对路径的格式，或者允许文件在调用者所在的 checkout 里存在。
- `--include` 的路径相对谁没写。调用者可能在 worktree 里，应写明相对主工作区根，并只接受 `.agents/works/` 下的路径（这是 t06 的 `normalizeRecordPath` 已有的约束）。

### 19. `data-nb-*` 和 nb-ui 共用一个前缀（耦合）
- **核实**：nb-ui 和主应用已经在用 13 种 `data-nb-*` 属性，例如 `data-nb-theme`（38 处）、`data-nb-appearance`（23 处）。t03 评审板的 `tokens-nbook.css` 里也有。
- **为什么是问题**：将来产品如果用了 `data-nb-type`、`data-nb-label` 或 `data-nb-option`，从 Lab 存下来的静态稿就会被当成“题外选项”，整次发布失败。
- **改法**：改用 `data-nbdev-*`，或者在文档里把这几个名字登记为保留名。

### 20. 引用检查的细节
- `src` 和 `href` 要先去掉 `#…` 和 `?…` 再判断文件是否存在。t03 评审板大量使用 `r3/home.html#A` 这种写法，不去掉会一律报 `missing_reference`。
- `r2/artifacts.html` 的 iframe 指向 `../../../../../../w00017-…/t80…/index.html`，在产物目录之外。这类引用不在 `contentHash` 的范围内，t09 的产物来源也未必提供。建议单独给 `reference_outside_artifact` 警告。

## 已核实没有问题的方面

- **轮询会不会读到写了一半的答复**：仔细检查后没有发现问题。`createFile` 先把内容写进 `run/tmp`，再用 `link` 一次性放到位，读的一方只会看到完整文件。
- **直接依赖 parse5 是否合规**：仔细检查后没有发现问题。
  - `packages/AGENTS.md` 和 `docs/standards/code/packages.md` 都没有禁止第三方依赖；
  - `bun.lock` 里有 `parse5@8.0.1`，它唯一的依赖 `entities@8` 嵌套在它下面；
  - `bunfig.toml` 用的是 `linker = "hoisted"`，主工作区根目录的 `node_modules` 里已经有 8.0.1，所以合入后不重装依赖，shim 也能正常解析；
  - 行列信息可用。
- **`contentHash` 的成本**：t03 评审板 29 个文件 519 KiB，列文件加算哈希共约 8 毫秒；t80 评审板 26 个文件 1473 KiB，约 6 毫秒。即使到每 Task 5 MiB 的上限，也只有几十毫秒。
- **`status` 能否 1 秒内完成**：
  - 现在真实仓库 22 个 Work、250 个 Task，4 次耗时 973、989、977、995 毫秒；
  - 新增的读取（读 250 个 Task 目录，读 97 份 Markdown 的标题，Work 层另有 10 份，以及 3 个产物目录）实测 4.5 到 17.7 毫秒，与计划“不到 30 毫秒”的估计一致；
  - 另外两点：收件箱要读答复文件的内容和 provenance，不只是文件名；`questions.ts` 如果在顶层导入 parse5，`status` 会多出 8 到 20 毫秒，建议在发布路径里按需导入。
- **两个进程同时发布的版本号**：都在同一把锁里，不会重号。
- **t03 评审板 `index.html` 加标记后的解析**：题都是静态的 `section`，parse5 解析正常，单页约 21 到 25 毫秒。

## 对决定点的判断

1. **答复与确认不记会话**：同意。这与不变量 1 一致，`submittedBy.kind` 保留了“是代录”这个关键信息，待确认清单里也已经登记。
2. **`--wait` 缺省 30 分钟**：同意。每次超时要花一轮唤醒，代价很小；但文档必须分开写退出码 0 和 4 的重挂办法（见第 17 条）。
3. **被取代、被撤回的题号不复活**：同意。但要先定义清楚“关闭再重新打开”这种情况，否则重新打开就要整体换题号（见第 2 条）。
4. **Task 关闭时还有 `open` 的必答题只警告**：同意。
5. **design-review 与命令行同一次合入**：同意时机，但 Skill 要加一句过渡条款。我核实过：`~/.local/bin/nbdev` 还不存在，`master` 上也还没有 dev-panel；合入后第一次在真实仓库发布又要开发者授权。所以 Skill 里要写明“nbdev 不可用或还没获授权时，按旧做法”。
