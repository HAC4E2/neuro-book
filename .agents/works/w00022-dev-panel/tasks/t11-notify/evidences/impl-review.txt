## 发现

### 重要 1：判“暗色占位”的 SGR 解析把 24 位色、256 色 2 号当成暗色，带颜色的输入框内容一律判为“空”，可投

- **位置**：`packages/dev-panel/src/herdr/screens.ts:33-48`（`segments`），由第 89 行 `typed` 使用。
- **现象**：`segments` 把一个 SGR 的参数按 `;` 拆开后逐个看，见到 `"2"` 就置暗色。可 `38;2;r;g;b`（24 位前景色）、`48;2;r;g;b`（24 位背景色）里的第二个参数就是 `2`，`38;5;2`（256 色的 2 号）最后一个参数也是 `2`。于是凡是用 24 位色（或 256 色 2 号）着色的文字都被当成暗色，进而被当成“占位或建议文字”，`typed` 为空。交叉核对拦不住：它比的是 herdr 的预览与这一行 `❯` 之后的**全部**文字（暗的、不暗的都算），两边都含这段字，照样一致。
- **为什么是问题**：
  - “输入框里有字就不投”是这次投递判据的核心（设计审查 B1、I1：防止指针消息接在开发者的半截字后面一起提交）。
  - herdr 把屏幕转成 ANSI 时，所有 RGB 颜色都写成 `38;2;r;g;b`（`tests/fixtures/screens.json` 里真实 Claude 的横线、状态栏都是这样）。只要 Claude 给输入框里的内容上了任何 RGB 颜色，例如粘贴块、关键词高亮之类，或者 256 色的 2 号，面板就会认成“空输入框”，把粘贴加回车打进去，开发者准备了一半的输入被连同指针消息一起提交。
  - 真实 Claude 2.1.296 给输入框里哪些内容上色、用哪种颜色写法，本审查没有核实（按规则不起真实 `claude`），所以“实际会被触发”是从代码推断的。解析错误本身是确定的，下面的实验在真实 herdr 上复现了。
- **如何核实**：
  - 纯函数：`scripts/e1-sgr-dim.ts`，结果在 `e1-sgr-dim.out`。无色的半截字判 `input_not_empty`（对）；`❯ \x1b[38;2;255;255;255m我正在打的半截字`、`❯ \x1b[38;5;2m[Pasted text #1 +40 lines]`、`❯ \x1b[48;2;40;40;40mhello` 都判 `{"ok":true}`。
  - 真实 herdr 0.9.3：`scripts/e2-live-colored-input.ts`，结果在 `e2-live-colored-input.out`。在自建命名会话 `nbdev-review-t11i` 里起名为 `claude` 的假界面（`tests/fixtures/fake-claude-tui.py`），把输入行分别画成无色、24 位色、256 色 2 号的半截字。herdr 三次都认成 `live_prompt_box`，预览是 `❯ 我正在打的半截字` 或 `❯ [Pasted text #1 +40 lines]`；`agent.read visible ansi` 原样带回 `\x1b[38;2;255;255;255m` 与 `\x1b[38;5;2m`。无色的判不可投；后两种 `checkDeliverable` 回 `ok`，`deliverText` 写入了 `\x1b[200~[nbdev] E2 …\x1b[201~` 和 300 毫秒后的 `\r`。会话用完已停、已删。
- **建议改法**：
  1. SGR 按标准解析：遇到 `38`、`48`、`58` 时，后面是 `5;n` 就跳过 2 个参数，是 `2;r;g;b` 就跳过 4 个，冒号子参数写法 `38:2::r:g:b` 整段跳过；只有独立的参数 `2` 才开暗色，`22` 与 `0`（以及空参数）才关。
  2. 占位的认法收紧：`❯` 之后去掉空白，只允许“空”或“紧接着的一整段暗色文字”这两种形态，暗色段之后再出现任何字都不可投。
  3. L1 加反例：带 `38;2`、`48;2`、`38;5;2` 颜色的输入（输入框里有字）判不可投。L4 的负样本加一份带颜色的输入。

### 重要 2：根 `AGENTS.md` 那一句“`<W>`、`<T>` 必须是你自己提过问的 Task”，与“发给现在的会话”“通知持有租约的会话”两条手动路径矛盾

- **位置**：根 `AGENTS.md:21`（提交 `0e3a40c9e`）；`packages/dev-panel/src/server/notifier.ts:353-371`（`sendManual` 的候选含 `replacedBy` 与 `alternatives`）；`packages/dev-panel/src/web/parts/ReplacedDialog.vue:24`（小窗文案“现在的会话没读过这道题。发给它，它会照着读答复并记进 Task”）；`packages/dev-panel/src/web/parts/NotifyStatus.vue:52-58`（`no_target`、`legacy`、`not_in_repository` 时列出持有租约的会话，按钮“通知 …”）。
- **现象**：
  - 规则让收到 `[nbdev]` 的会话只在“`<W>`、`<T>` 是你自己提过问的 Task”时照做。
  - 面板却有两条路径，专门把同一行指针消息发给**没提过问**的会话：
    - 会话已更换时“发给现在的会话”：`/clear` 之后的新会话，小窗自己也写着“现在的会话没读过这道题”；
    - 没有可通知的会话时“通知它”：持有这个 Task 租约、但不一定提过问的会话。
  - L3 的场景 3、4（`tests/panel-notify.test.ts:226-260`）测的正是发给这两类会话，断言“已投递”就算通过。
- **为什么是问题**：
  - 守规则的会话收到这两类消息应当不照做。于是这两条路径要么白发，要么要靠会话违反规则才起作用。
  - 小窗对开发者承诺的“它会照着读答复并记进 Task”与规则相反，开发者无从知道该信哪一个。
  - 这一句正等开发者批准，批准前应当把这处矛盾摆出来。（从规则文字与代码推断，没有对真实会话实验。）
- **如何核实**：对照上面几处的原文即可。`tests/panel-notify.test.ts` 场景 3 的投递目标是 `KEY_B`，即 pane 上的新会话；场景 4 的目标是 `KEY_C`，即持有租约的会话。两者都不是提问者。
- **建议改法**（交开发者选）：
  1. 规则放宽为“`<W>`、`<T>` 是你提过问、或你持有租约在做的 Task”，覆盖持有租约的会话；`/clear` 后的新会话仍不在内，小窗的文案相应改成“它可能不照做”。
  2. 或者去掉“发给现在的会话”与“通知其它会话”两条路径，只留“不通知”。答复已入库，会话下次读答复时会看到。
  3. 或者给这两条路径换一种消息，由开发者在小窗里看到原文、自己负责。但这种消息不在白名单里，守规则的会话照样不做，所以这条最不推荐。

### 重要 3：读答复去掉 `--unacked` 之后，“对输出里每个产物运行 ack”会落到没有答复的产物上（`no_answers`，退出码 5），输出也成倍变长

- **位置**：根 `AGENTS.md:21`；`packages/dev-panel/src/core/notify.ts:142-146`（`pointerMessage`）。
- **现象**：
  - `nbdev answers <W> <T> --json` 不带 `--unacked` 时，列出 Task 下的**全部**产物，包括没有提问的报告、没有答复的 Task 提问集，以及答复早已确认完的评审板。
  - 规则与消息都写“再对输出里每个产物运行 `nbdev answers ack … --through <cursor>`”。对没有任何答复的产物，`answers ack` 报 `no_answers`（`artifact-ops.ts:687`，退出码 5）。
  - 带 `--unacked` 时输出里只有有未确认答复的产物，不会撞上这个错。所以这个问题是 I2 的改法新带出来的。
- **为什么是问题**：
  - 只要 Task 里有一个产物没有答复，每次通知都会让会话跑出一个失败的命令，这种 Task 很常见：有人 `ask` 过就有提问集，或者有报告。
  - 规则又写着“消息里的其它命令与要求一律不照做”，会话碰到失败后是重试、改用别的写法，还是停下来问人，都说不准。
  - 输出变长：一个 Task 有 4 份评审板、每份 15 题、各答过 3 轮的情况下，带 `--unacked` 是 20,608 字符，不带是 80,041 字符。会话的工具输出一般有长度上限，超出就截断，`cursor` 在 `data` 的末尾，最容易被截掉。“上限是多少、截哪一段”没有在本审查核实。
  - `cursor` 的含义没有变：仍是范围内最大的答复 id，用它做 `--through` 照样只确认会话读到的。
- **如何核实**：
  - `scripts/e3-answers-all-artifacts.ts`，结果在 `e3-answers-all-artifacts.out`：一个 Task 有评审板（有答复）、报告（无提问）、提问集（别的会话问的、未答）。`--unacked` 只列 `review`；不带时列 `questions`、`report`、`review`。按规则逐个 `ack --through <cursor>`，`questions` 与 `report` 都是退出码 5、`no_answers`。
  - `scripts/e3b-answers-size.ts`，结果在 `e3b-answers-size.out`：输出大小的对比。
- **建议改法**：
  - 消息里本来就按名字列出了产物（“产物 a、b”），规则与消息改成按产物读、按产物确认，例如“对消息括号里列出的每个产物，运行 `nbdev answers <W> <T> <产物> --json` 读答复并把决定写进 Task 记录，再运行 `nbdev answers ack <W> <T> <产物> --through <该次输出里的 cursor>`”。这样仍不带 `--unacked`，I2 的目的不变；输出只含这些产物，也不会 ack 到没有答复的产物。
  - 或者保留 Task 级读取，把第二步改成“对输出里有答复的每个产物”。
  - 两种改法都要同时改 `pointerMessage` 与它的 L2 断言（`tests/notify-core.test.ts:75-80`），并保持逐字对应。

### 重要 4：收口时有一个失败的发送在进行，`Notifier.stop()` 抛出，`server.stop()` 后半段被跳过：面板放了锁、删了 `panel.json`，却仍在监听端口、不退出

- **位置**：
  - `packages/dev-panel/src/server/notifier.ts:108-120`（`stop` 里 `Promise.race([Promise.all([...this.inFlight, this.running]), 定时器])`）与 `:264-269`（`track` 放进 `inFlight` 的是原始的 `work`，会被拒）；
  - `packages/dev-panel/src/server/serve.ts`（`stop()` 里 `await notifier.stop()` 在 `state.stop()`、关 WebSocket、`panel.stop(true)`、`artifacts.stop(true)` 之前）；
  - `packages/dev-panel/src/cli/panel-commands.ts:60-68`（逐步收口，每步的异常只记一行日志）。
- **现象**：`sendManual` 判定不过时抛 409，`tryAuto` 里写审计或写记录失败时也会抛，这时 `track` 收进去的 promise 被拒。收口期间只要有一个这样的 promise 被拒，`Promise.all` 立刻拒绝，`Notifier.stop()` 跟着抛出，`server.stop()` 停在 `await notifier.stop()` 这一行：`state.stop()`（herdr 监视的定时器与订阅、文件监视）没做，两个 `Bun.serve` 也没关。命令行的收口记一行“收口时出错”，接着删 `panel.json`、放锁，打印“面板已退出”，但事件循环里还有监听的端口与定时器，进程不退出。
- **为什么是问题**：
  - 前台运行时，开发者按 Ctrl+C 看到“面板已退出”，面板其实还在：端口照常回应、登录的 cookie 照常可用，而锁已经放掉，再起一个面板会撞上 `port_in_use`。
  - 作为服务运行时，`systemctl --user stop`/`restart` 要等满 `TimeoutStopSec=30` 再 SIGKILL。
  - 这与 S11“收到 SIGTERM 先等进行中的投递结束（有上限），再收口”的合同不符：第一个失败就不再等其余进行中的投递。
  - 触发要求收口恰好落在一次会失败的发送当中，概率不高；但后果是收口半途而废，属于禁止清单里的“丢掉清理语句”。
- **如何核实**：`scripts/e4-stop-reject.ts`（借用 `scripts/panel-setup.ts`、`fake-herdr-proc.ts`、`panel-proc.ts`），结果在 `e4-stop-reject.out`。
  - 用真实的 `nbdev panel serve`（worktree 的 `cli.ts`，临时仓库，审计指到临时 `XDG_CONFIG_HOME`，假 herdr 报 0.9.2，任务是 `manual_only`），端口 4461 到 4464。
  - 对照组：没有进行中的发送，SIGTERM 后 100 毫秒退出，端口关闭。
  - 实验组：让假 herdr 的 `agent.read` 不回应，发起手动发送，400 毫秒后发 SIGTERM。2 秒后读屏本地超时，`sendManual` 抛 409，日志记“收口时出错：读屏失败（client_timeout）”与“面板已退出”。之后 20 秒进程仍在，`/api/meta` 仍回 HTTP 200，`panel.json` 与面板锁都已删除。脚本最后用记下的 PID 结束了它。
- **建议改法**：`stop()` 里改用 `Promise.allSettled([...this.inFlight, this.running])`。或者让 `track` 收进 `inFlight` 的是 `work.catch(() => undefined)`：注释原意是“只为收口时等它”，失败已经经 `work` 交给调用方。顺带把会话页的文字与按键也纳入同一份 `inFlight`，它们现在不在里面，收口时不等。加一条 L3：在进行中的手动发送失败的同时收口，断言 `server.stop()` 正常返回、端口关闭。

### 建议 5：暗色模式下产物页 iframe 深底黑字（t09 起就有）：原因是 iframe 元素自己的底色用了面板的主题色，Chrome 只在 iframe 载入时按明暗是否一致决定要不要垫白底

- **位置**：`packages/dev-panel/src/web/pages/ArtifactPage.vue:127`，iframe 的行内样式 `background: var(--page-surface, var(--bg-main))`。
- **现象与原因**：
  - 产物页多半没有自己的底色、用缺省的黑字。iframe 元素的底色取面板的 `--page-surface`，暗色时是 `rgb(45, 41, 37)`，会从透明的页面后面透出来。
  - Chrome 的规则是：iframe 元素的 `color-scheme`（随面板根元素，暗色时为 `dark`）与页面的不一致时，在页面后面垫一层不透明的白底。这一层是在 iframe **载入时**决定的，之后面板切换明暗不会重算。
  - 所以直接在暗色下打开产物页是白底黑字，看得清；先在亮色下打开、再切到暗色（系统切换，或顶栏的明暗按钮），就成了深底黑字。主 Agent 的截图是后一种情形。
- **如何核实**：`scripts/e6-iframe-dark.ts` 与 `scripts/e6b-iframe-dark-switch.ts`，结果在 `e6-iframe-dark.out`、`e6b-iframe-dark-switch.out`。真实面板用 worktree 构建的前端、临时仓库，Chrome 稳定版。截图在 `.local/agent/works/w00022-dev-panel/tasks/t11-notify/shots/review-t11-iframe-*.png`：
  - `review-t11-iframe-dark-as-is.png`：直接以暗色打开，白底黑字；
  - `review-t11-iframe-switch-{system,toggle}-as-is.png`：亮色打开再切暗，深底黑字，复现了问题；
  - `review-t11-iframe-switch-*-fix-no-bg.png`：只去掉底色、切换之后，透出外层的深色，没有修好；
  - `review-t11-iframe-switch-*-fix-light-white.png`：iframe 设 `color-scheme: light` 与白底，两种切换下都是白底黑字；
  - `review-t11-iframe-dark-light-scheme.png`：只设 `color-scheme: light`、保留主题底色，载入时就是深底黑字。
- **建议改法**：iframe 的行内样式改成 `color-scheme: light; background: #fff`，或者 `background: Canvas` 配 `color-scheme: light`，不用面板的主题色。并在旁边注释原因：产物页按亮色画、多半没有自己的底色；Chrome 只在载入时按明暗是否一致垫白底，切换明暗不重算。想支持暗色的产物页自己设底色即可。

### 建议 6：“看过屏幕再确认”的确认不绑定开发者看到的那一屏

- **位置**：`packages/dev-panel/src/server/session-io.ts:88-91`（`prompt`：`checked.code === "not_deliverable" && fields.confirmScreen === true` 就发）；`packages/dev-panel/src/server/notifier.ts:363-367`（`sendManual` 同样的写法）；前端 `src/web/host/notify-actions.ts:62-72`、`src/web/pages/SessionsPage.vue` 的 `sendPrompt`。
- **现象**：
  - 第一次请求判定不可投，回 409 并附屏幕末尾，开发者看过、点“仍然发送”。
  - 第二次请求只带 `confirmScreen: true`，服务端重新判定。不论这次为什么不可投、屏幕是不是还是刚才那一屏，都照发。
  - 两次之间开发者可能读了好几秒；屏幕换成 herdr 认不出的确认界面（状态仍是 idle）时，粘贴加回车就会打进这个确认界面。这正是 B1 要挡的情形，而开发者确认的是另一屏。
- **为什么是问题**：开发者同意的是“对这一屏发送”，不是“这个 pane 无论现在是什么样都发”。概率不高：两次请求之间要恰好换屏，而且要换成 herdr 认不出的界面；但改起来不难。
- **如何核实**：`scripts/e7-confirm-screen-toctou.ts`，结果在 `e7-confirm-screen-toctou.out`。真实的 `panel serve`、假 herdr，端口 4469。第一次 `POST /api/sessions/w9:p1/prompt` 回 409 `not_deliverable`，屏幕是“❯ 我正在打的半截字”；随后把假 pane 换成认不出的确认界面（`fallback: default_known_agent_idle_fallback`，状态 idle），带 `confirmScreen: true` 再发，回 200 `delivered`，假 herdr 收到了 `agent.prompt`。
- **建议改法**：409 里多给一个屏幕摘要，例如 `screenTail` 文字加判定原因的 sha256；确认时把它带回来（`confirmScreen: <摘要>`）。服务端重新判定，摘要不同就再回 409，附新屏幕，不发。

### 建议 7：投递后核对只在 500 毫秒后“仍在等确认”时报 `delivered_into_blocked`；回车恰好确认了刚弹出的确认界面时，状态已回到 working，记成 `delivered`

- **位置**：`packages/dev-panel/src/server/delivery.ts:130-145`。
- **现象**：判据是 `after.status === "blocked" && after.stateChangeSeq !== before.stateChangeSeq`。设计审查 I1 担心的那种情形是：粘贴之后、回车之前弹出确认界面，回车把它确认了。这时会话会进入 working，约 500 毫秒后的 `agent.get` 看到的是 working，结果记 `delivered`，界面不会醒目提示。
- **为什么是问题**：`delivered_into_blocked` 的用处，是在“回车可能确认了确认界面”时叫开发者马上看终端。最该提示的那一种情形，它偏偏报不出来。t11 只投空闲的会话，确认界面很少在空闲时自己冒出来，所以概率低。从代码推断，没有实验。
- **建议改法**：用状态序号的跳数补一条。从投递前的 `stateChangeSeq` 到 500 毫秒后，正常是“空闲到工作”一次变化；跳了 2 次以上，或者返回体与复读之间出现过 blocked，就标成要看终端，可以新加一个结果，也可以并入 `delivered_into_blocked`。状态序号每次变化加 1，S0 的记录里有。

### 建议 8：`unknown_status` 那一行给了“通知 …”按钮，可手动发送照样要求空闲，这个按钮按了一定是 409

- **位置**：`packages/dev-panel/src/web/parts/NotifyStatus.vue:52-58`（`targets()` 对 `unknown_status` 给提问者本人的按钮）；`packages/dev-panel/src/server/delivery.ts:61-63`（文字投递要求 `idle` 或 `done`，否则 `status_unknown`）；`notifier.ts:391-396`（`status_unknown` 转成 409 `agent_busy`）；`docs/panel.md` 的状态表写的是“`unknown_status` … 可手动发（仍要空闲）”。
- **现象**：状态未知就不是空闲，所以这一行的“通知”按钮永远走到 409，界面显示“通知没有发出去”。计划的“设计审查的处理”里，“状态未知时手动发”与“状态必须是 idle 或 done”本身就矛盾，实现照后者做，按钮却照前者给了。从代码推断。
- **建议改法**：`unknown_status` 不给按钮，只写“状态未知，空闲之后自动判定”，同时改掉文档里“可手动发”；或者明确允许“状态未知时看屏幕、两步确认后发”，那就要在 `identity` 里给手动发送单开一条路。前一种更简单，与“不在工作中投递”一致。

### 重要 9：同一个会话同时有两个 Task 的通知待发时，两条都永远发不出去（“空闲稳定”的记录被第二条任务当场删掉）

- **位置**：`packages/dev-panel/src/server/notifier.ts:164-175`（`once` 按任务逐条 `tryAuto`）、`:280-307`（`tryAuto`）；`packages/dev-panel/src/server/delivery.ts:85-87`（`not_stable` 把“序号变了”和“还不到 3 秒”合成一个码）。
- **现象**：
  - “空闲稳定”的记录按 pane 存（`this.stable`），任务却是按（Task、提问者）一条。同一个会话在两个 Task 上都有待发的通知时，这两条任务落在同一格 pane 上。
  - 每一轮里，第一条任务发现没有记录，就记下“第一次看到空闲”的状态序号与时刻，然后返回。第二条任务紧接着拿这份刚记下的记录去判定，因为还不到 3 秒，判 `not_stable`，`tryAuto` 随即把记录删掉。
  - 3.1 秒后的下一轮又是这样。两条任务一直停在 `ready`（界面写“空闲，几秒内通知”），一条也发不出去，每 3 秒对这格 pane 调一次 `agent.get`，直到其中一条任务因为别的原因消失。
- **为什么是问题**：
  - 一个主会话推进同一个 Work 的几个 Task、在几个 Task 上都提过问，开发者一次把两边都答了，这是常见的用法。
  - 这时通知静默失效，界面一直说马上就发。
  - L3 只测了一个 Task 一个提问者的情形，没有覆盖到。
- **如何核实**：`scripts/e9-two-jobs-same-pane.ts`，结果在 `e9-two-jobs-same-pane.out`。真实的 `panel serve`、假 herdr 0.9.3，端口 4471 到 4474，同一个 Claude 会话 A（`w9:p1`，空闲，在本仓库）。
  - 对照组：只有 t01 的提问被答复，7 秒内投递 1 次。
  - 实验组：t01、t02 各一题、都被答复，25 秒内投递 0 次，两条任务都停在 `ready`，期间 `agent.get` 调了 24 次。
- **建议改法**：
  - `checkDeliverable` 把两种不稳定分开：“序号变了”与“还不到 3 秒”。`tryAuto` 只在序号变了时删除记录；还不到 3 秒的只排下一次唤醒。
  - 或者按 pane 合并：一格 pane 一轮只处理一条任务，前一条投出去之后会话进入工作，后一条等下一次空闲。
  - L3 加一条：同一个会话、两个 Task，两次投递都在。
