## 发现

实验脚本在 `scratchpad/review-t10-impl/scripts/`，临时仓库在同目录的 `tmp/`，日志在 `logs/`。

### 1.【重要】暗色下“未提交改动”对话框透字：面板前端构建的 CSS 压缩把 nb-ui 的 `backdrop-filter` 丢了，不是零件样式也不是 Dialog 用法的问题

- **位置**：
  - `packages/dev-panel/vite.config.ts:11-16`（`build` 没有设 `cssMinify`，Vite 8.1.4 缺省用 Lightning CSS 压缩 CSS）；
  - 输入：`packages/nb-ui/dist/nb-ui.css:2874-2884`（`.nb-ui-popover-surface` 先写 `backdrop-filter: var(--overlay-blur)`，后写 `-webkit-backdrop-filter: var(--overlay-blur)`）；
  - 受影响的使用处：`packages/dev-panel/src/web/parts/UncommittedDialog.vue:15`（nb-ui 的 `Dialog`，面是 `.nb-ui-popover-surface .nb-ui-dialog-surface`）。
- **现象**：nbook 主题暗色下对话框的面是 `color-mix(in srgb, #2d2925 75%, transparent)`，本来要配 8px 的背景模糊（`--overlay-blur`）。浏览器里对话框面的计算样式 `backdrop-filter: none`，背后编辑器的字以 25% 透过来，清楚地叠在说明文字与差异上（亮色下面是 65% 不透明，同样透字，只是没那么扎眼）。
- **原因**（实验）：
  - 构建产物 `assets/index-*.css` 里这条规则只剩 `-webkit-backdrop-filter:var(--overlay-blur)`，没有不带前缀的那条；Chrome 不认 `-webkit-backdrop-filter`，所以没有模糊。
  - 同一份源码用 `vite build --minify false` 构建，两条都在；用 `build.cssMinify: "esbuild"` 构建，两条也都在。所以是压缩这一步丢的。
  - 直接用 Lightning CSS 转 `.a{backdrop-filter:var(--b);-webkit-backdrop-filter:var(--b)}`，压缩与不压缩、给不给 `targets`（含 chrome 120、safari 16）都只留最后一条 `-webkit-` 的。它把两条当成同一属性的前缀变体合并，保留后写的那条；nb-ui 的写法恰好是不带前缀的在前。
  - 零件自己的样式没有碰面色与模糊；`Dialog` 的用法（`size="lg"`、缺省的不透明遮罩）也没问题。下拉菜单（`FormSelect`）不受影响：它的模糊由 `useDropdownSurfaceStyle` 以内联样式给出，实测计算样式是 `blur(8px)`。
- **为什么是问题**：这个对话框是让开发者确认“把别人没提交的改动一起提交进 master”的地方，说明文字与差异要读清楚；现在暗色下背后的正文和对话框的字叠在一起。另外面板里所有只靠 `.nb-ui-popover-surface` 类给模糊的浮层都一样没有模糊，主题的设计意图在面板里静默失效。
- **如何核实**：
  - 临时仓库 `tmp/h-browser`，面板 4443/4444（`scripts/serve.sh`、`scripts/browser-setup.ts`）。
  - `scripts/browser.ts dialog`：暗色、亮色各开一次编辑页触发对话框，读计算样式（日志 `logs/browser-dialog.log`：`backdrop: "none"`，`--overlay-blur` 能解析成 `blur(8px) …`）。截图 `shots/review-dialog-dark.png`、`review-dialog-light.png`。
  - `scripts/browser-css.ts`：枚举命中对话框面的样式规则，只有一条 `.nb-ui-popover-surface`，它的 `backdrop-filter` 为空（`logs/browser-css.log`）。
  - `scripts/lcss.ts`：Lightning CSS 的转换结果（`logs/lightningcss.log`）。`logs/vite-build-nominify.log`、`logs/vite-build-esbuildcss.log`：两种构建的产物里两条都在。
  - `scripts/browser-blurfix.ts`：只在页面里注入 `.nb-ui-popover-surface{backdrop-filter:var(--overlay-blur)}` 后截图 `shots/review-dialog-dark-with-backdrop-filter.png`，背后的字变成糊团，对话框的字清楚。
- **建议改法**：
  - 面板这边（不改 nb-ui）：`vite.config.ts` 的 `build` 加 `cssMinify: "esbuild"`（已验证产物两条都在），或者 `cssMinify: false`（配置里已写明面板只在本机开、不在乎产物大小）；写一句注释说明 Lightning CSS 会丢掉写在前面的不带前缀的 `backdrop-filter`。
  - 根上的修法在 nb-ui：前缀写在前、标准写法写在后（`styles.css:159-160`、`:661-662` 两处），这是通行顺序，任何用 Lightning CSS 的消费方都会踩到。t10 约定不改 nb-ui，交开发者决定是否另开一处改。

### 2.【建议】编辑 Task 目录里的文档不要求 Task README 已提交：确认之后 master 上会出现没有 README 的 Task 目录

- **位置**：`packages/dev-panel/src/core/edit-ops.ts:79-86`（`TASK_DOCUMENT` 一支调 `resolveWritableTask(scope, w, t)`，没有传 `{requireCommittedReadme: true}`）；对照 `src/core/operations.ts:96-117` 的注释“产物与答复的写入要求 Task README 已提交，否则 `master` 上会出现没有 Task README 的提交”，以及同文件 README 一支（`edit-ops.ts:69`）是传了的。
- **现象**：Task README 与它目录里的 `notes.md` 都还没提交（会话按 Work 规则的兜底办法手工建号、还没来得及提交），面板编辑 `notes.md`：读接口给 `editable: true`；保存时弹“这个文件还没入库”的对话框，确认后提交里只有 `notes.md`。HEAD 上这个 Task 目录没有 README。
- **为什么是问题**：主工作区里 README 在磁盘上，本地的 `governance:check` 看不出来；但任何干净 checkout（CI、别的 worktree 同步 master）都报 `Work Task 缺少 README.md`。核心对产物、答复、确认都用 `task_not_committed` 守住了这条不变量，编辑是唯一漏掉的写入路径。发生的前提是主工作区里有一个未提交的 Task README（`nbdev task new` 会立即提交，所以只在手工建号或迁移的间隙出现），概率低，但改法只有一个参数。
- **如何核实**：`scripts/task-doc-uncommitted-readme.ts`（日志 `logs/task-doc-uncommitted-readme.log`）：`editable: true`；第一次保存 `uncommitted_changes`（`status: ["??"]`、`untracked: true`）；确认后提交成功，`git ls-tree HEAD` 只有 `notes.md`；对 `git archive HEAD` 的导出跑 `verifyWorkContracts` 得到 `Work Task 缺少 README.md：…/t02-manual/README.md`，主工作区本身为空；同一个 Task 上 `submitAnswer` 报 `task_not_committed`。
- **建议改法**：`TASK_DOCUMENT` 一支改成 `resolveWritableTask(scope, match[1]!, match[2]!, {requireCommittedReadme: true})`（读接口随之在 `reason` 里给出 `task_not_committed`，编辑页只读并写明原因）；L2 补一条。

### 3.【建议】“结果未知”在编辑页与新建页的处理与说明不符：没有重新取数，新建页的表单原样可以再交一次

- **位置**：`packages/dev-panel/src/web/host/writes.ts:31`（文案“已重新载入；刷新后看这次写入有没有生效，不要直接再提交一次”）；`src/web/pages/EditPage.vue:68-78`（`unknown` 只出提示，不重取）；`src/web/pages/NewPage.vue:80-83`（失败时保留表单，按钮照常可按）。
- **现象**（浏览器实验，服务端照常写入、浏览器拿到连接重置）：
  - 编辑页：提示写“已重新载入”，但页面没有重取（编辑页本来就不订阅推送）；“保存并提交”仍可按。再按一次走 `hash_mismatch`，“别人改了什么”里显示的其实是自己刚才那次保存。不会写第二次，只是说明对不上。
  - 新建页：提示同上；表单字段原样保留、“新建 Work”仍可按。服务端那次已经建好了 `w00002-lost`，再按一次就会领第二个号（请求不带幂等键；从代码推断，没有再按）。
- **为什么是问题**：设计审查第 2 条要防的正是“看到失败再按一次就多领一个号”。服务端的 `idleTimeout` 与 `request_aborted` 已经把这个窗口压得很窄（回环上基本只剩面板进程中途退出），剩下的只靠一句提示；而新建页上“再按一次”是最顺手的动作。
- **如何核实**：`scripts/browser.ts failures`（日志 `logs/browser-failures.log`）：Playwright 用 `route.fetch()` 把请求送到服务端、再 `route.abort("connectionreset")`。编辑页 `saveEnabled: true`、`retryVisible: false`、服务端已有提交；新建页 `submitEnabled: true`、`slugStillFilled: "lost"`、服务端已有 `docs(w00002): 面板新建 Work w00002-lost 与 t01-first`。
- **建议改法**：
  - 新建页拿到 `unknown` 时把提交按钮置灰，直到开发者在左栏或结果区确认过（例如结果区写“去左栏看有没有新 Work”，并给“我已确认，清空表单”与“我已确认，还要再建”两个按钮），或者至少清空短名；
  - 编辑页拿到 `unknown` 时重取一次 `/api/files`，哈希变了就直接进“别人改了什么”的分支并写明“可能是你刚才那次保存已经生效”；
  - 文案按页面分开：没有重新载入的页面不写“已重新载入”。

### 4.【建议】新建页：预览接口失败会挡住提交，与注释“预览失败不挡提交”相反

- **位置**：`packages/dev-panel/src/web/pages/NewPage.vue:55-57`（注释与把失败写成 `problems: [{field: "preview", …}]`）；`src/web/parts/NewWorkForm.vue:27-30`、`NewTaskForm.vue:24-27`（`errors` 吸收全部 `problems`，`complete` 要求全部为空）。
- **现象**：预览回 500 时提交按钮被禁用，预览区写“preview：预览时 git 失败”，按钮旁没有说明。
- **为什么是问题**：注释与行为相反，后来的人会按注释理解。实际影响小：预览与新建读的是同一份扫描，预览失败时新建多半也会失败。
- **如何核实**：`scripts/browser.ts failures` 的第三段，`page.route` 把 `/api/preview/work` 换成 500，表单填全后 `submitDisabled: true`。
- **建议改法**：二选一并让注释与之一致：要么零件只吸收字段名在表单里的 `problems`（`preview` 这一条只在预览区显示），要么改注释为“预览失败时不让提交”，并在按钮旁写原因。

### 5.【建议】编辑页“连同改动一起提交”成功之后，“这个文件有别人没提交的改动”的提示条还在

- **位置**：`packages/dev-panel/src/web/pages/EditPage.vue:59-66`（保存成功只换 `base` 与 `draft`，不重取 `file`）、`:135-137`（提示条读 `file.data.value.uncommitted`）。
- **现象**：确认一起提交、提示“已保存，已提交 …”之后，页面上方仍写“主工作区里这个文件有别人没提交的改动（ M）”，而 `git status` 里这个文件已经干净。
- **为什么是问题**：开发者刚确认过把别人的改动一起提交，紧接着又看到“有别人没提交的改动”，会以为提交没带上或又被改了。下一次保存不受影响（服务端现算）。
- **如何核实**：`scripts/browser2.ts` 第二段（日志 `logs/browser2.log`：`bannerStillVisible: true`、`gitStatusOfFile: ""`），截图 `shots/review-edit-after-confirm.png`。
- **建议改法**：保存成功后把本地的 `uncommitted` 置空（或者只重取 `/api/files` 的元信息，不覆盖编辑器文本）。

### 6.【建议】`UncommittedDialog.md` 的能力标签写成空，与仓库里包一层 Dialog 的组件的写法不一致

- **位置**：`packages/dev-panel/src/web/parts/UncommittedDialog.md:1-3`（`标签: []`）。nb-ui 的 `Dialog.md` 是 `[state:local, env:portal, env:global]`；仓库里包一层 Dialog 的组件都把这两条写上，例如 `packages/neuro-book/app/components/common/LucideIconPickerDialog.md`（`[state:local, env:portal, env:global]`）、`common/Dialog.md`。
- **为什么是问题**：组件规范的能力标签是“对实现的如实描述”，`env:portal` 还要求写出渲染目标（这里是 `body`）。不影响行为，只是声明与仓库惯例不一致。
- **建议改法**：标为 `[env:portal, env:global]`，正文写一句“内容经 nb-ui 的 Dialog 渲染到 body，Esc 与遮罩点击关闭”。

### 7.【重要】根上的完成门禁 `scripts/ci/dev-panel-records.test.ts` 在 Node 下因未处理的 EPIPE 失败（5 次全跑 5 次退出码 1）；根因在 `git.ts`，t10 的新用例与更多 Git 调用让它几乎每次出现

- **位置**：`packages/dev-panel/src/core/git.ts:43`、`:56`（`stdio` 一律 `pipe`，`child.stdin.end(options.input ?? "")` 对不读 stdin 的 Git 子命令也写一次，`child.stdin` 没有 `error` 监听）。触发它的是 `scripts/ci/dev-panel-records.test.ts:85-100`（t10 新加的“面板与命令行同时新建 Work…”）；CI 在 `.github/workflows/code-baseline.yml:109` 跑这份测试。
- **现象**：
  - `bun x vitest run --config scripts/vitest.config.ts scripts/ci/dev-panel-records.test.ts` 连跑 5 次，每次都是 `Tests 5 passed`，但每次带 1 到 5 个 `Uncaught Exception: Error: write EPIPE`（栈指向 `git.ts:56`），vitest 以 1 退出。
  - 只跑 t10 之前就有的三条用例：3 次里 1 次出现同样的 EPIPE；只跑 t10 新加的那条：3 次里 2 次出现。
  - 同一个 `runGit` 并发跑 800 次 `git rev-parse`：Node（tsx）下 1 次未处理的 EPIPE，Bun 下 0 次。
- **为什么是问题**：计划的“验证”一节写根上三个测试文件全部通过，但在本机 Node v26.10.0 下这份文件稳定失败，CI 的 code-baseline 也跑它，会时红时绿。核心库对外声明 Node 兼容（包 `AGENTS.md` 的“边界”一节），在 Node 进程里这是一个未处理的异常，不只是测试噪音。面板与 `nbdev` 跑在 Bun 上，实测没有这个问题，所以不影响产品行为。根因是 t06 的 `git.ts`，不是 t10 写的；t10 的写入路径多了 `hash-object`、`diff --cached`、`status` 等调用，新用例又并发两次 `createWork` 再编辑，命中的机会大了很多。
- **如何核实**：日志 `logs/root-test.log`、`logs/root-test-1.log` 到 `-4.log`（全跑）、`logs/root-test-old-*.log`（只跑旧用例）、`logs/root-test-new-*.log`（只跑新用例）；`scripts/epipe-stress.ts`（Bun）与 `scripts/epipe-stress.mts`（Node，经 `node_modules/.bin/tsx`），日志 `logs/epipe-node.log`。
- **建议改法**：`runGit` 只在给了 `input` 时才给子进程开 stdin（`stdio: [options.input === undefined ? "ignore" : "pipe", "pipe", "pipe"]`）；给了 `input` 的那条再挂 `child.stdin.on("error", …)`，EPIPE 记一条诊断后忽略（子进程提前退出时以退出码与 stderr 报失败），其它错误照常拒绝。改完连跑几次根上的这份测试确认没有未处理的错误。
