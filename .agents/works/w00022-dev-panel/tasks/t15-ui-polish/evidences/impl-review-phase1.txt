## 发现

### 1. 建议：确认前重读屏幕失败时，确认框照开，显示的是早先那一屏

- 位置：`packages/dev-panel/src/web/host/session-console.ts:208-211`（`pressKey`），`:113-127`（`readScreen` 失败时只写提示，不清 `screen`）。
- 场景：选中 A 时读到一屏 S1；过一阵按 Enter，`pressKey` 重读屏幕，这次回 409、503 或超时。`readScreen` 只把提示写成“读不到屏幕”，`screen` 仍是 S1；目标没变，于是确认框照开，屏幕区显示 S1，看不出这不是刚读到的。提示在页面里，被模态框盖住。Enter 的说明写着“可能是‘允许执行’”，开发者是对着旧屏幕批准的。计划 1.1 的改法写的是“屏幕取这次读到的”，失败这一支没有做到。
- 证据：实测。在 `/dev/shm` 里复用 `tests/web-env.ts` 跑：第一次读屏回 S1，第二次回 409 `session_changed`，`pressKey("enter")` 之后 `confirm` 不为空，`confirm.screen` 是 S1，提示是“读不到屏幕”。
- 影响面：最常见的失败（`session_changed`）在发按键时还会被服务端的 `expectedSession` 拦下；剩下的是 herdr 读屏偶发失败、按键却能发出的情况。旧代码也是这样，所以不是回归，但这是 1.1 自己列出的根因（“确认框显示的屏幕可能……是空的”）没收干净的一半。
- 建议改法：`readScreen` 返回这次有没有读到（或直接返回读到的 `ScreenData`）；`pressKey` 只在读到时用这一屏开确认框；没读到就不开，或开着但 `screen` 传 `null` 并在说明里写“这次没读到屏幕：<原因>”。补一条“重读失败不拿旧屏幕开确认框”的用例。

### 2. 建议：发文字在途时同一格换了会话，发出去的文字留在输入框里，还提示“发出去会发给后者”

- 位置：`packages/dev-panel/src/web/host/session-console.ts:154-159`（`sendPrompt` 成功后只在三项身份都相同时才加 `resetKey`、清 `sessionChange`）。
- 场景：在 A 的输入框发 `/clear`。服务端 `agentPrompt` 要等到 working 或 blocked（`src/server/delivery.ts:147`，最长 10 秒），`/clear` 不进 working，多半回 `uncertain`；这期间 herdr 报了新会话 id，面板 500 毫秒一次的轮询先看到，`selected` 变成同一格的 A2。回包到时 `sameTarget(A, A2)` 为假，`resetKey` 不加：输入框里还是 `/clear`，上面还挂着“这格的会话换了（A → A2），发出去会发给后者”，读起来像是没发出去、该再发一次。回包是 `delivered_maybe_wrong_session`（投递的瞬间换了会话）时同样如此。
- 证据：实测（同上的实验环境）：发送挂起时把 `selected` 换成同一 pane 的另一个会话，再放行 `delivered_maybe_wrong_session`：`resetKey` 没变，`sessionChange` 仍是 `{from: A, to: A2}`。
- 为什么算问题：草稿的模型是“按 pane 记”（决定点 2），输入框里的就是刚发出去的那段文字。“A 的回包不清 B 的草稿”防的是换到别的 pane 之后清掉那边新打的字，同一格不存在这个问题。
- 建议改法：发送成功后按 pane（加终端）判断，不按会话：`target.paneId === current.value?.paneId && target.terminalId === current.value?.terminalId` 时加 `resetKey`、清 `sessionChange`。同步改 `parts/SessionConsole.md` 与 `docs/panel.md` 里“给当前目标发送成功后才加 resetKey”的说法，并把 `tests/web-session-console.test.ts` 的草稿用例补上同一格的这一支。

### 3. 建议：给 A 的文字回 `not_deliverable` 时已经换到 B，没有任何提示，文字也被换 pane 清掉了

- 位置：`packages/dev-panel/src/web/host/session-console.ts:161-171`（`not_deliverable` 分支只在目标没变时开“仍然发送”，目标变了什么都不做）。
- 场景：在 A 打了一段字点发送，判定还没回来就点了列表里的 B。换 pane 时 `resetKey` 加一，A 的草稿被清空；随后 A 回 409 `not_deliverable`（输入框里有字、开着菜单），这一支既不开确认框也不写提示。开发者在 B 上什么都看不到，以为那段话已经给了 A，实际没发出去，原文也没了。别的失败（`else` 分支）和 200 的投递结果都会照常写一条带 pane 号的提示，只有这一支是空的。
- 证据：实测：发送挂起时把 `selected` 换成 B，放行 `not_deliverable`：`confirm` 为空，`notice` 为空。
- 影响面：`not_deliverable` 在打字之前就判定，回包快，窗口短，所以列为建议。
- 建议改法：目标已经变了时写一条提示，例如“给 <A> 的文字没有发出去：<原因>；目标已经换了，没有再问”，与其它失败一样带上 pane 号。要不要把原文放进提示让开发者能复制，由主 Agent 定。

### 4. 建议：新建页的“重试”按切换之后的模式提交

- 位置：`packages/dev-panel/src/web/pages/NewPage.vue:123`（`@retry="submit"`）、`:94`（`submit` 现读 `mode.value`）、`:79`（模式只在提交在途时锁）。
- 场景：新建 Work 等锁超时（`lock_timeout`），提示带“重试”，表单解锁；开发者切到“新建 Task”看了一眼（Task 表里有之前填的内容），再点那条提示上的“重试”，发出去的是 `POST /api/works/<id>/tasks`，不是刚才没建成的 Work。提示不随模式切换清掉，所以按钮一直在。这和 1.9 修的 Task 页“重试”是同一类错位（重试现读当前状态），只是换成了页面内的模式。
- 证据：从代码推断；模板接线单元测试测不到，验收没走这条。
- 建议改法：二选一，改动都很小：切换模式时清掉带 `retry` 的提示；或者“重试”按 `submittedMode` 重发（不是 `submittedMode` 时先切回去）。前者更简单。

### 5. 建议：“我已重新登录”时面板连不上，提示文字重复了一遍前缀

- 位置：`packages/dev-panel/src/web/host/panel-data.ts:135`。
- 场景：面板进程已经退出，开发者在阻挡层上点“我已重新登录”。`getJson` 的网络错误本身就是“连不上面板：它可能已经退出……”，这里又拼了一个“连不上面板：”。
- 证据：实测：让 `fetch` 抛 `TypeError`，`confirmRelogin()` 回“连不上面板：连不上面板：它可能已经退出，在终端重新运行 nbdev panel serve”。
- 建议改法：非 401 时直接用 `caught.message`（503 `warming_up` 的“面板正在启动”本身也说得清）。

## 逐项核对（没有发现问题的部分）

下面这些按代码读过、对照了原始缺陷与计划，没有找到要列的问题；“实测”的指本次跑过的测试或实验，其余是从代码推断。

- **会话确认绑定目标（阻断 1）**：`useSessionConsoleHost` 把目标记成 `{paneId, terminalId, sessionKey}`；`confirmRun`、`confirmTakeover`、`need_confirm` 都先比三项再发；`watch(current)` 在目标变化时关掉两种小窗、清屏幕与冲突、把读屏序号加一；读屏与读历史回来时核对目标。按键与文字的请求体里 `paneId`、`expectedSession` 取打开时的目标。确认在途时目标变了会先显示“没有发送”，回包到后被真实结果覆盖，最终提示正确。`tests/web-session-console.test.ts` 9 条实测通过。
- **终端按连接重建（重要 3）**：连接的 `watch` 键是 `paneId + terminalId + authEpoch`（失效期间为 null），每建一条 `connection` 加一，两个终端零件都以它为 key；同一格换会话键不变、连接与终端不动；旧作用域 `stop()` 时关连接、摘监听、清心跳与重连定时器。
- **页面按路由参数重建（1.9）**：`pageKey` 只取路由名与 params；编辑页、会话页、文档页的查询参数变化仍复用实例，`onBeforeRouteUpdate` 照常触发。旧实例卸载后，在途的 `useWrite` 回包只写进已经卸载的 ref，`useResource` 有 `disposed` 挡住补取。Task 页的 `useStatusChange` 随实例重建，“重试”不再跨 Task。
- **编辑会话（重要 4、5）**：换路径时代号加一并清空基线、草稿、冲突、提示；新文件到达时要求 `data.path === path`（服务端原样回传路径，`src/core/edit-ops.ts:164`），所以旧文件的数据不会被当成新文件的基线；`save`、`loadMismatch`、`checkAfterUnknown` 回来时核对代号。保存在途时 `FileEditor` 只读，两个路由守卫直接拒绝；`beforeunload` 照旧。`tests/web-file-edit.test.ts` 5 条实测通过。
- **401 统一出口与恢复（重要 6）**：`readEnvelope` 与 `streamLines` 先按状态码通知，再照常抛 `ApiError`，没有按文案分支；数据宿主失效时关 `/ws`、清重连定时器，`useResource` 不再发请求（含 checkout 页 10 秒一次的 `reload()`）；“我已重新登录”的按钮在请求中是禁用的（nb-ui `Button` 的 `loading` 会置 `disabled`），不会并发两次 `confirmRelogin` 建出两条 `/ws`；重登后全部重取、`authEpoch` 加一、会话页重建终端。外壳不再卸载 `RouterView`。
- **单飞重取（重要 7）**：推送只在不在途时发请求，在途时记一笔，结束后（成功或失败）至多补一次；`reload()` 与地址变化清掉这一笔并中止在途；路径变成 null 时被中止的那次请求的 `finally` 仍会复位 `inflight`（序号没加）。`tests/web-panel-data.test.ts` 13 条实测通过。“推送停下后恰好再取一次”断言成“至多一次”，加上“最后的数据等于最后一次推送之后的状态”，是因为停下那一刻在途请求开始的时刻不确定，不算放宽。
- **旧数据提示（重要 8）**：`stale` 只在有数据又有错误时为真，换地址时数据清空、不会误报；10 个页面都接上了 `StaleNotice`，404 不给重试、给上一级链接。服务端 `state.ts` 恢复时补推一次，前端外壳 `meta` 订阅了 records 与 activity，能收到（`src/server/serve.ts:446-448` 推送带 `parts`，不靠 revision 差）。
- **后台首次建连（重要 9）**：`connect()` 在后台时记 `paused`，回到前台由原有分支连上；`disposed` 与终止码不重连的合同没动。`tests/web-terminal-socket.test.ts` 3 条实测通过。
- **资源收口**：`useResource` 订阅随 scope 摘除；`onAuthLost` 只在模块级注册一次；`stopPanelData` 清定时器、关连接；会话页的 `matchMedia` 监听、终端的 `visibilitychange` 与 `pagehide` 都在卸载时摘掉。没有发现重复订阅或泄漏。
- **测试**：新测试没有跳过、没有 `.only`，没有删改旧测试；产品代码里没有测试专用分支或导出（`stopPanelData` 由外壳卸载时调用）。假 `WebSocket` 的 `close()` 同步派发 close，和浏览器的异步不同，但被测代码在关之前就把连接引用置空或先置 `paused`，两种时序结果一样，没有掩盖问题。`tsc --noEmit -p tsconfig.web-tests.json` 实测通过。
- **偏离计划的四处**：终端 key 用连接序号是对的，只按 pane 加终端的话重登后视图会留在关掉的旧连接上；`StaleNotice` 在首页、Work、Task 放在最上方，因为这三页的标题在数据块里，合理；`state.ts` 恢复时补推，代价是一次 records 订阅者的重取，恢复本来就少见，可以接受，但没有测试钉住（实施记录已写明没验证到）；`useWebEnv(teardown)` 在拆环境之前收口，注释写明了原因，合理。
