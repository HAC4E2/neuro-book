## 条目（按核实顺序追加）

### 重要 1：给 SessionConsole 按会话身份加 key，会在接管中把实时终端整个重建

- **位置**：plan.md 1.2 改法第二点（“给 SessionConsole 加会话身份 key（paneId + sessionKey）”）与决定点 2；web/pages/SessionsPage.vue:282-302（TerminalView 在 SessionConsole 的 #screen 插槽里，298 行）；web/pages/SessionsPage.vue:71-81（终端连接只按 paneId+terminalId 重建）；web/host/terminal-socket.ts:252-255；web/parts/TerminalView.vue:123-176；server/terminal-hub.ts:156、300-308；packages/dev-panel/docs/herdr.md:80。
- **问题**：插槽内容属于子组件的渲染树，SessionConsole 一按 key 重建，插槽里的 TerminalView（或 TerminalTextView）也随之卸载、重新挂载。而同一格 pane 换会话（/clear、--resume，按 docs/herdr.md:80 还有 /compact）时终端与连接都没变，接管也不会因此结束。于是开发者接管着 Claude、在终端里打 /clear 回车，面板轮询到新会话 id 之后，正在用的 xterm 被换成一个新实例：
  1. 新实例从空屏开始，而 source.subscribe 只在观看时发 resync（terminal-socket.ts:254），接管中拿不到整屏，只收到之后的增量帧，画面错乱或残缺，直到 TUI 整屏重画；
  2. 新实例挂载时不 focus：term.focus() 只在 mode 变化的 watch 里调（TerminalView.vue:167-176），接管中 mode 没变，键盘输入落到页面上，开发者要再点一次终端；
  3. 服务端照旧认为这个连接在控制（conn.sessionKey 只在 open 时记一次，terminal-hub.ts:156；会话换了不释放），所以界面显示“你已接管键盘”，键盘却不在终端里。
  观看中换会话也会重建 xterm（会发 resync，能恢复，但每次 /compact 都闪一次），输入框里写了一半的字也一起丢掉。
- **为什么**：计划要的是“换会话就丢掉给旧会话写的草稿”，但 key 放在 SessionConsole 上，连带重建了不该随会话变化的终端视图；而接管正是开发者直接在终端里操作、最可能当场 /clear 的场景。终端的身份是 paneId+terminalId，与会话身份是两回事，计划在 1.2 里把两者绑到了同一棵子树上。
- **如何核实**：从代码推断（插槽归属是 Vue 的确定语义）。浏览器里可以这样复现修好前后的差别：接管 A，对 A 运行 pane report-agent-session 换会话 id，等 500 毫秒轮询之后看 .xterm-rows 是否被清空、document.activeElement 是否还是 xterm 的 helper textarea。
- **建议改法**：
  - TerminalView、TerminalTextView 的 key 只取终端身份；更稳的是取“这一条连接”的身份（页面在 71-81 行的 watch 里每建一个 socket 就加一的序号），与 source 对象的生命期一一对应，合同“source 在实例一生里不变”就由构造保证；
  - 草稿随会话清空，改用 SessionConsole 已有的 resetKey（.md 的合同就是“变了清空输入框”）：页面在会话身份变化时把 resetKey 加一，或者把草稿与输入框抽成插槽之外的一个小零件、只给它加 key。不要给包着插槽的 SessionConsole 加 key；
  - 浏览器验收补一个场景：接管 A 期间对 A 换会话 id，断言仍是“你已接管键盘”、终端画面没被清空、打字仍进 A 的日志。
- **补充核实（实验）**：用 happy-dom 加真实的 vue 跑了一个最小树：父零件按 `p1:<会话>` 加 key，插槽里的子零件按终端身份 `p1:t1` 加 key（不变），把会话从 A 改成 B。输出 `Term#1 unmounted`、`Term#2 mounted`：子零件自己的 key 没变也照样重建。上面“从代码推断”的第一步因此是实测成立的；接管中的后果（空屏、失焦）仍是从代码推断。

### 重要 2：同类的身份错位漏了一处：页面实例随路由参数复用，状态切换的“重试”会改到另一个 Task 上

- **位置**：web/App.vue:148（RouterView 没有 key）；web/router.ts:6-9（work、task、artifact 三个带参数的路由）；web/host/status-change.ts:172-218；web/pages/TaskPage.vue:37、78；web/pages/WorkPage.vue:189、215；web/pages/ArtifactPage.vue:29-31、73-97、133。
- **问题**：在同一个 Work 里从 Task A 点左栏到 Task B，vue-router 复用同一个 TaskPage 实例、只换 props（ArtifactPage.vue:29-31 专门 watch 参数去清 version，说明作者知道这一点）。useStatusChange 的 notice、pending 与 last 都挂在实例上，换参数时不清；endpoint() 与 expectedHash() 在发送时现读。于是：
  1. 在 A 上改状态遇到等锁超时（lock_timeout）或面板刚启动（warming_up），提示带“重试”；等锁最长 30 秒，开发者这时很可能已经点去了 B；
  2. 提示留在 B 的页面上，点“重试”会以 B 的端点、B 当前的 README 哈希发出 A 上选的状态，服务端的哈希核对拦不住（哈希就是 B 的），B 被改成 done 或 shelved，核心随之释放 B 的全部租约，并在 master 上提交；
  3. A 的写请求在途时换到 B，A 的“状态已改”或“结果未知”提示也落在 B 的页面上。
  产物页同理：答复的“重试”是 submitAnswer(lastAnswer)，现读 data.value，换到另一个产物后会把 A 的答案按 B 的 workId、artifactId、最新版本发出去（题号相同时服务端照收）；formErrors、lastAnswerId、notice 都不随参数清。产物页之间直接切换现在少见（只有前进后退），状态切换那一条是常见操作。
- **为什么**：这正是计划阶段 1 要收的“异步状态迁移里的身份错位”，而且后果是写到错误的记录、进 master。计划只核查了会话页、编辑页与通知（plan.md 75 行），没有覆盖按参数复用的三个页面。
- **如何核实（实验）**：在 effectScope 里用真实的 useStatusChange，假 fetch 先回 409 lock_timeout、再回成功；props 从 tA 改成 tB 后调 retry()。输出：A 上的结果“没有改 retry = true”；换到 B 之后提示还在；重试发出的请求是 `{"url":"/api/works/w1/tasks/tB/status","body":{"status":"done","expectedHash":"hashB",...}}`，提示“状态已改 已提交 abcdef012”。页面实例复用是 vue-router 的既定行为，未在浏览器里复现。
- **建议改法**（二选一，推荐第一种）：
  - 在外壳给带参数的页面按参数重建实例：`<RouterView v-slot="{Component, route}">` 里给 `<component>` 加 `:key`，取路由名加 params（不含 query，免得 ?pane=、?path=、以后的 ?peek= 也重建）。这样整类“结果与重试落到新页面”一次收掉，新页面不用逐个记得清状态；在途请求的回包只写进已卸载实例的状态，无害。代价是 Work 之间、Task 之间切换不再就地复用（这些页面本来就整页重取）；
  - 或者在 useStatusChange 里把端点在 change 时捕获、retry 用捕获的端点并要求页面的身份未变，同时页面在参数变化时清 notice、pending、formErrors、lastAnswerId 与 lastAnswer。
  无论哪种，都在阶段 1 加一条：L3 用上面的实验做回归（换参数之后 retry 不发请求或提示已清），浏览器验收在 Task 页制造一次等锁超时（page.route 把这次 POST 改成 409 lock_timeout），点左栏到另一个 Task，断言提示不在、没有“重试”。

### 重要 3：1.1 与 1.3 的浏览器验收靠 page.goBack() 换目标，但写法造不出那两条相邻的历史

- **位置**：plan.md 1.1 浏览器验收场景一、场景三（105、107 行），1.3 浏览器验收（161-163 行）；web/pages/SessionsPage.vue:131-133（open 用 router.replace）；web/App.vue:123、138（进会话页的链接都不带 ?pane=）；web/pages/EditPage.vue:139。
- **问题**：
  - 会话页“从列表打开 A”走 `router.replace`，不留历史。场景一“先打开 B，再从列表打开 A，确认框出现后 page.goBack() 回到 B”实际退回的是进会话页之前的那一页：SessionsPage 被卸载，确认框随之消失，审计与假 Claude 日志里自然也没有新的按键。这条用例在修复之前也会“通过”前两个断言，测不到“目标变了自动取消”这条路径（“出现提示”那条断言会失败，但失败原因与要测的无关）。场景三同理。
  - 1.3 写“经 Task 页的‘编辑 README’链接进入”造 /edit?path=B、/edit?path=A 两条相邻历史：从 Task 页进编辑页，历史是 [Task 页, 编辑 A]，后退回到 Task 页，走的是 onBeforeRouteLeave 而不是要测的 onBeforeRouteUpdate 换文件路径。只有计划里的另一个写法（经 __vue_app__ 上的路由 push）能造出来。
- **为什么**：验收是阶段 1 唯一覆盖模板接线（:key、确认框关闭、提示位置）的手段（plan.md 45-49 行），造法不对，这几条就等于没有浏览器证据。
- **如何核实**：读代码。站内没有任何链接带 ?pane=（grep 'pane=' 只在 SessionsPage 与 terminal-socket 的连接地址里出现），会话页里换 pane 只有 replace 一条路。
- **建议改法**：两处都统一用路由的 push 造历史（`document.querySelector('#app').__vue_app__.config.globalProperties.$router.push(...)`，计划已允许“只用于驱动验收”），依次 push `?pane=B`、`?pane=A`（或 /edit?path=B、/edit?path=A），每步等页面就绪再继续；后退之后先断言 URL 是 B、页面仍是会话页（或编辑页），再断言确认框关闭与提示。顺带写明 page.on('dialog') 要在 goBack 之前挂上（1.3 的原生确认框）。

### 重要 4：测试方法对模块单例的处理不够：同一进程里的状态与遗留定时器会让无关用例失败

- **位置**：plan.md 共同做法的测试方法（36-50 行）与风险“模块级单例”（466 行）；web/host/panel-data.ts:21-34（panelState、subscribers、socket、attempts、started 都是模块级）、87-98（重连定时器没有保存）、102-106（started 之后 startPanelData 不再建连接）；packages/dev-panel/package.json 的 test 脚本是不带 --isolate 的 `bun test`。
- **问题**：
  1. bun test 默认所有测试文件共用一个模块注册表（实验：两个文件导入同一模块，第二个文件看到第一个文件改过的计数与同一个随机 id；加 --isolate 后各自独立）。计划把推送相关用例放进同一个文件，只解决了“同一文件里不并行”，没解决“用例之间共用状态”：第一个用例 startPanelData() 之后 started 永远为真，后面的用例拿不到新的 /ws；1.5 的用例把 panelState.unauthorized 置真、关掉连接之后，同一文件里排在后面的推送用例（1.6、1.7）再也收不到推送，用例顺序一换就红。别的文件（web-session-console、web-file-edit）一旦触发 401，经新的 onAuthLost 也会翻转这份全局状态。
  2. 遗留定时器会打到别的文件。实验：用例里装上假 WebSocket 与 location，startPanelData()，触发一次 close，然后按计划拆掉环境。约 1 秒后模块级的重连定时器照常触发：probeBeforeReconnect 用真实 fetch 取相对地址失败、只告警，接着 connect() 读 location 抛 ReferenceError，记在下一个文件里一个与面板无关、正在 sleep 的用例头上：`(fail) 另一个文件里与面板无关的用例`。1.5 会把这条定时器存下来并在失效时取消，但正常断线的重连路径仍然没有停止入口；terminal-socket 的心跳与重连定时器在 scope.stop() 时会清，这一点没问题。
  3. 环境的装法有顺序要求：vue 的 runtime-dom 在模块求值时就调 `document.createElement("template")`（实验：先装只有 querySelector 的假 document 再导入 vue，直接 TypeError）。测试文件用静态 import 先载入 vue、再在用例里装环境就没事，但 web-env.ts 要么给假 document 补上 createElement，要么写明“只在 vue 载入之后安装”。
  4. 计划没有测重连与实例变化这两条与单飞交织的路径：单飞在途时来了 hello（实例变了，全部重取），在途的旧实例回包会被接受（实例不同不算回退），之后补取一次拿到新实例的数据——这是对的，但要有用例钉住；决定点 1 的“我已重新登录”恢复路径也没有用例（见重要 5）。
- **为什么**：阶段 1 每个提交都要过全量测试（plan.md 308 行），这类与顺序、时序相关的失败会表现成无关用例偶发变红，最容易诱导出“加一个测试专用的 reset 导出”或“放宽断言”，正是禁止清单要防的。
- **如何核实（实验）**：两组临时脚本：一组是两个测试文件共用模块的计数（不加与加 --isolate 对比）；一组是上面的遗留重连定时器，复现时第二个文件的用例被记为 fail，堆栈指向 web/host/panel-data.ts:81 的 location。
- **建议改法**：
  - 给 panel-data 的单例一个产品里也要用的生命期：startPanelData() 返回或另导出 stopPanelData()，关闭 /ws、清掉重连定时器、复位 started 与 attempts，外壳卸载时调用，认证失效时也走它（omp 报告“重构路线第二步”已经提了“为全应用 WS 增加明确 stop/dispose owner”）。这不是测试专用导出，测试用它在每个用例结束时收口；panelState 的复位也放进同一个入口；
  - 新的前端宿主测试单独成组用 --isolate 跑（例如 test 脚本拆成 `bun test --isolate tests/web-*.test.ts` 与其余两段，或在 web-env.ts 的拆除里断言没有挂着的定时器），不要靠“放进同一个文件”；
  - web-env.ts 的拆除用 afterEach 保证失败时也执行；假 WebSocket 要带 OPEN 等静态常量与 readyState（terminal-socket.ts:264 用 `WebSocket.OPEN` 判断能不能发）。

### 重要 5：决定点 1（阻挡层、页面不卸载）的恢复路径没写全：终端连接回不来，同实例重登不重取，定时器照常打 401

### 重要 7：文档差异的基线（决定点 12）与文档树标“改动”的口径不一致，路径白名单也接不住删去的文件

- **位置**：plan.md“要改服务端的几处”文档差异一行（402 行）与决定点 12（455-457 行）；packages/dev-panel/src/core/docs.ts:79-88（branchChangedDocs 用 `master...HEAD` 三点 diff）、90-101（工作区未提交的改动）、107-127（readDocTree：分支改的、master 有这里没有的）；server/views.ts:275-279（/api/docs/file 的白名单是这个 checkout 的文档树或记录）。
- **问题**：
  1. 计划推荐“对 master 这个引用求差异”，理由是“与文档树标改动的口径一致（要核对）”。核对结果：树上标“改动”的口径是“分支自分出以来改过的（master 与 HEAD 的合并基点，三点 diff）加工作区没提交的”，另列 master 在分支分出之后新增的（master_only）。如果差异接口按计划写的“在那个 checkout 里对 master 求这一个文件的差异”（两点 diff，对 master 当前的提交），那么分支分出之后 master 也改过的文件，差异里会混进 master 那边的新改动，显示成“分支把这些行删了或改回去了”，与树上“这个分支改了它”的含义对不上，读的人会误判分支做了什么；
  2. “新增与删除的文件给整份”：删去的文件（树上的 deleted）与 master_only 的文件在这个 checkout 的文档树里不存在，按现在 /api/docs/file 的白名单（views.ts:278）会 404；新增而没跟踪的文件（树上 `??` 记成新增）不在 `git diff` 的输出里，要单独取工作区文件。
- **为什么**：差异视图是开发者第 4 条现场下钻的核心，基线错了比没有更糟；白名单照抄现有的会让一半的“改动”点不开。
- **如何核实**：读代码，见上面的行号；没有起 git 实验。
- **建议改法**：
  - 决定点 12 改成“与树同口径”：分支改的文件，差异取“合并基点 → 工作区”（`git diff <merge-base master HEAD> -- <path>`，含未提交改动；未跟踪的新文件整份当新增）；master_only 的文件整份显示 master 的版本并写明“分支分出之后 master 新增的”；需要的话另给一个“与 master 当前比”的次要切换，不作缺省；
  - 白名单取“这个 checkout 的文档树 ∪ 这个 checkout 的 changes 列出的路径 ∪ 记录里的文档”，路径照常过现有的路径守卫，git 参数用 `--` 隔开路径、只读调用带 `--no-optional-locks`（core/git.ts:47 的 readOnly 已有）。

### 建议 2：1.6 的单飞不要把显式 reload() 也合并进在途请求

- **位置**：plan.md 1.6 改法（227-231 行）；web/pages/EditPage.vue:34-38、64-68；web/host/panel-data.ts:177、185。
- **问题**：计划让“在途时再来推送或 reload()”都只记一笔。推送合并是对的（饥饿只来自推送风暴）；但 reload() 多半是写入之后调的，意思是“要比这次写入新的数据”，合并进一个写入之前发出的在途请求，会先接受一份写入前的数据。编辑页最明显：保存成功后 draft 等于新 base、不 dirty，这时如果有一个保存前发出的 /api/files 在途（hello 触发的全部重取），它的旧文本回来时 watch 会把 base 与 draft 改回保存前的内容，补取回来再改回新的；中间开发者若已开始打字（只读已解除），dirty 为真、补取被忽略，编辑器就停在“旧基线加新输入”，下次保存报 hash_mismatch、差异里是自己刚保存的内容。/api/files 不订阅任何块（parts 为空），revision 判据保护不到它。
- **建议改法**：只有推送触发的 refresh 合并；reload() 保持现在的“中止在途、立即重取”（调用点都是写入之后、重试按钮与 checkout 页 10 秒一次的轮询，不会形成风暴）。另外两个小点写进改法：path 变了要把 dirty 复位；unauthorized 为真时不补取（与重要 5 一起）。测试加一条：在途请求挂起时调 reload()，旧回包不写进 data。

## 决定点意见

1. **登录失效时的呈现（阻挡层，页面不卸载）**：同意，有条件。前提是把恢复路径补全（重要 5）：重登之后显式全部重取、会话页终端重连、失效期间 useResource 不发请求。否则只保住了草稿，其它都要刷新。
2. **会话输入框的草稿随目标切换**：部分反对。反对用“给 SessionConsole 加 key”实现（重要 1：会连带重建插槽里的终端，接管中失焦、空屏）。对“换会话就清空”本身也有保留：按 docs/herdr.md:80，/compact 也会换会话 id，开发者在输入框里写到一半、Claude 自动压缩一次，字就没了，而从开发者看这仍是同一段对话。建议：换 pane 时清空（经 resetKey）；同一格换会话时保留草稿，在输入框上方给一行“这格的会话换了（A → B），发出去会发给 B”，发送仍带当时的 expectedSession，由服务端核对。若主 Agent 仍要清空，也用 resetKey 而不是 key。
3. **终端零件不加防御性的 watch(source)**：同意。补一句：key 取“这一条连接”的序号（页面每建一个 socket 加一）比取 paneId+terminalId 更直接地保证“source 在实例一生里不变”，也不用另写 watch。
4. **保存在途时编辑器只读**：同意。另见建议 1：保存在途时也拒绝站内离开，否则只读挡住了打字、挡不住“以为丢掉了其实提交了”。
5. **同一地址在不同组件之间共用请求，本阶段不做**：同意。补一个事实：重复的不只外壳与首页、会话页，Work、Task、文档、编辑、产物、新建、会话七个页面各有一份 /api/meta（订阅 records 或 notify），外壳那份订阅全部四块；/api/meta 便宜，单飞之后不会饥饿，开销仍可以接受。
6. **重取遇到 404 时保留旧数据、给“回到上一级”**：同意。
7. **抽屉断点改到 lg**：同意。会话页的“手机”判定（SessionsPage.vue:56 的 `(max-width: 767px), (pointer: coarse)`）与抽屉断点是两回事，计划里写明两个断点各管什么，不要顺手一起改到 1024（那会让 768 到 1024 宽的桌面窗口失去接管）。
8. **左栏完全收起、顶栏给展开按钮**：同意。
9. **Work 页就地展开按需取 Task 接口**：同意。补一句：每个展开的行都是一份订阅 records 与 activity 的资源，Task 接口每次要跑一次 git log 与执行 checkout 的判定（core/task-detail.ts:81-102），展开多行时每次推送就是多次 git；展开的行只订阅 records，或限制同时展开的行数（例如最多 3 行），二选一写进计划。
10. **速览面板显示什么（主 Agent 改为：产物也显示页面本身的沙箱 iframe，加状态行与“去答复 / 打开完整页”，不放答复表单）**：同意主 Agent 的改法。开发者第 3 条要的是“不跳页就能看产物”，只给摘要解决不了；不放表单则避开了表单状态与产物页重复、窄宽下难填两个问题，与后续清单里“产物页内就地答复”推迟的口径一致。实现条件见建议 8（iframe 与产物页共用一个零件、焦点与关闭按钮）。
11. **接管时退出键盘用 Ctrl+]**：同意。Chrome 在 Linux 上不占用它，Claude 与 omp 的界面也不靠它；接管只开放给 Agent 会话，与 vim 的 Ctrl+] 冲突的情形（普通 shell 接管）本来就推迟了。提示条上写明，并保留“释放”按钮作为主要入口。
12. **文档差异的基线**：反对计划的推荐（对 master 这个引用求差异）。理由见重要 7：文档树标“改动”用的是合并基点（三点 diff）加未提交改动，对 master 当前的提交求两点差异会把 master 那边的新改动混进来；应与树同口径（合并基点 → 工作区），master_only 的文件整份显示 master 的版本。
13. **不引入组件挂载测试**：同意，但要承认代价并补上：重要 1 这类“key 放在哪一层”的接线错误只有挂载才测得到，计划靠浏览器验收覆盖，就要把“接管中换会话 id”“同一终端换会话不重建终端”写成验收场景。另外，本审查用 happy-dom 加真实的 vue、渲染函数（不经 .vue 编译）几行就验证了插槽重建，说明以后真要测接线，不一定要引入 .vue loader 与 @vue/test-utils。
