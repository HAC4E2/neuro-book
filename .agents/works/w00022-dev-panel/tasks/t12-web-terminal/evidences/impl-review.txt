## 发现

### F1（重要）xterm 的格宽是按“10px sans-serif”量的：`fontFamily` 里的 `var(--font-mono)` 让 canvas 拒收整串字体，中文与数字被拉开

- **位置**：`packages/dev-panel/src/web/parts/TerminalView.vue:73`（`fontFamily: "\"Noto Sans Mono CJK SC\", \"Sarasa Mono SC\", var(--font-mono), monospace"`）；xterm 6.0.0 的 `src/browser/services/CharSizeService.ts:104-126`（`TextMetricsMeasureStrategy`：`ctx.font = \`${fontSize}px ${fontFamily}\``，再 `measureText('W')`）。
- **现象**：主 Agent 截图里的“标 记 5 2 6 4 2”。xterm 6 优先用 `OffscreenCanvas` 量字宽；canvas 的 `font` 属性不认 CSS 变量，整串赋值被丢弃，仍是缺省的 `10px sans-serif`。于是格宽是 10px 无衬线字体里 “W” 的宽度，与字号无关；DOM 渲染层的 `font-family` 是 CSS，`var()` 照常生效，字形按 Noto Sans Mono CJK SC 画，xterm 再用 `letter-spacing` 把每个字撑满过宽的格子，字与字之间就空出一截。手机文字视图是普通的 `<pre>`，不经 xterm 量字，所以正常。
- **为什么是问题**：
  - 画面难读，与 herdr 那边看到的不一致；
  - 格宽不随字号变：观看时 `watchFontSize` 按容器缩字号（8 到 14px）完全不起作用，窄容器里终端缩不下去，只能横向滚动；
  - 接管时 fit 插件按错的格宽算列数，比容器放得下的少约四分之一（1440 宽时 122 列，按 13px 的真实格宽 6.5px 能放约 165 列）；
  - 行高也按 10px 无衬线字体的字框量（页面语言不同、缺省无衬线字体不同时会更矮，独立页面里是 11px 的行装 13px 的字）。
- **如何核实**：
  - `scripts/b1-desktop.ts`（面板 4481，临时仓库加命名会话里的假 claude 界面，1440×900 暗色）：观看时字号 14px、接管时 13px，“标记52642”每个数字占 8.8px、每个汉字 17.6px，两种字号下完全一样；行容器的缺省 `letter-spacing` 分别是 1.78px 与 2.28px（= 8.78 − 字形宽 7.0 与 6.5）。日志 `b1.log`，截图 `shots/review-watch-1440-dark.png`、`shots/review-control-1440-dark.png`。
  - `scripts/b2-font.ts` 加 `fontpage/index.html`（直接加载 node_modules 里的 xterm 6.0.0，定义与 nb-ui 相同的 `--font-mono`）：`canvas.font = "13px … var(--font-mono), monospace"` 读回来是 `10px sans-serif`，“W” 宽 9.44px；同一串字体把变量换成具体值后读回原串，“W” 宽 6.5px。两个终端的格宽分别是 9.43px 与 6.5px，行高 11px 与 19px。对照截图 `shots/review-font-var-vs-resolved.png`：上面一行就是“标 记 5 2 6 4 2”，下面一行正常。日志 `b2.log`。
- **建议改法**：给 xterm 的 `fontFamily` 不含 `var()`。在 `onMounted` 里从终端容器读一次 `getComputedStyle(frameBox).getPropertyValue("--font-mono")`，拼成具体的字体串再交给 `new Terminal`（或者直接写 `"Noto Sans Mono CJK SC", "Sarasa Mono SC", monospace`，不引用变量）；`TerminalView.md` 写明“xterm 用 canvas 量字，字体串里不能有 CSS 变量”。改完之后 `watchFontSize` 的“等宽字约 0.6 个字号宽”也要按真实格宽（`term` 的格宽或 `fit.proposeDimensions`）重算，否则观看时缩放仍不准；`docs/panel.md` 与截图里的“122 列”会变。

- **F1 补充**：手机 390 宽切到“终端画面（只看）”时最明显：字号已缩到下限 8px，格宽仍是约 8.8px，100 列的画面只露出前 35 列左右、每个字之间隔开一个字宽（`shots/review-phone-terminal-390.png`，`scripts/b3-confirm-phone.ts`，日志 `b3.log`）。

### F2（重要）接管中窗口变窄（小于 768px）：终端换成文字视图，“释放”按钮与终端画面都没了，控制权一直占着

- **位置**：`packages/dev-panel/src/web/pages/SessionsPage.vue:55-61`（`narrowQuery` 按 `(max-width: 767px), (pointer: coarse)` 随时切换）、`:283-292`（`narrow && !showTerminalOnPhone` 时整块换成 `TerminalTextView`，不看是否正在接管）；“释放”只在 `TerminalView` 的状态条里（`packages/dev-panel/src/web/parts/TerminalView.vue:146-150`）；`packages/dev-panel/src/web/host/terminal-socket.ts:52`（新挂上的视图只在观看时发 `resync`）。
- **现象**：桌面上接管之后把浏览器窗口缩到 700 宽（例如把窗口贴到 1366 或 1440 宽屏幕的半边），页面立刻换成手机版式：终端画面没了，只剩文字视图，而且是“还没有画面”（接管中不发 `resync`，要等下一次输出）；状态条与“释放”按钮随 `TerminalView` 一起卸掉；输入框因为 `controlling` 也不给；按键按钮仍是“单击即发”。服务端那边接管照旧：pty 停在网页尺寸，`waiting_takeover` 挡着通知，页面的心跳照常发，所以只有 15 分钟没有输入或切到别的标签页才会释放。
- **为什么是问题**：开发者丢了“正在接管”的提示与释放的入口，却仍然占着控制权、改着尺寸、挡着通知；按钮单击即发又没有任何“你在接管”的提示。设计里“手机不给接管”指的是一开始就不给，没有覆盖“桌面接管之后变窄”。
- **如何核实**：`scripts/b1-desktop.ts` 的“接管中把窗口缩到 700 宽”一段（面板 4481，命名会话）：缩窄之后 `hasRelease: false`、`hasXterm: false`、文字视图是“还没有画面”、没有输入框；pty 仍是 `40 122`，子进程仍是 control。截图 `shots/review-narrow-700-while-control.png`，日志 `b1.log`。
- **建议改法**：正在接管时不切到文字视图（`narrow && !controlling && !showTerminalOnPhone`），或者一变窄就先发 `release`（原因可记 `user` 或新加 `narrow`）再切；另外把文字视图的 `resync` 条件放宽到“接管中新挂的视图也要整屏”（服务端接管时可以不重起 control，而是把最近一帧整屏缓存起来，或者让页面在接管中不卸 `TerminalView`）。前一种改法最小。

### F3（建议）接管时先按“观看时的高度”算行数：接管小窗写的尺寸不对，接管后再 resize 一次；“抢过来”时干脆用的是观看尺寸

- **位置**：`packages/dev-panel/src/web/parts/TerminalView.vue:52-64`（`proposeControlSize` 在观看状态下量容器；观看时容器高度随行数，`h-[70vh]` 只在 `mode === 'control'` 时才加，`:153`）、`:102-111`（接管后容器变高，ResizeObserver 再发 `resize`）；`packages/dev-panel/src/web/pages/SessionsPage.vue:99-105`（收到 `need_confirm` 时 `takeoverAsk` 已经在确认时清成 null，回退到 `terminal.state.cols/rows`，即观看尺寸）。
- **现象**：桌面 1440×900：接管小窗写“终端会改成网页的尺寸 122×30”，实际先以 122×30 接管，约 1 秒后又改成 122×40（释放行 `resizes: 1`）。别处在控制时，“抢过来”小窗写“改成 100×30（现在是 100×30）”，带 `--takeover` 起的 control 也是 100×30，之后再改成 122×40。
- **为什么是问题**：每次接管 Agent 的界面都要连着重排两次；小窗里的“改成多少”不可信，`takeover` 意图行记的尺寸与实际不符；“抢过来”路径的尺寸来源与计划写的“网页终端按字号算出的列数与行数”不一致。
- **如何核实**：`scripts/b1-desktop.ts`（日志 `b1.log`：小窗 122×30，接管时 pty `30 122`，1.5 秒后 `40 122`，释放行 `resizes: 1`）；`scripts/b3-confirm-phone.ts`（日志 `b3.log`：外面先起一个 100×30 的 control，“抢过来”小窗写 100×30，`takeover` 意图 `cols: 100, rows: 30, takeover: true`，接管时 pty `30 100`、1.5 秒后 `40 122`）。截图 `shots/review-need-confirm-1440-dark.png`。
- **建议改法**：算接管尺寸时按接管后的容器算（观看时也给终端框固定高度，或者在算之前临时套上接管时的高度再 `proposeDimensions`）；`need_confirm` 时保留第一次算出的尺寸（确认时不要先把 `takeoverAsk` 清掉，或另存一份），不要回退到 `state.cols/rows`。

### F4（建议）握手开始之后、第一帧回来之前连接关了：照样起 control、接管成功又不改回尺寸，审计却记“失败”

- **位置**：`packages/dev-panel/src/server/terminal-hub.ts:294-319`（`handshake` 只在开头看一次 `conn.closed`，之后经过 `readSize`、写审计意图、收 observe 三次 await，再起 control，中间不再看）；`:328-335`（失败路径：第一行是帧、但 `conn.closed` 为真时，直接 `stream.stop()`，只发 release、不先发 resize 改回，审计结果写 `failed`/`disconnect`）。
- **现象**：页面发出 takeover 之后约 5 到 80 毫秒内关连接（关标签页、切到后台都是关连接），终端停在网页请求的尺寸上，没有任何东西改回；审计里是 `takeover` 意图加结果 `failed (disconnect)`，没有释放行，看不出终端被改过尺寸。连接在起 control 之前就关了的时候（5 毫秒那次），面板仍然为一条已关的连接起了 control。
- **为什么是问题**：与面板被 SIGKILL 时的后果一样（尺寸停在网页的尺寸），但面板好好的；审计写“没接管上”与事实相反。窗口不宽（握手拿到锁之后约 100 毫秒），所以列为建议。
- **如何核实**：`scripts/e08-close-during-handshake.ts`（面板 4481，命名会话，pty 原尺寸 100×30，请求 90×25）：在发出 takeover 之后 5、15、30、60、80 毫秒关连接，pty 都变成 `25 90` 且没改回，审计是 `failed (disconnect)`；45、100、150 毫秒时走到了接管成功再以 `disconnect` 释放，尺寸改回。日志 `e08.log`（每次之后脚本在命名会话里手动改回）。
- **建议改法**：`handshake` 在起 control 之前再看一次 `conn.closed || this.exiting`；失败路径里第一行是帧（已经接上）时，先 `stream.send({type: "resize", …before})` 再收，审计结果记 `attached` 加一行 `release`（原因 `disconnect`），或者至少在 `failed` 行里写明“已改过尺寸、没有改回”。

### F5（建议）“连续 3 次第一行就结束就 4404”只数了“一行都没有”的结束：observe 第一行是 `terminal.closed` 而终端还在时，无限重起

- **位置**：`packages/dev-panel/src/server/terminal-hub.ts:193-210`（`first` 在收到任何一行时就变成 false，传给 `onStreamEnd` 的 `endedBeforeFirstLine` 只表示“一行都没有”）；`:229-232`（只在 `endedBeforeFirstLine` 时 `failures += 1`，否则 200 毫秒后照常重起）。
- **现象**：设计审查 S4 的处理写的是“观看中流结束：终端还在 → 重起一次 observe（连续 3 次第一行就结束则关连接 4404）”。实现里第一行是 `terminal.closed`（herdr 拒绝这次观看、终端仍在列表里）不计数，于是每 200 毫秒加一次对账就重起一个 setpriv 加 herdr 子进程，一直到页面关掉。结束原因也不进日志（观看分支不记 `closed` 的原文），看日志找不到原因。
- **为什么是问题**：S4 的兜底没有按处理意见落实；遇到 herdr 拒绝观看的情形（版本不兼容、对账拿到的是旧快照等）就成了每秒四五个子进程的忙循环。
- **如何核实**：`scripts/e13-observe-closed-loop.ts`（L3 夹具，假命令行的 `gone` 模式：observe 第一行就是 `terminal.closed`，假 herdr 的 pane 列表里终端还在）：6 秒内推了 27 次 `state`（即起了 27 次 observe），连接一直没关。日志 `e13.log`。包里的 L3 只测了“终端也不在了 → 4404”。
- **建议改法**：计数条件改成“这条 observe 没出过一帧就结束”（`onLine` 里只在收到帧时置位），收到 `closed` 时把原因写进面板日志；补一条 L3（终端在、observe 第一行就 closed → 第三次之后 4404）。

### F6（建议）审计的结果行与释放行把设备写死成 `local`，没有按 S10 从连接取

- **位置**：`packages/dev-panel/src/server/terminal-hub.ts:352-359`（`auditResult` 写 `device: PANEL_DEVELOPER.device`）；对照 `:300`（意图行用 `conn.device`）、`:146`（`state` 里的 `controller.device` 也取自连接）。
- **现象**：`takeover` 的结果行与 `release` 行不经连接，直接写常量设备；只有意图行取自连接。
- **为什么是问题**：S10 的处理要求“审计行的 `device` 与 `state` 消息里的控制者都从连接取”，理由就是 t13 不必回头逐处改；现在 t13 引入别的设备之后，同一个 `actionId` 的意图行与结果、释放行会写出不同的设备。从代码推断（t12 里所有设备都是 `local`，没有可观察的差别）。
- **建议改法**：`auditResult` 收一个 `device` 参数（或直接收 `conn`），三处调用都传 `conn.device`。

- **收口与控制权**（命名会话、真实 herdr 0.9.3，pty 都核对 `stty -F`）：
  - 面板 SIGTERM（`e04-term.log`）与给面板进程组 SIGINT（模拟前台 Ctrl+C，`e04-int.log`）：页面收到 `released: panel_exit, restored: true`，约 1 秒内面板与子进程都退出，尺寸改回，随后不带 takeover 的 control 能连上；子进程自成会话，进程组的 SIGINT 打不到它们。
