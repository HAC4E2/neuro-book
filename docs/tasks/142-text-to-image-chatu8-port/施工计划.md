## 2. 背景与现状

当前代码同时存在两套互相矛盾的设计：

1. 服务端仍实现 `lorebook/character/<groupId>/<characterId>/visual.json`、分组 CRUD、分组扫描和显式 `groupId` 解析。
2. 前端 `loadGroups()` 只保留服务端返回的第一个分组，并显示“角色统一归属于当前项目，不再新建分组”。
3. 前端记录了 `activeCharacterGroupId`，但角色视觉读取、保存、生成和删除没有把 `groupId` 传给 API。
4. `character-visual.get/put/list` 的现有合同测试明确拒绝浏览器提供 `groupId`。
5. 正文扫描在没有显式 `groupId` 时扫描全部分组，没有 Project 级“已启用分组”状态。
6. “当前启用角色”分页实际上按角色名和触发词展示角色，并没有真正的启用开关。
7. `listCharacterGroups()` 依靠目录中是否直接存在 `visual.json` 区分“角色目录”和“分组目录”，角色原始 Markdown 与视觉分组共用命名空间，结构存在天然歧义。
8. 当前 `character-visual.generate.post.ts` 在 LLM 返回后立即写入 `visual.json`，用户没有覆盖、另存或取消的确认机会。
9. NovelAI 页面顶部存在独立“生图方案组”，下方又有“画风串和模型参数设置”，入口和术语重复。

因此本次不继续在现有单集合合同上补条件分支，而是统一角色、分组、视觉文件、启用状态和画风串的数据模型。

## 3. 最终产品合同

### 3.1 领域层级

```text
Project
└── 角色分组（故事阶段 / 启用范围）
    └── 角色（稳定 characterId）
        └── 一份或多份视觉 JSON（设计版本）
            └── 零套或多套服装
```

各层职责不得混用：

- **角色分组**：表达故事阶段、角色集合和正文自动扫描范围，例如“故事前期”“故事后期”。
- **角色**：表达同一个逻辑人物；`characterId` 稳定，允许安全的中文和 Unicode。
- **视觉 JSON**：表达同一角色在某分组内的一套完整视觉设计；同一角色、同一分组可以有多份 JSON。
- **服装**：属于具体视觉 JSON，不是角色或分组级全局数据。
- **当前选中 JSON**：工作台正在查看和编辑的文件。
- **当前生效 JSON**：正文生成实际使用的文件；浏览历史 JSON 不得自动改变生图结果。

### 3.2 分组合同

- 一个 Project 可以存在多个角色分组。
- `default` 是正式分组，不再使用 `null`、`legacy` 或目录猜测表达默认分组。
- 未手动分组的视觉资料进入 `default`。
- 分组具有稳定 `groupId`、用户可编辑名称、说明、排序和启用状态。
- `groupId` 由服务端生成或校验，用户界面不要求作者手写 ASCII 技术 ID。
- 修改分组名称不修改 `groupId`，也不批量移动文件。
- 分组允许零个、一个或多个同时启用。
- 零分组启用表示正文只生成场景/环境内容，界面必须给出明确提示。
- 分组顺序同时是自动解析优先级；顺序靠前者优先。
- 提供“仅启用此组”快捷操作，但底层仍保存启用 ID 集合，不引入另一套单选模式。

### 3.3 角色与视觉资料合同

- 左侧角色视觉树只列出至少存在一份视觉 JSON 的角色。
- 尚未建立视觉资料的 Lorebook 角色不进入该树；首次建立视觉资料从角色原始档案页或明确的“从角色档案创建视觉资料”入口发起。
- 同一个 `characterId` 可以同时存在于多个分组；各分组的外貌、服装和照片互不覆盖。
- 同一个角色、同一个分组可以有多份视觉 JSON。
- 每份 JSON 是完整快照，不保存依赖其它文件的局部补丁。
- 每份 JSON 包含稳定 `visualId`；其它配置引用 `visualId`，不得引用易变文件名。
- 文件名只用于本地管理和展示，不参与角色匹配、触发或身份判断。
- JSON 内的 `characterId`、中文名、英文名和 `triggerWords` 保持正常角色身份。LLM 角色/服装修改不得擅自改变这些身份字段。
- 修改角色身份或触发词必须走独立的身份编辑操作，并同步更新该角色全部视觉 JSON；不得通过重命名 JSON 实现。

### 3.4 当前生效视觉资料

- 每个 `groupId + characterId` 最多有一个当前生效 `visualId`。
- 点击侧边栏 JSON 只切换右侧编辑对象，不自动改变当前生效版本。
- 文件节点或操作菜单提供“设为当前使用”。
- 当前生效 JSON 在侧边栏显示明确徽标。
- 删除当前生效 JSON 前必须选择替代项；最后一份视觉 JSON 不能作为普通“删除版本”处理，只能走“移出分组/清除该分组视觉资料”的高风险操作。

### 3.5 正文扫描与冲突规则

- 正文自动扫描只读取已启用分组。
- 每个分组只读取角色当前生效的视觉 JSON。
- 同一 `characterId` 同时出现在多个已启用分组时，自动扫描使用优先级最高分组的当前生效 JSON，不重复注入同一个逻辑角色。
- “当前启用角色分组”页面必须显示这类覆盖关系和最终生效来源。
- 不同 `characterId` 使用同一触发词时属于真实歧义，必须返回可理解的冲突信息，不按遍历顺序静默选择。
- 提示词调用显式提供 `groupId` 时，使用指定分组的当前生效 JSON；显式调用用于覆盖自动分组优先级。
- 如果未来调用合同支持 `visualId`，显式 `visualId` 优先级高于 `groupId`；本次首版不要求 LLM 输出文件名。

### 3.6 “发送资料”与启用分组

- “已启用分组”决定正文自动扫描的默认角色范围。
- “发送资料”中的角色选择表示即使正文没有命中触发词，也要向 LLM 提供该角色上下文；两者不是同一功能。
- 发送角色默认存 `characterId` 并在运行时跟随当前有效分组/视觉版本。
- 用户需要固定版本时才额外保存 `groupId` 或 `visualId`。
- 切换故事阶段后，普通发送选择不应要求用户重新勾选全部角色。

## 4. 建议的 Project 存储结构

新真相源与 Lorebook 原始 Markdown 分离，避免分组目录和角色目录同名歧义：

```text
<project>/.nbook/text-to-image/
├── character-groups.json
└── character-groups/
    ├── default/
    │   └── <characterId>/
    │       ├── manifest.json
    │       ├── visual.json
    │       └── visual-20260815T143052123Z-a1b2c3d4.json
    └── <groupId>/
        └── <characterId>/
            ├── manifest.json
            └── visual.json
```

原始角色文档继续位于既有 Lorebook 路径，不因视觉资料写入、重命名或删除而移动：

```text
<project>/lorebook/character/<characterId>/index.md
```

如果真实 Project 中存在其它合法的角色 Markdown 布局，迁移器记录原始 `characterPagePath`，不得为了视觉重构擅自移动作者文件。

### 4.1 `character-groups.json`

建议合同：

```json
{
  "schema": "nbook.character-groups/v2",
  "groups": [
    {
      "groupId": "default",
      "name": "默认分组",
      "description": "",
      "enabled": true,
      "sortOrder": 0
    }
  ]
}
```

更新启用状态和排序时必须原子写入整个规范化快照，避免多个开关请求造成丢失更新。

### 4.2 角色分组内 `manifest.json`

建议合同：

```json
{
  "schema": "nbook.character-visual-collection/v1",
  "characterId": "艾璃丝·赛瑞利亚",
  "activeVisualId": "8fb1f3a2-0000-4000-8000-000000000001",
  "visuals": [
    {
      "visualId": "8fb1f3a2-0000-4000-8000-000000000001",
      "fileName": "visual.json",
      "createdAt": "2026-08-15T06:30:00.000Z",
      "updatedAt": "2026-08-15T06:30:00.000Z",
      "source": "manual"
    }
  ]
}
```

`visuals` 顺序用于稳定展示，不作为冲突优先级。当前生效项只由 `activeVisualId` 决定。

### 4.3 视觉 JSON v2

在现有 `nbook.character-visual/v1` 基础上增加：

- `visualId`；
- 可选的创建/修改来源元数据；
- 保留 `characterId`、角色字段、服装数组和照片数组；
- 保持文件自包含，正文编译器不需要拼接另一个视觉文件才能使用。

`characterId` 和 `visualId` 必须分别校验：

- `characterId` 允许安全的 Unicode 单路径段；
- `groupId` 和内部 ID 使用更严格的稳定 ID 规则；
- 文件名使用独立的 Windows 安全文件名校验，不得复用 `characterId` 校验函数代替。

## 5. JSON 文件创建与重命名

### 5.1 自动文件名

首份视觉资料默认使用：

```text
visual.json
```

LLM“另存为新设计”默认使用：

```text
visual-<UTC时间>-<8位随机标识>.json
```

示例：

```text
visual-20260815T143052123Z-a1b2c3d4.json
```

要求：

- 时间不包含 Windows 禁止的冒号；
- 文件名可按创建时间自然排序；
- 使用排他创建；发生 `EEXIST` 时重新生成随机后缀，绝不覆盖；
- 不依赖文件名推导角色名或触发词。

### 5.2 前端重命名

- 用户可以从侧边栏文件菜单执行“重命名”。
- 前端允许用户输入不带扩展名的名称，并自动补 `.json`。
- 后端必须重新校验，前端校验只用于即时反馈。
- 禁止路径分隔符、控制字符、Windows 保留名称、尾随点/空格和内部保留文件名（至少包括 `manifest.json`）。
- 同一 `groupId + characterId` 目录内按 Windows 大小写不敏感规则检查重名。
- 文件名长度必须留出父路径空间，不能把完整 Windows 路径推到不可维护长度。
- 重命名使用同目录原子 rename；目标存在返回 `409`，不自动覆盖。
- 成功后以 `visualId` 更新 `manifest.json` 的 `fileName`；`activeVisualId` 不变。
- 重命名不改变 JSON 内容、照片登记、角色触发词、发送选择或正文引用。

## 6. LLM 角色/服装修改确认流程

### 6.1 不可变原则

LLM 只生成“待确认草稿”，确认前角色视觉文件零持久化。现有生成接口末尾直接调用 `writeCharacterVisual()` 的行为必须移除。

### 6.2 流程

1. 前端发送当前 `groupId + characterId + visualId`、当前视觉快照和修改要求。
2. 服务端解析 LLM 输出并返回完整候选快照、字段差异、警告以及 `baseRevision`。
3. 前端弹出“应用角色设计修改”Dialog，显示分组、当前文件、角色字段差异和服装新增/修改/删除摘要。
4. 用户选择：
   - **覆盖当前设计**：原子覆盖当前 `visualId` 对应文件；
   - **另存为新设计**：创建新 `visualId` 和新 JSON，更新 `manifest.json`，将新文件设为当前生效并在侧边栏选中；
   - **取消**：关闭 Dialog，不调用提交接口，不修改任何角色文件。

### 6.3 草稿与提交边界

- 草稿保留在前端内存；取消时直接丢弃。
- 提交接口重新用 Zod 校验完整视觉快照。
- 对角色/服装修改锁定 `characterId`、中文名、英文名和触发词；候选值与当前身份不一致时，服务端使用当前身份并返回警告，不能让 LLM 偷偷改名。
- `baseRevision` 使用内容哈希或稳定修订号。
- 用户确认时当前文件已经变化，返回 `409`，不得覆盖新内容。
- 覆盖写使用临时文件加原子 rename。
- 另存顺序为：创建新文件、原子更新 manifest；manifest 更新失败时回滚本次新文件，不改变旧 `activeVisualId`。
- 另存保存完整快照，不保存 delta。

### 6.4 两份“小克”预设的参考合同

两份预设都由 8 条启用消息组成，按 `user → assistant` 交替排列。它们应作为所绑定请求类型的完整消息合同执行，不能在预设末尾再追加一套固定 system/user 提示词，否则会形成重复或互相矛盾的输出要求。

`小克角色/服装展示` 对应 `char_display`：

- 输入变量为 `{{当前角色}}`、`{{当前服装}}`、`{{服装列表}}`、`{{用户需求}}`；
- 输出为一个 `<image>`，内部允许 `<imgthink>`，最终生图串使用 `image###...###`；
- 最终串允许角色调用 `${"name":"角色名","angle":"视角","upperBody":"nsfw/sfw/hidden","lowerBody":"nsfw/sfw/hidden"}$`；
- 最终串还允许独立服装调用 `${"name":"服装名称","upperBody":"visible/hidden","lowerBody":"visible/hidden"}$`；这不是当前编译器已有的“角色对象带 outfit 字段”写法，必须显式兼容；
- `{{tag}}`、`{{{tag}}}` 等双/多重大括号在该预设中同时承担 NovelAI 权重语法，不能被通用占位符扫描器吞掉或改写。

`小克角色和服装修改` 对应 `char_modify`：

- 输入变量为 `{{上下文}}`、`{{世界书触发}}`、`{{当前角色}}`、`{{当前服装}}`、`{{用户需求}}`；
- 输出为一个 `<角色设计>`，内部可以只包含修改后的 `<人物>`，也可以只包含修改后的 `<服装>`，不要求每次重发完整视觉快照；
- 角色字段沿用人物名称、五官正背和上下半身 SFW/NSFW 正背语义；服装字段沿用名称和上下半身正背语义；缺少的当前 v1 字段必须从原快照保留，不能被 schema 默认空字符串清除；
- LLM 回复中的省略表示“保持原值”，不表示删除。删除人物字段或服装必须走独立、显式的用户操作，不能从缺失标签推断。

### 6.5 运行时变量对齐规则

- 只替换注册表中完整匹配的运行时变量。未知 `{{...}}` 原样保留，并在组合提示词预览中列为警告；不得执行任意 JavaScript、EJS、酒馆斜杠命令或其它未声明宏。
- `{{当前角色}}` 使用当前选中 `groupId + characterId + visualId` 的结构化角色字段；不得按角色名重新扫描后命中另一分组或另一视觉版本。
- `{{当前服装}}` 使用工作台当前选中的单套服装；`{{服装列表}}` 使用当前视觉 JSON 的完整服装列表。若尚未选择服装，当前服装为空，但服装列表仍可用。
- `{{上下文}}` 定义为本次请求明确选中的角色原始档案与用户发送上下文；`{{世界书触发}}` 只包含本次请求实际解析并命中的 Lorebook 条目。两者不能都塞入整个 Project 或互相重复。
- 预设导入时显示“已支持 / 将原样保留 / 不支持”的宏诊断。无法对齐的酒馆原生宏不能静默替换为空字符串。

### 6.6 角色展示输出的编译边界

`char_display` 的 LLM 原始回复不能直接作为 NovelAI prompt。服务端必须按以下顺序处理：

1. 保留并流式转发原始回复给测试工具；
2. 去除 `<imgthink>` 等思考块，提取唯一的 `<image>` / `image###...###` 生图块；
3. 使用请求快照中的精确视觉版本展开角色调用和独立服装调用；
4. 合并角色负面提示词，并验证展开后不再残留 `${...}$`；
5. 将编译后的正向/负向 prompt 与 NovelAI 参数一起入队。

独立服装调用优先在 `{{服装列表}}` 对应的当前视觉版本内解析；只有明确设计为 Project 独立服装时才允许全 Project 查找。名称不存在或同名歧义必须在进入 NovelAI 队列前报错，不能把调用源码发给 NovelAI。

### 6.7 角色修改的局部补丁模型

角色修改解析器需要先产生保留字段存在性的中间补丁，而不是立即经过带默认值的完整 Zod schema：

- 顶层区分 `character: omitted | present` 与 `outfits: omitted | present`；
- 人物内部区分“未返回字段”和“明确返回空值”；首版两者都不得删除已有数据，明确清空走工作台手动编辑；
- 服装修改以当前选中服装为首选目标；需要修改其它服装时，按中英文名唯一匹配，歧义时返回可理解错误；
- 将补丁合并到当前完整视觉快照后，再进行完整 schema 校验、身份字段锁定、diff 生成和覆盖/另存/取消确认；
- 只返回 `<服装>` 时必须完整保留人物和其它服装；只返回 `<人物>` 时必须完整保留全部服装与照片。

### 6.8 请求反馈、原始回复与链路可观察性

- “生成首份设计草稿”“生成修改预览”“生成照片 prompt”“生成角色照片”“加入/复制到分组”等所有网络操作拥有各自的 pending 状态，按钮禁用并显示转圈与明确阶段文案；不能只共用一个无法判断具体请求的 `saving`。
- 成功、失败和取消都要结束 pending；跨入口或 Dialog 关闭后的结果使用 `useNotification()`，当前面板可恢复错误保留局部错误。
- LLM 测试工具底部显示最近一次原始回复，支持随 SSE 增量显示；同时显示本次请求类型、实际采用的预设、已解析变量警告、解析结果或解析失败原因。原始回复只保存在调试状态，不写入角色 JSON、日志或公开错误。
- `char_design` 只用于首份角色设计，`char_modify` 只用于已有视觉资料的修改，`char_display` 只用于角色展示/照片 prompt。前端按钮与 API 路由必须逐项做请求类型断言测试。
- “选择分组后加入分组”必须有明确目标分组、重复成员处理、成功反馈和失败恢复；请求期间禁止重复提交，完成后刷新树并选中新产生的视觉文件。

### 6.9 前三份用户预设的参考合同

此前提供的三份独立导出预设同样只作为本地只读参考，不把全文、成人示例或大体积 Tag 库提交到仓库。后续测试使用能覆盖语法边界的最小脱敏 fixture。

- 双大括号权重示例数量很大，不能用“看到 `{{...}}` 就当变量”的正则实现。

### 6.10 五类请求统一的预设执行合同

`image_gen`、`char_design`、`char_display`、`char_modify`、`tag_modify` 必须共用同一套请求快照和预设执行器：

1. 固定请求类型、Provider、预设版本、启用条目、运行时资料和用户输入；
2. 按 `enabled + triggerMode + triggerWords + andTriggerWords` 过滤，但不改变剩余消息的顺序和 role；
3. 顺序执行请求内变量和白名单运行时占位符，保留未知双大括号文本；
4. 根据“自定义完整预设”或“内置默认预设”二选一构造消息，禁止两套合同叠加；
5. 记录脱敏后的消息元数据、变量警告和输出解析诊断；完整正文、完整提示词和原始回复不得进入服务端日志；
6. 将同一份实际消息快照用于“组合提示词预览”和正式发送，预览不能在浏览器另写一套近似拼接；
7. 上游流式响应一边进入原始回复观察通道，一边由服务端累积供最终业务解析；调试显示和最终业务结果来自同一次请求，不允许为了显示原文再请求一次 LLM。

各请求类型的最小运行时输入：

| 请求类型 | 必须提供的运行时数据 | 业务输出 |
| --- | --- | --- |
| `image_gen` | 正文、历史上下文、命中世界书、用户需求、启用角色、通用角色、通用服装、请求内变量 | 一个或多个结构化图片块 |
| `char_design` | 角色原始档案、用户设计需求；已有资料为空 | 完整或可补全为完整的角色视觉草稿 |
| `char_display` | 精确当前角色、精确当前服装、当前视觉的服装列表、用户需求 | 可编译的单张角色展示 prompt |
| `char_modify` | 角色原始档案/选中上下文、命中世界书、精确当前角色、精确当前服装、用户需求 | 保留省略语义的角色/服装局部补丁 |
| `tag_modify` | 当前正向 Tag、修改要求；负向 Tag 只随原资产沿用，不交给 LLM 修改 | 一条完整的新正向 Tag |

`{{当前tag}}` 应增加为正式白名单变量并映射到当前资产正向 Tag。为兼容现有内部合同，可在迁移期让 `{{上下文}}` 同时获得相同值，但新内置预设与调试界面必须使用语义明确的 `{{当前tag}}`。

- Markdown Studio 的角色可用性键和初始角色上下文。

正文链路必须通过 `CharacterVisualResolver` 获得有效视觉，不允许各调用方自行遍历目录并形成不同冲突规则。

照片资产需要记录 `groupId + characterId + visualId`，避免同一角色不同视觉 JSON 的照片写错文件。文件重命名后照片登记仍通过 `visualId` 有效。

## 10. 旧数据迁移

### 10.1 输入

迁移器至少识别：

- `lorebook/character/<characterId>/visual.json`；
- `lorebook/character/<groupId>/<characterId>/visual.json`；
- `.group.json` 分组元数据；
- 已有 `photos[]` 和 `assets/tti/` 受控照片；
- `.nbook/text-to-image-send-data.json` 中的旧 `characterIds`、`characterSelections` 和 `outfitSelections`。

### 10.2 迁移规则

1. 先 dry run，生成计数、目标路径和冲突报告，不写新真相源。
2. 创建 `default` 分组。
3. 旧单层视觉资料迁入 `default`。
4. 旧分组视觉资料迁入同名稳定分组。
5. 每个旧视觉文件分配稳定 `visualId`，第一份可保留 `visual.json` 文件名。
6. 同一角色不同分组的外貌、服装和照片全部保留，不合并视觉内容。
7. 中文和 Unicode `characterId` 原样保留，只做安全单路径段校验。
8. 同一角色不同旧文件的身份字段不一致时进入迁移冲突报告，不静默挑选。
9. 旧 `groupId = null/legacy` 发送选择规范化为 `default` 或“跟随当前有效版本”。
10. 校验新旧角色数、视觉文件数、服装数、照片登记数和资产存在性。
11. 新结构完整校验成功后才切换真相源。
12. 不长期保留双写或两套运行时读取；旧目录只作为一次性迁移输入。是否删除或归档旧文件必须是明确、可恢复的迁移收尾步骤。

迁移必须幂等：重复执行不得创建重复分组、重复视觉文件或重复照片登记。

## 14. 验收标准

1. 一个 Project 可维护多个角色分组，支持零个、单个和多个启用，重开 Project 后状态保持。

6. LLM 角色/服装修改结果先进入确认 Dialog；覆盖、另存和取消三条路径都符合零误写合同。
7. 正文扫描严格使用已启用分组和当前生效 JSON；同角色跨组选择稳定，不重复注入。

10. 中文角色 ID `艾璃丝·赛瑞利亚` 完成读取、保存、LLM 草稿确认、另存、重命名、照片生成和正文扫描全链路。

12. “小克角色/服装展示”预设生成的角色调用和独立服装调用在进入 NovelAI 前按当前精确视觉版本展开，权重语法不受损，原始调用代码不泄漏到 NovelAI。
13. “小克角色和服装修改”只返回人物或只返回服装时，未涉及的字段、服装和照片保持不变，用户确认前磁盘零变化。

15. 所有耗时请求都有可见的进行中、成功或失败反馈；加入分组可完成、可防重复提交、失败后可重试。
16. LLM 测试工具可流式显示最近一次原始回复，并显示实际请求类型、预设、变量警告和解析结果；原始回复不写入业务文件或日志。
17. 正文生图预设的启用/trigger 条目、请求内变量、多图片五要素和分角色提示词按原合同执行；NovelAI 权重与未知宏不被误改。

## 19. 精确施工规格（后续 Agent 以本节为实现准绳）

本节把前文产品合同拆成具体代码施工顺序。后续 Agent 如果发现本节与早期 Task 记录、旧注释或“12+4 字段”等描述冲突，以当前 schema、用户提供的预设合同和本节为准；不能自行选择更省事但会改变用户行为的实现。

### 19.1 目标调用链和责任边界

```text
前端动作
  → 业务 API 校验请求
  → 冻结 Project/角色/资产运行时快照
  → 按 requestType 解析 Provider + 预设
  → 统一预设执行器生成最终 messages
  → OpenAI-compatible 请求（同时发布原始回复观察事件）
  → requestType 专用输出解析器
  → 领域结果：草稿 / 图片块 / Tag / 编译后照片 prompt
  → 用户确认或 NovelAI 入队
```

职责必须保持单向：

- API 只校验输入、读取授权范围内的 Project 数据并调用领域服务，不在路由文件手拼预设消息；
- 统一预设执行器只负责消息合同、trigger、变量、Provider 请求和调试事件，不解析角色/图片/Tag 业务输出；
- 输出解析器只把原始 LLM 文本变成类型化结果，不读写 Project 文件；
- 角色草稿必须经过确认提交，解析器和 LLM 调用阶段都不能写视觉 JSON；
- NovelAI 队列只能接收已经完成角色/服装调用编译的 prompt，不认识 LLM 宏或 XML；
- 原始回复观察功能只读，不得成为业务结果的第二真相源。

### 19.2 第一批必须先落的共享类型

#### 19.2.1 预设模式

在 `TextToImageContextProfileSchema` 增加：

```ts
promptMode: z.enum(["complete", "augment"]).default("augment")
```

语义固定为：

- `complete`：预设条目构成完整消息合同，不追加内置 system/user，也不隐式追加历史消息；预设需要通过占位符自行选择输入；
- `augment`：预设是补充上下文，过滤后的条目在前，随后追加该 requestType 的内置消息；这是现有行为的明确命名。

迁移与默认值：

- 从 chatu8 JSON 导入的 profile 强制写 `complete`；
- 已保存在全局配置、但没有该字段的旧 profile 规范化为 `augment`，确保升级时行为不突变；
- 新建 profile 的 UI 推荐并默认选择 `complete`，同时显示两种模式的用户可见说明；
- 内置 `default` 空 profile 使用 `augment`；
- `complete` profile 如果过滤后没有任何消息，预检直接报错，不能退回内置提示词掩盖配置问题。

这项修改需要同时更新 DTO 测试、配置 normalizer、导入器、导出器、全局配置导入和 LLM 设置 UI。无需修改 Prisma 或创建数据库 migration。

#### 19.2.2 运行时上下文

在现有 `TextToImageRuntimePlaceholderContext` 上新增：

```ts
characterSource?: string; // 角色原始 Markdown/档案
currentTag?: string;      // 当前资产正向 Tag
triggerText?: string;     // 只用于 trigger 条目判断，不直接替换到消息
```

不得把 `requestType` 判断塞进通用字符串替换器。每个业务入口先构造语义正确的 runtime，再交给执行器。

#### 19.2.3 请求快照

新增仅存在于服务端内存的 `PreparedTextToImageLlmRequest`，至少包含：

```ts
type PreparedTextToImageLlmRequest = {
    requestId: string;
    requestType: TextToImageRequestType;
    providerId: number;
    profileId: string;
    promptMode: "complete" | "augment";
    messages: LlmChatMessage[];
    runtimeDiagnostics: RuntimeDiagnostic[];
    provider: {
        baseUrl: string;
        credential: string;
        settings: TextToImageLlmProviderSettings;
    };
};
```

`credential` 只能留在服务端对象中。返回给预览 API 或调试事件时必须投影为不含 credential、Base URL 查询参数、图片二进制和完整 Project 路径的安全 DTO。

#### 19.2.4 运行时诊断

诊断至少区分：

- `unsupported_macro`：看起来像操作宏但未注册，例如 `{{rll 1d999999}}`；
- `preserved_braces`：保留的普通双/多重大括号文本，只汇总数量和少量脱敏示例，避免数千条权重刷屏；
- `missing_required_input`：完整预设没有消费该请求的关键输入；
- `trigger_excluded`：条目因 trigger 未命中而排除，仅在组合预览中展示，不作为错误；
- `output_warning`：未知人物/服装字段、可选包装或兼容回退；
- `truncated_debug_output`：调试视图达到显示上限，业务解析仍使用完整文本。

### 19.3 占位符和变量解析的精确顺序

每条消息必须按原顺序执行以下步骤：

1. 执行 `setvar/setworldvar`，更新本次请求内的变量表；
2. 执行 `getvar/getworldvar`；
3. 替换注册的中文运行时占位符；
4. 解析合法的 `roll`；
5. 扫描疑似未支持的操作宏并生成诊断；
6. 保留所有其它大括号文本，包括 `{{tag}}`、`{{{tag}}}` 和预设示例中的权重。

正式白名单如下：

| 预设占位符 | runtime 字段 | 说明 |
| --- | --- | --- |
| `{{正文}}` | `body` | 当前章节或本次正文输入 |
| `{{上下文}}` | `context` | 本次明确选中的历史/角色上下文，不等同整个 Project |
| `{{世界书触发}}` | `worldBook` | 本次“发送资料”明确选中的 Lorebook 内容；首版不复制 SillyTavern 的自动世界书引擎 |
| `{{用户需求}}` | `userDemand` | 当前按钮对应的用户自然语言要求 |
| `{{角色启用列表}}` | `characterList` | 正文有效角色列表 |
| `{{通用角色启用列表}}` | `commonCharacterList` | 额外发送角色；已有去重规则继续生效 |
| `{{通用服装启用列表}}` | `outfitList` | 额外发送服装列表 |
| `{{当前角色}}` | `currentCharacter` | 请求类型定义的精确当前角色内容 |
| `{{当前服装}}` | `currentOutfit` | 当前选中的一套服装，不是数组 |
| `{{服装列表}}` | `outfitList` | 当前视觉版本内的完整服装列表 |
| `{{角色原始档案}}` | `characterSource` | 新增的清晰别名，供新预设使用 |
| `{{当前tag}}` | `currentTag` | 新增；当前资产正向 Tag |

兼容语法继续支持 `{{getvar::name}}`、`{{setvar::name::value}}`、`{@getvar::name@}`、`{@setvar::name::value@}`、worldvar 对应形式以及合法 `{{roll ...}}`。变量表每次请求新建，消息只准备一次；Provider 重试复用同一份 prepared messages，因此骰子和变量结果不会在重试时漂移，也不会跨请求泄漏。这里的 `worldvar` 只做 SillyTavern 预设语法兼容，作用域仍是当前请求；持久化世界变量、跨会话共享变量和执行 SillyTavern 扩展脚本不在本任务范围内，也不得伪装成已对齐能力。

禁止：

- 不得使用一个宽泛的 `/\{\{.*?\}\}/` 把所有双大括号当变量；
- 不得对未知宏执行 `eval`、模板表达式、SillyTavern 脚本或斜杠命令；
- 不得自动把 `rll` 猜成 `roll`；
- 不得因为变量缺值就替换为字符串 `undefined` 或 `null`；注册变量缺省为空，但必须在预检里记录是否为请求必需输入。

### 19.4 五类请求的 runtime 构造

#### `image_gen`

- `body`：当前章节发送前、应用 `textReplacement` 后的正文；
- `context`：历史正文和解析出的角色摘要，具体分段保持现有历史层数合同；
- `worldBook`：`readProjectSendDataSnapshot()` 返回的 Lorebook 内容，保留 path 包装；
- `characterList`：正文扫描命中、且来自已启用分组的有效角色；
- `commonCharacterList`：发送资料显式选中的角色，去掉已经出现在角色列表中的相同视觉身份；
- `outfitList`：发送资料显式选中的服装；
- `userDemand`：正文生图界面有额外要求时传入；没有 UI 输入时明确为空；
- `triggerText`：正文、用户需求、已选世界书标题以及最终角色/服装的名称和触发词拼接。不要把整份大体积 Tag DNA 放进 trigger corpus。

#### `char_design`

- 只用于尚无 `visualId` 的首份设计；API 不再接受由浏览器决定的 `replace_visual`；
- `characterSource` 与 `body`：角色原始 Markdown；
- `currentCharacter`：为兼容旧角色设计预设，在首份设计时同样映射角色原始 Markdown；
- `currentOutfit`、`outfitList`：为空；
- `userDemand`：本次设计要求；
- `triggerText`：角色原始档案、角色 ID、用户需求。

#### `char_modify`

- 必须携带完整 `groupId + characterId + visualId` 并由服务端读出当前快照；
- `characterSource`、`context`：工作台明确提交的角色原始档案；若为空，显示“缺少角色原始档案”警告，但仍允许只根据当前视觉和修改要求工作；
- `worldBook`：读取 Project 当前“发送资料”中选中的 Lorebook 快照；缺失条目进入 warnings，不把路径文字当内容；
- `currentCharacter`：只序列化当前视觉的 `character`；
- `currentOutfit`：只序列化 `selectedOutfitIndex` 指向的单套服装，未选中时为空；
- `outfitList`：序列化当前视觉全部服装；
- `userDemand`：修改要求；
- `triggerText`：角色原始档案、角色名称/触发词、当前服装名称、修改要求和已选世界书标题。

#### `char_display`

- 必须从完整视觉 ref 读取服务端快照，不能只信任浏览器传来的任意 JSON；
- `currentCharacter`：精确视觉版本的角色字段；
- `currentOutfit`：当前选中单套服装；
- `outfitList`：同一视觉 JSON 的完整服装数组；
- `userDemand`：展示图要求；
- `triggerText`：角色名称/触发词、当前服装中英文名、用户需求；
- 当前视觉存在未保存修改时，生成展示 prompt/照片前必须弹出“保存、放弃、取消”；首版不支持把浏览器临时 JSON 与磁盘视觉混合生成。API 删除任意 `characterText/outfitText` 输入，只接受视觉 ref、`selectedOutfitIndex` 和用户要求。

#### `tag_modify`

- `currentTag`：资产快照中的正向 Tag；
- `context`：迁移期兼容映射为同一正向 Tag；
- `userDemand`：修改要求；
- `triggerText`：当前正向 Tag与修改要求；
- 不向 LLM 发送负向 Tag；返回后只更新“待发送正向 Tag”，原资产、负向 Tag、模型参数和历史图片保持不变。

### 19.5 trigger 与消息组装算法

将现有 `buildContextMessages()` 拆为可测试的准备阶段：

1. 读取绑定的 profile 并冻结深拷贝；
2. 丢弃 `enabled=false`；
3. `always` 直接保留；
4. `trigger` 使用 `runtime.triggerText` 做 Unicode 小写包含匹配：`triggerWords` 任一命中，且 `andTriggerWords` 全部命中；空 `triggerWords` 延续现合同，视为保留；
5. 不修改保留消息的原始 role 和相对顺序；
6. 对保留消息顺序执行请求内变量和占位符；
7. `complete` 模式到此结束；`augment` 模式再按 requestType 追加历史和内置任务消息；
8. 最后执行 `sendImages` 过滤和 `mergeSystemUser`，得到真正发送给 Provider 的 messages；
9. 组合提示词预览返回第 8 步的安全投影，正式请求直接使用同一个对象，不能重新组装。

预检关键输入：

- `image_gen` 的完整预设至少消费 `{{正文}}`；
- `char_design` 至少消费 `{{角色原始档案}}`、`{{正文}}` 或兼容的 `{{当前角色}}` 之一；
- `char_display` 至少消费 `{{当前角色}}`；
- `char_modify` 至少消费 `{{当前角色}}` 和 `{{用户需求}}`；
- `tag_modify` 至少消费 `{{当前tag}}`/兼容 `{{上下文}}` 与 `{{用户需求}}`。

缺少关键输入时，导入阶段给警告；正式执行 `complete` profile 时阻止请求并告诉用户缺哪项。不得自动追加内置 user 消息“帮忙补齐”，否则又会回到双合同问题。

### 19.6 原始回复与流式观察的实现

#### 服务端观察器

新增进程内、按 `userId` 隔离的 `TextToImageLlmTraceHub`：

- 每个用户只保留“最近启动的一次” trace；新请求开始后，旧请求的迟到事件不能覆盖新 trace；
- trace 事件为 `started`、`delta`、`retrying`、`completed`、`failed`；均携带 `traceId`、递增 `seq`、requestType、profileId、model 和时间；
- 不含 credential、Authorization、完整 messages、Project 正文、文件路径或图片数据；
- 原始回复只在内存保留最近一份，最长保留 30 分钟或直到进程重启；调试显示最多 512 KiB，超出时设置 `truncated=true`，但业务解析仍使用完整回复；
- 观察器推送失败不得影响业务请求。

扩展 `requestLlmCompletion()` 的可选 observer 回调，而不是复制第二套 Provider fetch：

- 五类业务请求统一尊重 Provider 的 `stream`、`maxTokens`、temperature、topP、retryCount 等设置；业务 service 不再硬编码 `stream: false` 或角色展示 `maxTokens: 2048`；
- 流式响应每个有效 delta 立即调用 observer，再追加到业务完整文本；
- 非流式响应读取完整 content 后发送一次 delta；
- 429/5xx 等既有可重试条件触发时发送 `retrying`，新 attempt 清空调试视图中的旧半截文本；Provider 重发冻结的 prepared messages，不重新掷骰子或执行变量；
- 最终返回值仍是完整字符串，现有业务解析器不直接消费 SSE event。

#### 调试 API 与前端

- `GET /api/text-to-image/llm/latest-response`：返回当前用户最近 trace 的安全快照；
- `GET /api/text-to-image/llm/response-events`：复用 H3 `createEventStream`，认证后订阅当前用户事件，连接关闭只取消订阅，不取消业务 LLM；
- LLM 设置页打开时先读 latest，再使用现有 `readSseStream()` 订阅；组件卸载时 abort；
- UI 显示请求类型、预设名、模型、attempt、开始/完成时间、流式正文、截断和失败状态；
- “连接测试”仍只发一次 LLM 请求。原始回复面板从 trace 读取，禁止为了显示原文再调用一次模型。

### 19.7 组合提示词预览的正确实现

删除前端 `buildTestPreview()` 的本地字符串拼接，新增只准备、不发送 Provider 的服务端 preview API。请求体使用 requestType 判别联合，避免一个通用 `prompt` 无法表达五类运行时：

- `image_gen`：正文、上下文、世界书、角色列表、服装列表、用户需求；
- `char_design`：角色原始档案、设计要求；
- `char_display`：当前角色 JSON、当前服装 JSON、服装列表、用户要求；
- `char_modify`：角色档案、世界书、当前角色、当前服装、修改要求；
- `tag_modify`：当前正向 Tag、修改要求。

响应至少包含：最终 messages 的 role/content、安全的 Provider/profile 元数据、被排除条目 ID 与原因、运行时诊断和 `promptMode`。图片内容只显示“包含 N 张图片”，不能把 base64 塞进 textarea。

测试工具的正式发送也使用同一判别输入和同一 prepare 函数。预览与发送的单元测试应对最终 messages 做深相等断言。

### 19.8 角色字段与服装字段解析合同

#### 角色 JSON 的真实字段

| 中文标签 | schema 字段 | 首份设计 | 修改模式 |
| --- | --- | --- | --- |
| 中文名称 | `cnName` | 接受 LLM 值 | 锁定当前值，差异记 warning |
| 英文名称 | `enName` | 接受 LLM 值 | 锁定当前值，差异记 warning |
| 触发词 | `triggerWords` | 不要求预设输出；由用户编辑或扫描回退 | 永远保留当前值 |
| 角色特征 | `profileTraits` | 接受 | 未出现则保留 |
| 五官外貌 | `facialAppearance` | 接受 | 未出现则保留 |
| 五官外貌背面 | `facialBack` | 接受 | 未出现则保留 |
| 上半身SFW | `upperSfw` | 接受 | 未出现则保留 |
| 上半身SFW背面 | `upperBackSfw` | 接受 | 未出现则保留 |
| 下半身SFW | `lowerSfw` | 接受 | 未出现则保留 |
| 下半身SFW背面 | `lowerBackSfw` | 接受 | 未出现则保留 |
| 上半身NSFW | `upperNsfw` | 接受 | 未出现则保留 |
| 上半身NSFW背面 | `upperBackNsfw` | 接受 | 未出现则保留 |
| 下半身NSFW | `lowerNsfw` | 接受 | 未出现则保留 |
| 下半身NSFW背面 | `lowerBackNsfw` | 接受 | 未出现则保留 |
| 负面 / 负面提示词 | `negativePrompt` | 接受 | 未出现则保留 |

因此当前持久化角色对象是 15 个字符串字段；常见预设只输出除 `triggerWords` 外的 14 个设计字段。`characterId`、`visualId`、`schema` 和 `photos` 不属于 LLM 人物字段。

#### 服装 JSON 的真实字段

| 中文标签 | schema 字段 |
| --- | --- |
| 中文名称 | `cnName` |
| 英文名称 | `enName` |
| 上半身 | `upper` |
| 上半身背面 | `upperBack` |
| 下半身 | `lower` |
| 下半身背面 | `lowerBack` |

服装对象是 6 个字符串字段，不是旧文档中的 4 个。施工时同步修正 Task README、prompt 注释、测试名称和用户可见字段计数，不能只改代码留下相反文档。

#### 输入包装与首份设计最低有效性

- XML/标签格式继续接受 `<角色设计><人物>...</人物><服装>...</服装></角色设计>`，外层 `<角色设计>` 可省略；人物和服装内部使用上表的精确中文标签。
- JSON 格式接受当前 canonical 英文字段名，也接受上表列出的精确中文键；允许外层为 `角色设计`、`design` 或 `draft`，但归一化后只能得到一个人物和零到多个服装。不得递归搜索任意同名字段，以免把示例、解释或历史内容误当结果。
- 同一响应同时出现可解析 JSON 和 XML 时，若两者归一化后不完全相同则返回“多个互相冲突的候选结果”；完全相同时只保留一份。不得静默按“JSON 优先”或“最后一块优先”。
- `char_design` 必须解析出且仅解析出一个人物；`cnName` 与 `enName` 至少一个非空，并且 12 个外貌/服装 DNA 字段（`profileTraits` 到 `lowerBackNsfw`）至少一个非空，否则视为无效草稿，不允许进入确认 Dialog。
- 首份设计缺少某个可选 DNA 字段时以空字符串完成完整 schema，并把缺失字段列入 warnings；服装可为零套。`triggerWords` 不因模型未输出而报错，也不能从模型解释文本猜测生成。
- 解析器只消费候选数据块；块外解释允许作为诊断丢弃，但不得拼接进任何 JSON 字段。原始全文仍仅在 LLM 调试面板展示。

#### 标签解析规则

- 标签匹配去除首尾空白，中文全角冒号与英文冒号均接受；标签名本身不做模糊相似匹配；
- 同一块出现同一字段两次直接返回解析错误，不能静默使用最后一个；
- 未知字段保留为 warning 并展示给确认 Dialog，不写入 JSON；
- `<人物>` 在 `char_modify` 最多一个；多个人物属于错误；
- `<服装>` 可以多个，但必须按 19.9 的确定规则绑定目标；
- JSON 输出先经过“可选字段 patch schema”，不允许直接用带 `.default("")` 的完整 schema 解析；
- 最终合并完成后才调用 `CharacterVisualFileSchema.parse()`；
- 思考包装统一移除 `<thinking>`、`<think>`、`<tag_think>`、`<imgthink>`、`<disclaimer>`，标签匹配大小写不敏感；包装内容不得进入业务字段。

### 19.9 `char_modify` 局部补丁与合并算法

新增不持久化的中间类型：

```ts
type CharacterFieldPatch = Partial<Record<keyof CharacterVisualField, string>>;
type OutfitFieldPatch = Partial<Record<keyof OutfitVisual, string>>;

type CharacterVisualModifyPatch = {
    character?: CharacterFieldPatch;
    outfits?: Array<{
        fields: OutfitFieldPatch;
        sourceOrder: number;
    }>;
    warnings: string[];
};
```

合并步骤必须严格如下：

1. 读取当前完整视觉快照和 `updatedAt`；
2. 解析 LLM 输出为 patch，保留“字段没出现”和“块没出现”；
3. 人物 patch 覆盖对应可修改字段；`cnName/enName/triggerWords` 强制恢复当前值并记录 warning；
4. 空字符串不执行删除：忽略该字段并记 warning；字段清空只能由工作台手动编辑后保存；
5. 服装绑定：如果请求提供合法 `selectedOutfitIndex`，第一个服装块绑定该索引，即使 LLM 同时改了服装名称；
6. 其余服装块按原快照中英文名做唯一匹配；零匹配且中英文名至少一个非空时视为新增服装；多匹配或没有名称时返回可理解错误；
7. 未命中的原服装全部保留；不从 LLM 省略推断删除；
8. `photos`、`schema`、`characterId`、当前 `visualId` 原样保留；
9. 对合并后的完整候选调用 Zod；
10. 生成逐字段 diff、服装新增/修改摘要、warnings 和 `baseRevision` 返回前端；
11. 覆盖/另存/取消继续走现有 commit 合同，commit 重新验证身份和 revision。

API 调整：

- 初次设计路由只绑定 `char_design`；
- `character-visual.modify-preview` 请求增加 `selectedOutfitIndex: number | null`，严格验证不超过当前服装数组；
- 工作台 `activeVisualId` 为空调用初次设计，有值调用 modify-preview；不再由浏览器传 `mode` 决定 Provider 绑定；
- commit 接口继续接收完整候选快照，不接收原始 patch，避免确认后因基础数据变化重新合并。

### 19.10 `char_display` 输出解析与角色/服装调用编译

#### 输出提取

- 去除思考包装后接受 `<image>...</image>` 或 `image###...###`；
- 角色展示要求恰好一个非空图片 prompt；返回多个时阻止并提示“角色展示预设返回了 N 个图片块”，不能静默取最后一个；
- `<image>` 内允许 `<prompts>` 包装；其它说明性 XML 不进入最终 prompt；
- 原始回复保存到 trace，解析后的 prompt 单独进入编译器。

#### 调用扫描器

把当前正则调用解析改成平衡扫描器，并拆成“扫描”和“解析/展开”两层：

- 识别 `${...}$`，正确处理 JSON 字符串内的转义引号和大括号；
- 不执行 JavaScript，只允许 JSON 对象；
- 保留已有“外层对象大括号遗漏”的兼容形式，但必须产生 warning；
- 继续支持真正匹配旧 marker 规则的 `$...$`，普通美元文本原样保留；
- 未闭合调用、非法 JSON、非法 angle/body 状态在入队前失败。

新调用推荐增加可选 `kind: "character" | "outfit"`，但必须兼容用户预设的无 `kind` 格式。`char_display` 的无 kind 判定只在当前精确视觉快照中进行：

1. `name` 命中当前角色中文名、英文名或触发词 → 角色调用；
2. `name` 命中当前视觉某服装中文名或英文名 → 独立服装调用；
3. 两者同时命中 → 歧义错误；
4. 两者都不命中 → 未找到错误；
5. 不回退扫描其它分组或其它视觉版本。

#### 展开规则

- 角色调用沿用 `front/back` 与上下半身 `sfw/nsfw/hidden`，并累积角色 `negativePrompt`；
- 独立服装调用的 `visible/hidden` 控制上下半身服装字段；
- 独立服装调用如果没有 angle，继承同一 prompt 中前一个角色调用的 angle；没有前序角色时使用 front 并产生 warning；
- back 使用 `upperBack/lowerBack`，front 使用 `upper/lower`；
- 展开后再次扫描，若仍有 `${...}$` 或已识别的旧调用残留，禁止 NovelAI 入队；
- 正向与负向 Tag 做现有规范化去重，但不得改写 `{{tag}}` 权重。

建议抽出可复用接口：

```ts
scanPromptCalls(text): PromptCallNode[]
compilePromptCalls(text, resolver): Promise<CompiledBodyPrompt>
```

正文 resolver 使用 `CharacterVisualResolver` 和启用分组规则；角色展示 resolver 只使用请求快照中的单一视觉版本。不能为了复用而让角色展示重新按名称查询 Project。

### 19.11 `image_gen` 正文输出字段对齐

| 预设字段 | 内部字段 | 规则 |
| --- | --- | --- |
| `<content>/<images>` | 外层容器 | 可有可无，不持久化 |
| `<image>` | `BodyImageBlock` | 按出现顺序产生多个块 |
| `<regex>` | `anchor` | 必须是正文逐字子串，不按正则执行 |
| `<title_styled>` | `title` | 可空，保存到占位符元数据 |
| `<Tag_think>` | `tagThink` | 可空，只用于展示/调试，不进 NovelAI prompt |
| `<size>` | `size` | 保存原值；合法 `宽x高` 可转结构化尺寸，非法值警告并沿用当前 NovelAI 尺寸 |
| `<prompts>` | prompt 容器 | 必须非空 |
| `<scene_composition>` | 场景 prompt | 合并到基础正向 prompt |
| `<character_N><prompt>` | 分角色正向 prompt | N 按出现顺序，最多 4 |
| `<character_N><uc>` | 分角色负向 prompt | 进入对应角色 UC，不混进正向 |
| `<centers>/<center>/<position>` | `centerX/centerY` | 接受现有 0–1 数值或 A1–E5；非法即块解析失败 |

正文块处理增加逐块诊断：

- `<regex>` 为空、`<prompts>` 为空、坐标非法属于解析错误；
- anchor 在当前正文中零命中时不再静默跳过，返回 `anchor_missing` 并阻止本次确认写回；
- anchor 多次命中时返回 `anchor_ambiguous`，要求 LLM 给更长逐字片段；
- 多个图片块使用相同 anchor 时返回冲突，不按数组顺序反复插入；
- 所有块都成功定位后才一次性生成新正文，保持现有章节哈希/CAS；任一块失败时正文零修改；
- LLM 原始 XML 仍只存在内存，正文只写结构化 `<text-to-image-prompt>`。

请求内变量和 trigger 测试至少覆盖：set 后续 get 可见、禁用条目不执行 set、trigger 未命中条目不执行 set、Provider 重试复用完全相同的最终 messages、不同请求不共享变量。

### 19.12 `tag_modify` 字段与输出对齐

解析顺序：

1. 去除 reasoning/disclaimer 包装；
2. 接受 `image###...###`；
3. 接受单个 `<image>`，并剥离内部 `<prompt>/<prompts>`；
4. 接受单个 `<images>`：若内部有一个 `<image>`，解析该块；若内部只有文本或 `<prompts>`，解析其内容；
5. 以上均无时接受无包装纯文本；
6. 折叠换行、trim，并拒绝空结果；
7. 如果得到多个非空候选，返回歧义错误，不静默取最后一个；
8. 最终结果不得残留已知包装标签 `<image(s)>`、`<prompt(s)>`、`<thinking>` 等。

Tag 修改完成只更新对话框内 `pendingPrompt`。发送按钮才使用原 Job 的负向 Tag、模型参数、Vibe/角色参考等快照创建新 NovelAI Job。LLM 失败、解析失败、用户关闭或取消时，资产和队列零变化。

### 19.13 角色管理动作状态机与“加入分组”

用明确动作状态替换一个覆盖所有场景的 `saving`：

```ts
type CharacterWorkbenchAction =
    | "load_library"
    | "load_visual"
    | "save_visual"
    | "rename_visual"
    | "copy_to_group"
    | "create_group"
    | "update_activation"
    | "generate_design"
    | "generate_modify"
    | "commit_overwrite"
    | "commit_create_new"
    | "generate_photo_prompt"
    | "generate_photo"
    | null;
```

状态包含 `kind`、`phase`、`startedAt`。同一面板同一时间只允许一个写操作；按钮是否转圈只看自身 `kind`，其它会冲突的按钮禁用但不显示错误转圈。所有 `try/finally` 必须清理对应 action。

已有视觉出现未保存手动编辑时，调用 `generate_modify`、`generate_photo_prompt`、`generate_photo` 或 `copy_to_group` 前统一复用“保存、放弃、取消”保护。选择保存时等待保存成功后再冻结请求快照；保存失败不继续后续动作。不能让 LLM/复制请求基于磁盘旧版本、界面却显示未保存新版本。

按钮文案示例：

- `generate_design`：正在发送角色资料… → 正在等待 LLM… → 正在解析草稿…；
- `generate_modify`：正在生成修改建议…；
- `generate_photo`：正在生成照片提示词… → 正在等待 NovelAI… → 正在登记照片…；
- `copy_to_group`：正在加入“故事后期”…。

“加入分组”具体流程：

1. 前端先校验当前视觉 ref、目标分组存在且不是来源分组；失败显示局部错误，不允许静默 return；
2. 请求期间锁定来源 ref 和目标 groupId，用户切换 select 不改变已发请求；
3. API 返回 `{ref, info, visual}` 后使用返回的目标 ref；
4. 重新加载树，展开目标分组与目标角色，选中 `result.ref.visualId`；
5. 清空或更新目标选择，显示“已复制到 X，原分组资料仍保留”的通知；
6. 目标已存在同角色时仍创建新视觉版本并由服务端安全分配文件名；
7. 请求失败保持来源选择和目标下拉，允许重试；
8. 双击或连续点击只产生一个请求。

### 19.14 API 合同调整清单

| API | 修改 |

#### 20.4.2 并发与版本冲突

新增正文图片写回服务，建议文件：

```text
server/text-to-image/body-image-writeback.service.ts
```

写回算法：

1. 解析并校验 Project、章节路径、占位符 ID 和图片资产；
2. 在当前 Project 修改保护范围内读取最新正文和文件版本；
3. 如果目标占位符存在，只替换该 ID 对应的节点，不重建其它正文；
4. 通过 Workspace 跟踪写入保存，并携带读取时的文件版本；
5. 文件版本已经变化时重新读取、重新执行目标替换，最多进行有界重试；
6. 重试耗尽时不强制覆盖，保留成功资产并返回可恢复结果；
7. 成功写入后才把来源插入状态改为 `inserted`。

第一版对当前章节正文保留只读保护，避免未保存编辑覆盖服务端局部写回；但不再把整章的“生成图片”按钮作为同一个锁。每个占位符独立创建 Job，卡片只显示自己的状态，服务端消费者按 FIFO 逐个访问 NovelAI。这样其它图片块可以继续排队，同时仍避免边生成边编辑带来的整篇正文覆盖窗口；若未来要开放正文编辑，需要另行设计增量编辑合并，而不能重新传整篇正文快照。

#### 20.4.3 接口结果

生成端点返回结构化插入结果：

```ts
type SourceInsertResult =
    | { status: "inserted"; content: string; assetId: string }
    | { status: "already_inserted"; content: string; assetId: string }
    | { status: "missing"; content: string; assetId: string };
```

- `inserted`：本次图片引用已经持久化到章节；
- `already_inserted`：章节已经引用该来源的成功资产，不再次调用 NovelAI；
- `missing`：图片已生成或已有成功资产，但最新章节没有目标占位符，资产保留供恢复；
- 前置保存失败、资源非法和版本冲突耗尽使用明确的非 2xx 错误，不伪装成成功；
- 端点在决定是否创建 NovelAI Job 前必须读取最新章节。占位符不存在时先判断同一 `sourceAnchorId` 的资产是否已经在正文中，不能依据浏览器旧内容重复生图。

#### 20.4.4 `sourceInsertStatus` 状态迁移

沿用现有状态，不新增数据库列：

| 场景 | Job 状态 | `sourceInsertStatus` |
| --- | --- | --- |
| 已入队或正在生成，尚未写入正文 | 现有队列状态 | `pending` |
| 图片生成失败，没有可插入资产 | `failed` | 保持 `pending`，失败原因由 Job 状态表达 |
| 图片引用已经持久化 | `succeeded` | `inserted` |
| 图片成功但目标占位符不存在或写回重试耗尽 | `succeeded` | `missing` |
| 非正文来源 | 现有队列状态 | `not_applicable` |

在 `server/text-to-image/queue.service.ts` 增加受类型约束的状态更新方法，不允许 API 直接散写字符串。

### 20.5 前端流程修复

#### 请求前

1. 当前章节进入 `saving_source` 状态；
2. 明确刷新活动编辑器待提交内容；
3. 使用现有乐观写入合同保存正文；
4. 等待保存完成并确认未冲突；
5. 冻结 Project、章节路径、占位符 ID 和保存后的文件版本；
6. 进入 `generating_and_inserting` 状态并发送生成请求。

`saveCurrentFile({ content })` 的合同同时修正：调用方显式提供 `content` 时，不得再用旧活动编辑器内容覆盖它；保存失败必须向调用方抛出或返回可判定失败，不能只记录后继续执行。

#### 请求中

- 当前章节正文只读；
- 被点击的正文占位符按钮显示“排队或生成中”，其它占位符按钮仍可独立入队；
- 每个按钮只绑定自己的 Job 轮询，不用整页全局 busy 状态阻塞其它图片块；
- 页面切换或组件卸载不得把任务误报为成功，重新进入章节时从服务器读取正文和 Job 状态。

#### 请求后

- `inserted`：用服务端返回或重新读取的权威正文刷新编辑器，显示“图片已插入正文”；
- `already_inserted`：刷新正文，显示“图片已在正文中”，不创建新 Job；
- `missing`：保留资产，显示“图片已生成，但原位置不存在，可从已有图片恢复”；
- 请求或写回失败：使用 `resolveApiErrorMessage()` 和 `useNotification()` 显示真实原因；
- 所有分支在 `finally` 中解除当前章节锁。

### 20.6 已有资产恢复计划

新增恢复服务或复用正文写回服务的 `existingAssetId` 输入，使恢复流程只执行“校验资产 → 读取最新正文 → 精确替换 → 受控写入”，不调用 NovelAI。

当前章节恢复按以下步骤执行：

1. dry run：列出 `4` 个剩余占位符及各自成功资产候选；
2. 每个占位符默认选择最近一次成功资产，同时保留其它候选供用户回退；
3. 逐个使用最新章节内容执行目标替换，不能用初始整篇快照批量覆盖；
4. 所有替换通过 Workspace 文件历史写入；
5. 更新实际写入资产对应 Job 的 `sourceInsertStatus`；
6. 不删除 `9` 个未引用资产，不修改图片文件；
7. 验证失败时从文件历史回退正文，不需要重新生图。

恢复验收目标：

| 指标 | 恢复前 | 恢复后 |
| --- | ---: | ---: |
| 当前章节 Markdown 图片引用 | `4` | `8` |
| 当前章节正文生图占位符 | `4` | `0` |
| Project 成功图片资产 | `13` | `13` |
| 新增 NovelAI 请求 | — | `0` |

上述数字只适用于本次已检查的章节。实际施工前必须重新 dry run；如果用户在此期间修改了正文或重新生成了图片，以施工时重新读取的结果为准，并在实施记录中写明偏差。

### 20.7 正文图片宽度合同

正文内工作区图片使用正文内容盒作为宽度边界：

```css
width: 100%;
max-width: 100%;
height: auto;
max-height: none;
object-fit: contain;
```

同时保留块级显示、正文间距和水平居中。结果应满足：

- 横图和竖图都占用正文栏可用宽度；
- 图片不越过正文栏和编辑器内边距；
- 图片保持原始宽高比，不裁切、不强制固定高度；
- 窄屏跟随正文栏缩小；
- 原图宽度低于正文栏时允许按产品要求放大到正文栏宽度，本轮不增加“禁止低分辨率放大”的例外。

### 20.8 施工批次与退出条件

#### Batch W1：失败测试与写回服务

- 增加旧快照、并发乱序、已插入、真实缺失和文件冲突的红灯测试；
- 新增正文图片写回服务；
- 接入 Workspace 修改保护、乐观版本和跟踪写入；
- 增加 `sourceInsertStatus` 状态推进。

退出条件：两个基于同一初始正文的目标插入即使乱序完成，最终章节仍同时保留两张图片；写入失败不会返回 `inserted`。

#### Batch W2：生成 API 与前端状态

- 生成 API 改为以最新章节判断占位符；
- 生成前保存正文，生成后服务端直接写回；
- 保留当前章节正文只读保护和可信通知，但不再用单任务锁禁用其它图片卡片；
- 删除生成结果返回后再次保存整篇正文的路径。

退出条件：保存失败不创建 Job；连续点击不能创建并发正文生图；成功通知出现时重新读取磁盘仍可看到图片引用。

#### Batch W3：已有资产恢复

- 实现免生图恢复入口；
- 先对当前章节 dry run；
- 用户批准实际恢复时再执行 `4` 个目标替换；
- 核对资产数、引用数、占位符数和 Job 插入状态。

退出条件：恢复不产生 NovelAI 请求，正文历史可回退，未选中的历史资产保持不变。

#### Batch W4：宽度样式与总回归

- 修改正文图片样式；
- 增加样式合同测试；
- 运行聚焦测试和 typecheck；
- 更新 Task 142 实施记录与 `PROJECT-STATUS.md` 的真实验证口径。

退出条件：自动化回归通过；未授权时明确记录浏览器、真实 NovelAI 和视觉截图验收未执行。
