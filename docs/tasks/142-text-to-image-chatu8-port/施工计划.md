## 2. 背景与现状

当前代码同时存在两套互相矛盾的设计：

1. 服务端仍实现 `lorebook/character/<groupId>/<characterId>/visual.json`、分组 CRUD、分组扫描和显式 `groupId` 解析。
2. 前端 `loadGroups()` 只保留服务端返回的第一个分组，并显示“角色统一归属于当前项目，不再新建分组”。
3. 前端记录了 `activeCharacterGroupId`，但角色视觉读取、保存、生成和删除没有把 `groupId` 传给 API。
4. `character-visual.get/put/list` 的现有合同测试明确拒绝浏览器提供 `groupId`。
5. 正文扫描在没有显式 `groupId` 时扫描全部分组，没有 Project 级“已启用分组”状态。
6. “当前启用角色”分页实际上按角色名和触发词展示角色，并没有真正的启用开关。
7. `listCharacterGroups()` 依靠目录中是否直接存在 `visual.json` 区分“角色目录”和“分组目录”，角色原始 Markdown 与视觉分组共用命名空间，结构存在天然歧义。
8. 当前 `character-visual.generate.post.ts` 在 LLM 返回后立即写入 `visual.json`，用户没有覆盖、另存或取消的确认机会。
9. NovelAI 页面顶部存在独立“生图方案组”，下方又有“画风串和模型参数设置”，入口和术语重复。

因此本次不继续在现有单集合合同上补条件分支，而是统一角色、分组、视觉文件、启用状态和画风串的数据模型。

## 3. 最终产品合同

### 3.1 领域层级

```text
Project
└── 角色分组（故事阶段 / 启用范围）
    └── 角色（稳定 characterId）
        └── 一份或多份视觉 JSON（设计版本）
            └── 零套或多套服装
```

各层职责不得混用：

- **角色分组**：表达故事阶段、角色集合和正文自动扫描范围，例如“故事前期”“故事后期”。
- **角色**：表达同一个逻辑人物；`characterId` 稳定，允许安全的中文和 Unicode。
- **视觉 JSON**：表达同一角色在某分组内的一套完整视觉设计；同一角色、同一分组可以有多份 JSON。
- **服装**：属于具体视觉 JSON，不是角色或分组级全局数据。
- **当前选中 JSON**：工作台正在查看和编辑的文件。
- **当前生效 JSON**：正文生成实际使用的文件；浏览历史 JSON 不得自动改变生图结果。

### 3.2 分组合同

- 一个 Project 可以存在多个角色分组。
- `default` 是正式分组，不再使用 `null`、`legacy` 或目录猜测表达默认分组。
- 未手动分组的视觉资料进入 `default`。
- 分组具有稳定 `groupId`、用户可编辑名称、说明、排序和启用状态。
- `groupId` 由服务端生成或校验，用户界面不要求作者手写 ASCII 技术 ID。
- 修改分组名称不修改 `groupId`，也不批量移动文件。
- 分组允许零个、一个或多个同时启用。
- 零分组启用表示正文只生成场景/环境内容，界面必须给出明确提示。
- 分组顺序同时是自动解析优先级；顺序靠前者优先。
- 提供“仅启用此组”快捷操作，但底层仍保存启用 ID 集合，不引入另一套单选模式。

### 3.3 角色与视觉资料合同

- 左侧角色视觉树只列出至少存在一份视觉 JSON 的角色。
- 尚未建立视觉资料的 Lorebook 角色不进入该树；首次建立视觉资料从角色原始档案页或明确的“从角色档案创建视觉资料”入口发起。
- 同一个 `characterId` 可以同时存在于多个分组；各分组的外貌、服装和照片互不覆盖。
- 同一个角色、同一个分组可以有多份视觉 JSON。
- 每份 JSON 是完整快照，不保存依赖其它文件的局部补丁。
- 每份 JSON 包含稳定 `visualId`；其它配置引用 `visualId`，不得引用易变文件名。
- 文件名只用于本地管理和展示，不参与角色匹配、触发或身份判断。
- JSON 内的 `characterId`、中文名、英文名和 `triggerWords` 保持正常角色身份。LLM 角色/服装修改不得擅自改变这些身份字段。
- 修改角色身份或触发词必须走独立的身份编辑操作，并同步更新该角色全部视觉 JSON；不得通过重命名 JSON 实现。

### 3.4 当前生效视觉资料

- 每个 `groupId + characterId` 最多有一个当前生效 `visualId`。
- 点击侧边栏 JSON 只切换右侧编辑对象，不自动改变当前生效版本。
- 文件节点或操作菜单提供“设为当前使用”。
- 当前生效 JSON 在侧边栏显示明确徽标。
- 删除当前生效 JSON 前必须选择替代项；最后一份视觉 JSON 不能作为普通“删除版本”处理，只能走“移出分组/清除该分组视觉资料”的高风险操作。

### 3.5 正文扫描与冲突规则

- 正文自动扫描只读取已启用分组。
- 每个分组只读取角色当前生效的视觉 JSON。
- 同一 `characterId` 同时出现在多个已启用分组时，自动扫描使用优先级最高分组的当前生效 JSON，不重复注入同一个逻辑角色。
- “当前启用角色分组”页面必须显示这类覆盖关系和最终生效来源。
- 不同 `characterId` 使用同一触发词时属于真实歧义，必须返回可理解的冲突信息，不按遍历顺序静默选择。
- 提示词调用显式提供 `groupId` 时，使用指定分组的当前生效 JSON；显式调用用于覆盖自动分组优先级。
- 如果未来调用合同支持 `visualId`，显式 `visualId` 优先级高于 `groupId`；本次首版不要求 LLM 输出文件名。

### 3.6 “发送资料”与启用分组

- “已启用分组”决定正文自动扫描的默认角色范围。
- “发送资料”中的角色选择表示即使正文没有命中触发词，也要向 LLM 提供该角色上下文；两者不是同一功能。
- 发送角色默认存 `characterId` 并在运行时跟随当前有效分组/视觉版本。
- 用户需要固定版本时才额外保存 `groupId` 或 `visualId`。
- 切换故事阶段后，普通发送选择不应要求用户重新勾选全部角色。

## 4. 建议的 Project 存储结构

新真相源与 Lorebook 原始 Markdown 分离，避免分组目录和角色目录同名歧义：

```text
<project>/.nbook/text-to-image/
├── character-groups.json
└── character-groups/
    ├── default/
    │   └── <characterId>/
    │       ├── manifest.json
    │       ├── visual.json
    │       └── visual-20260815T143052123Z-a1b2c3d4.json
    └── <groupId>/
        └── <characterId>/
            ├── manifest.json
            └── visual.json
```

原始角色文档继续位于既有 Lorebook 路径，不因视觉资料写入、重命名或删除而移动：

```text
<project>/lorebook/character/<characterId>/index.md
```

如果真实 Project 中存在其它合法的角色 Markdown 布局，迁移器记录原始 `characterPagePath`，不得为了视觉重构擅自移动作者文件。

### 4.1 `character-groups.json`

建议合同：

```json
{
  "schema": "nbook.character-groups/v2",
  "groups": [
    {
      "groupId": "default",
      "name": "默认分组",
      "description": "",
      "enabled": true,
      "sortOrder": 0
    }
  ]
}
```

更新启用状态和排序时必须原子写入整个规范化快照，避免多个开关请求造成丢失更新。

### 4.2 角色分组内 `manifest.json`

建议合同：

```json
{
  "schema": "nbook.character-visual-collection/v1",
  "characterId": "艾璃丝·赛瑞利亚",
  "activeVisualId": "8fb1f3a2-0000-4000-8000-000000000001",
  "visuals": [
    {
      "visualId": "8fb1f3a2-0000-4000-8000-000000000001",
      "fileName": "visual.json",
      "createdAt": "2026-08-15T06:30:00.000Z",
      "updatedAt": "2026-08-15T06:30:00.000Z",
      "source": "manual"
    }
  ]
}
```

`visuals` 顺序用于稳定展示，不作为冲突优先级。当前生效项只由 `activeVisualId` 决定。

### 4.3 视觉 JSON v2

在现有 `nbook.character-visual/v1` 基础上增加：

- `visualId`；
- 可选的创建/修改来源元数据；
- 保留 `characterId`、角色字段、服装数组和照片数组；
- 保持文件自包含，正文编译器不需要拼接另一个视觉文件才能使用。

`characterId` 和 `visualId` 必须分别校验：

- `characterId` 允许安全的 Unicode 单路径段；
- `groupId` 和内部 ID 使用更严格的稳定 ID 规则；
- 文件名使用独立的 Windows 安全文件名校验，不得复用 `characterId` 校验函数代替。

## 5. JSON 文件创建与重命名

### 5.1 自动文件名

首份视觉资料默认使用：

```text
visual.json
```

LLM“另存为新设计”默认使用：

```text
visual-<UTC时间>-<8位随机标识>.json
```

示例：

```text
visual-20260815T143052123Z-a1b2c3d4.json
```

要求：

- 时间不包含 Windows 禁止的冒号；
- 文件名可按创建时间自然排序；
- 使用排他创建；发生 `EEXIST` 时重新生成随机后缀，绝不覆盖；
- 不依赖文件名推导角色名或触发词。

### 5.2 前端重命名

- 用户可以从侧边栏文件菜单执行“重命名”。
- 前端允许用户输入不带扩展名的名称，并自动补 `.json`。
- 后端必须重新校验，前端校验只用于即时反馈。
- 禁止路径分隔符、控制字符、Windows 保留名称、尾随点/空格和内部保留文件名（至少包括 `manifest.json`）。
- 同一 `groupId + characterId` 目录内按 Windows 大小写不敏感规则检查重名。
- 文件名长度必须留出父路径空间，不能把完整 Windows 路径推到不可维护长度。
- 重命名使用同目录原子 rename；目标存在返回 `409`，不自动覆盖。
- 成功后以 `visualId` 更新 `manifest.json` 的 `fileName`；`activeVisualId` 不变。
- 重命名不改变 JSON 内容、照片登记、角色触发词、发送选择或正文引用。

## 6. LLM 角色/服装修改确认流程

### 6.1 不可变原则

LLM 只生成“待确认草稿”，确认前角色视觉文件零持久化。现有生成接口末尾直接调用 `writeCharacterVisual()` 的行为必须移除。

### 6.2 流程

1. 前端发送当前 `groupId + characterId + visualId`、当前视觉快照和修改要求。
2. 服务端解析 LLM 输出并返回完整候选快照、字段差异、警告以及 `baseRevision`。
3. 前端弹出“应用角色设计修改”Dialog，显示分组、当前文件、角色字段差异和服装新增/修改/删除摘要。
4. 用户选择：
   - **覆盖当前设计**：原子覆盖当前 `visualId` 对应文件；
   - **另存为新设计**：创建新 `visualId` 和新 JSON，更新 `manifest.json`，将新文件设为当前生效并在侧边栏选中；
   - **取消**：关闭 Dialog，不调用提交接口，不修改任何角色文件。

### 6.3 草稿与提交边界

- 草稿保留在前端内存；取消时直接丢弃。
- 提交接口重新用 Zod 校验完整视觉快照。
- 对角色/服装修改锁定 `characterId`、中文名、英文名和触发词；候选值与当前身份不一致时，服务端使用当前身份并返回警告，不能让 LLM 偷偷改名。
- `baseRevision` 使用内容哈希或稳定修订号。
- 用户确认时当前文件已经变化，返回 `409`，不得覆盖新内容。
- 覆盖写使用临时文件加原子 rename。
- 另存顺序为：创建新文件、原子更新 manifest；manifest 更新失败时回滚本次新文件，不改变旧 `activeVisualId`。
- 另存保存完整快照，不保存 delta。

## 7. 角色管理 UI

当前 `TextToImageCharacterSection.vue` 已接近 900 行并混合分组、角色、服装、照片和生成逻辑。施工时按职责拆分，不继续把全部状态堆入同一组件。

### 7.1 左侧视觉资料树

信息结构固定为：

```text
分组
└── 角色目录
    └── JSON 文件
```

具体行为：

- 只展示至少有一份视觉 JSON 的角色。
- `default` 与其它分组使用相同节点，不显示“旧版/未分组”双重语义。
- 分组和角色目录分别支持折叠/展开。
- 展开状态按 Project 保存；不写全局配置。
- JSON 文件节点显示文件名、当前选中态、当前生效态、错误态和未保存态。
- 点击文件加载精确 `groupId + characterId + visualId`。
- 文件菜单至少包含：设为当前使用、重命名、复制、删除。
- 角色目录菜单至少包含：复制到其它分组、移出当前分组。
- 分组菜单至少包含：新建/编辑、复制分组、排序、删除。
- JSON 无法解析时仍显示错误节点，允许用户查看错误和定位本地文件；不能因为解析失败从树中消失。
- 切换文件、角色、分组或关闭工作台前处理未保存修改：保存、放弃或取消切换。

### 7.2 右侧分页

继续保留：

- 角色详情；
- 服装详情；
- 角色照片。

将“当前启用角色”改为“当前启用角色分组”。该分页只管理 Project 级启用集合和生效预览，不再按“是否有触发词”伪装成启用状态。

“当前启用角色分组”至少展示：

- 每个分组的复选框、名称、说明和角色数量；
- “仅启用此组”；
- 拖拽排序或明确的上移/下移操作；
- 当前最终生效角色数量；
- 同一角色被更高优先级分组覆盖的提示；
- 无触发词、无当前生效 JSON、视觉文件损坏等不完整状态；
- 零分组启用时“将只生成场景内容”的说明。

### 7.3 新视觉资料入口

- 不在角色详情页增加一个与侧边栏重复的“视觉版本切换器”。
- 同一角色不同视觉资料只通过点击侧边栏 JSON 切换。
- 新视觉资料主要来自 LLM 确认后的“另存为新设计”、复制 JSON、复制分组或从角色档案首次创建。
- 如果保留手动空白新建，只能放在侧边栏角色目录菜单，并且创建后立即成为可见 JSON 节点；不得在详情页制造第二套导航状态。

### 7.4 推荐组件边界

可按现有代码实际情况调整文件名，但职责必须分离：

- `CharacterGroupActivationPanel.vue`：启用集合、排序和生效预览；
- `CharacterVisualDetail.vue`：角色视觉字段；
- `CharacterOutfitEditor.vue`：服装列表与编辑；
- `CharacterPhotoPanel.vue`：照片 prompt、生成和图库；
- `CharacterVisualCommitDialog.vue`：覆盖/另存/取消；

复用项目已有 `Dialog`、`useNotification()` 和 `resolveApiErrorMessage()`；颜色只使用已登记主题变量。

## 8. 后端服务与 API 改造

### 8.1 服务拆分

当前 `character-visual.service.ts` 同时承担路径、分组、角色、冲突、文件和照片删除。重构为清晰领域边界：

- `CharacterGroupService`：分组 manifest、CRUD、启用集合和排序；
- `CharacterVisualLibraryService`：树索引、角色分组成员关系、manifest；
- `CharacterVisualService`：精确视觉文件读写、创建、复制、重命名、删除；
- `CharacterVisualResolver`：按启用分组、优先级和显式调用解析生效视觉；
- `CharacterVisualMigrationService`：旧结构 dry run、迁移、校验和一次性切换。

后端高领域逻辑使用 class，保持完整类型，不使用 `any` 或绕过 schema。

### 8.2 DTO

共享 DTO 至少新增或调整：

- `CharacterGroupDto`：`groupId/name/description/enabled/sortOrder/characterCount`；
- `CharacterVisualTreeDto`：分组、角色和视觉文件节点；
- `CharacterVisualRef`：`groupId/characterId/visualId`；
- `CharacterVisualManifest`；
- `CharacterVisualModifyDraftDto`：候选快照、diff、warnings、baseRevision；
- `CharacterVisualCommitRequest`：`action = overwrite | create_new`、ref、draft、baseRevision；
- 发送资料选择支持“跟随当前有效版本”和“固定 group/visual”两种模式。

### 8.3 API 行为

优先改造现有路由，必要时新增职责单一的 commit/rename/activation 路由。最终必须满足：

- 分组列表返回全部分组，不截断；
- 分组启用列表与排序通过单次原子请求更新；
- 视觉 get/put/delete 使用精确 `CharacterVisualRef`，不再依靠“项目内 characterId 必须唯一”猜测位置；
- list 返回视觉树，不把没有视觉 JSON 的 Markdown 角色混入；
- rename 使用 `visualId + newFileName`，服务端从 manifest 定位原文件；
- LLM generate/modify 返回草稿，不写盘；
- commit 执行覆盖或另存；
- 照片生成和登记携带完整视觉 ref，写回正确 JSON；
- 删除视觉资料只处理该 JSON 登记的照片，不删除角色 Markdown；
- 删除分组前返回影响摘要，不能沿用当前无保护的递归删除行为。

所有浏览器请求继续经过 Project Root 解析、认证、路径 containment 和 Zod 校验。

## 9. 正文生成、提示词编译与照片链路

需要审查并修改所有按 `characterId` 或可选 `groupId` 读取视觉资料的调用方：

- `body-character-scanner.ts`；
- `body-prompt-compiler.ts`；
- `body-prompts.post.ts`；
- `project-send-data.service.ts`；
- `character-photo.service.ts`；
- `character-photo.generate.post.ts`；
- 角色视觉生成、删除、列表和照片相关 API；

正文链路必须通过 `CharacterVisualResolver` 获得有效视觉，不允许各调用方自行遍历目录并形成不同冲突规则。

照片资产需要记录 `groupId + characterId + visualId`，避免同一角色不同视觉 JSON 的照片写错文件。文件重命名后照片登记仍通过 `visualId` 有效。

## 10. 旧数据迁移

### 10.1 输入

迁移器至少识别：

- `lorebook/character/<characterId>/visual.json`；
- `lorebook/character/<groupId>/<characterId>/visual.json`；
- `.group.json` 分组元数据；
- 已有 `photos[]` 和 `assets/tti/` 受控照片；
- `.nbook/text-to-image-send-data.json` 中的旧 `characterIds`、`characterSelections` 和 `outfitSelections`。

### 10.2 迁移规则

1. 先 dry run，生成计数、目标路径和冲突报告，不写新真相源。
2. 创建 `default` 分组。
3. 旧单层视觉资料迁入 `default`。
4. 旧分组视觉资料迁入同名稳定分组。
5. 每个旧视觉文件分配稳定 `visualId`，第一份可保留 `visual.json` 文件名。
6. 同一角色不同分组的外貌、服装和照片全部保留，不合并视觉内容。
7. 中文和 Unicode `characterId` 原样保留，只做安全单路径段校验。
8. 同一角色不同旧文件的身份字段不一致时进入迁移冲突报告，不静默挑选。
9. 旧 `groupId = null/legacy` 发送选择规范化为 `default` 或“跟随当前有效版本”。
10. 校验新旧角色数、视觉文件数、服装数、照片登记数和资产存在性。
11. 新结构完整校验成功后才切换真相源。
12. 不长期保留双写或两套运行时读取；旧目录只作为一次性迁移输入。是否删除或归档旧文件必须是明确、可恢复的迁移收尾步骤。

迁移必须幂等：重复执行不得创建重复分组、重复视觉文件或重复照片登记。
