# 正文生图独立服装调用解析修复施工计划

- 状态：已落地（2026-08-17）
- 制订日期：2026-08-17
- 关联任务：Task 142「正文文生图 chatu8 合同移植」的独立修复项
- 本轮范围：已按本计划落地合同与代码；未修改角色视觉文件或章节占位符

## 一、结论

当前报错不是 `from side` 解析失败，也不是 JSON 格式问题，而是独立服装调用被错误识别成了角色调用。

章节中已经存在以下合法的 chatu8 风格组合：

```text
${"name":"Saki Terashima","angle":"from side","upperBody":"sfw","lowerBody":"sfw"}$,
${"name":"office lady smart casual outfit","upperBody":"visible","lowerBody":"visible"}$
```

第一段角色调用已经能正确编译；第二段没有 `angle`，并用 `visible` 描述服装可见性，应当解析为独立服装调用。但当前通用解码器把所有 `name` 都写入角色字段，编译器随后先查找名为 `office lady smart casual outfit` 的角色，于是抛出：

```text
未找到角色“office lady smart casual outfit”的 visual.json
```

该服装并未缺失。它存在于寺島佐紀当前视觉文件的 outfits 中，英文名就是 `office lady smart casual outfit`。当前章节共有 3 个占位符包含同一种调用，修复应让这些既有占位符在不重新抽取、不重写章节数据的情况下恢复生成。

## 二、修复目标

1. 正确支持 chatu8 的无 `kind` 独立服装调用：

   ```text
   ${"name":"office lady smart casual outfit","upperBody":"visible","lowerBody":"visible"}$
   ```

2. 推荐新生成内容显式携带 `kind: "character" | "outfit"`，同时继续兼容已经落盘的无 `kind` 调用。
3. 独立服装未写 `angle` 时，继承同一提示词中前一个角色的朝向；本例 `from side` 使用正面服装素材，不错误切换到背面素材。
4. 保留当前已支持的角色调用、角色内联 `outfit`、显式 `outfit` 字段、临时视觉和缺失结束 `$` 修复能力。
5. 角色、服装不存在或名称歧义时返回可操作的业务错误，并且不创建生图队列任务。
6. 编译完成后不得残留 `${...}$` 调用标记。

## 三、合同设计

### 3.1 分离语法解码与语义解析

`body-prompt-call.codec.ts` 只负责：

- 扫描 `${...}$`；
- 修复允许修复的缺失结束 `$`；
- 验证 JSON 结构；
- 保存调用中实际出现的 `kind`、`name`、`angle`、上下半身状态和可选定位字段。

它不能在缺少项目视觉上下文时断言所有 `name` 都是角色名。角色或服装的最终判定由编译阶段完成，因为只有编译器能够访问当前项目启用的角色视觉、服装列表和前序调用上下文。

建议将语法层产物命名为 `BodyPromptCallDraft`，语义层产物收敛为判别联合：

```ts
type ResolvedBodyPromptCall =
    | ResolvedCharacterCall
    | ResolvedOutfitCall
```

是否新增 `body-prompt-call.resolver.ts` 由施工时按代码体量决定；如果逻辑仍能清楚地留在编译器内，不为单点逻辑额外造抽象。

### 3.2 无 `kind` 调用的判定顺序

按以下优先级解析，前一条命中后不继续猜测：

1. 显式 `kind: "character"` 或 `kind: "outfit"`：以 `kind` 为准，再按对应合同校验字段。
2. 内联对象：内联 character 是角色；只有内联 outfit 且没有角色的是独立服装；角色调用中的 `outfit: string` 继续表示该角色携带的服装。
3. 存在 `angle`：判为角色调用。
4. 没有 `kind`、没有 `angle`、只有 `name`：在当前有效视觉范围内分别精确匹配角色名和服装名。
   - 只命中角色：判为角色，保留已有无角度角色调用兼容性；
   - 只命中服装：判为独立服装；
   - 两边都命中：报名称歧义，要求补 `kind`；
   - 两边都未命中：报引用不存在，不把它伪装成 JSON 错误。

`visible` / `hidden` 是服装状态的强提示，但不能覆盖真实的名称歧义。不能采用“没有 `angle` 就一律是服装”的简化规则，否则会破坏已有的无角度角色调用。

### 3.3 独立服装的作用域与前序角色上下文

编译器按提示词中的出现顺序处理调用，并维护当前提示词内的最近角色上下文：

```ts
type LastCharacterContext = {
    visualRef: CharacterVisualRef
    facing: "front" | "back"
    angleText?: string
}
```

- 每次成功解析角色后更新 `lastCharacterContext`。
- 后续无 `angle` 的独立服装优先在该角色的同一份有效 visual 中按中英文名精确匹配，并继承该角色的 `facing`。
- `from side`、`from front` 等非背面角度均使用正面服装字段；`from behind` 使用背面服装字段。
- 独立服装只输出服装提示词，不重复输出角色已经提供的视角标签。
- 如果调用前没有角色，则在当前项目有效视觉中查找唯一服装候选；唯一命中时按正面素材编译并记录结构化 warning，多候选时拒绝猜测。
- 如果合同已有 `characterId`、`groupId`、`visualId` 等定位字段，显式定位优先于前序上下文，用于消除同名服装歧义。
- 搜索范围沿用角色解析的“当前有效视觉”规则，不静默搜索已禁用、已废弃或非当前版本的 visual。

上下文只在单次 `compileBodyPrompt` 中有效，不能跨占位符、跨请求或跨用户共享。

### 3.4 身体状态在类型确定后校验

- 角色调用：`upperBody` / `lowerBody` 只接受 `sfw`、`nsfw`、`hidden`。
- 独立服装调用：`upperBody` / `lowerBody` 只接受 `visible`、`hidden`。
- 角色调用中的 `outfit: string` 继续沿用现有角色身体状态和隐藏逻辑，不改成独立服装状态。
- 状态与已判定类型冲突时直接报合同错误，不做静默转换。

### 3.5 错误合同

引入或补齐可识别的编译错误分类，建议至少包含：

| 错误码 | HTTP | 用户可感知结果 |
| --- | ---: | --- |
| `call_invalid` | 422 | 调用 JSON 或字段组合不符合合同，指出具体字段 |
| `reference_missing` | 409 | 指明缺失的是角色还是独立服装 |
| `reference_ambiguous` | 409 | 指明同名候选冲突以及如何消歧 |

建议文案：

- `未找到独立服装“office lady smart casual outfit”`
- `调用名“X”同时命中角色与服装，请增加 kind`
- `独立服装“X”存在多个候选，请指定角色/视觉，或将调用放在对应角色调用之后`

上述错误在进入图片生成队列前返回。前端沿用统一 API 错误展示，不向用户暴露堆栈、磁盘路径或内部模块名。

### 3.6 illustration.director 输出合同

`illustration.director` 继续负责把 LLM 回复修复、规范化成可供编译器消费的调用。系统提示词和示例改为优先输出显式类型：

```text
${"kind":"character","name":"Saki Terashima","angle":"from side","upperBody":"sfw","lowerBody":"sfw"}$
${"kind":"outfit","name":"office lady smart casual outfit","upperBody":"visible","lowerBody":"visible"}$
```

无 `kind` 格式仍是输入兼容合同，不能因为导演提示升级而要求用户重新抽取旧章节。导演层只修语法和可确定的字段结构，不查询 visual、也不凭名称猜角色或服装；名称解析仍由编译器统一完成。

## 五、测试矩阵

### 5.1 解码与导演测试

- 显式 `kind: "character"`、`kind: "outfit"` 均能解析。
- 无 `kind` 调用保留未决信息，不在 codec 中误判。
- 非法 `kind`、类型与状态不一致时给出稳定错误。
- 独立服装调用缺失结束 `$` 时可以被导演按现有规则修复。
- 完整合法调用不被导演改坏。

### 5.2 编译器聚焦测试

至少覆盖：

1. `from side` 角色 + 无角度 `visible` 独立服装：角色使用正面 DNA，服装使用正面 upper/lower，保留 `from side`，结果无调用标记。
2. `from behind` 角色 + 无角度独立服装：服装使用 upperBack/lowerBack。
3. 无前序角色、项目内唯一服装：使用正面素材并产生结构化 warning。
4. 无角度角色名：仍按角色解析，防止兼容性回归。
5. 同一名称同时命中角色与服装：返回 `reference_ambiguous`。
6. 多份有效 visual 中存在同名服装且无上下文：返回 `reference_ambiguous`。
7. 显式定位字段可以消除同名服装歧义。
8. 角色携带 `outfit: string` 的现有格式保持不变。
9. 内联/临时角色视觉和服装保持可用。
10. 角色使用 `visible` 或独立服装使用 `sfw` 时返回 `call_invalid`。
11. 角色或服装不存在时错误类型和文案正确。

本次报错应固化为最小化 fixture，不把用户章节全文复制进测试：

```text
${"name":"Saki Terashima","angle":"from side","upperBody":"sfw","lowerBody":"sfw"}$,
${"name":"office lady smart casual outfit","upperBody":"visible","lowerBody":"visible"}$
```
