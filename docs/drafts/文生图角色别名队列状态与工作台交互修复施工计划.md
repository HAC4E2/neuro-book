# 文生图角色别名、图片块状态与工作台交互修复施工计划

> 状态：设计完成，尚未施工。
>
> 日期：2026-08-19。
>
> 归属：[Task 142：文生图 chatu8 移植](../tasks/142-text-to-image-chatu8-port/README.md)。

## 1. 本轮目标

本轮集中修复五组互相关联的文生图体验问题：

1. 角色英文名称包含 `|` 分隔的别名时，正文图片角色调用无法按其中一个名称找到视觉资料。
2. 图片块已排队或正在生成时，离开当前页面再返回，卡片退回“待生成”，丢失真实任务状态提示。
3. 角色服装页面存在角色选择不直观、LLM 只能覆盖既有服装、修改输入与提交入口分离的问题。
4. 画风串的新建入口不明显，应用、保存、重命名和底部保存等入口重叠，保存语义不清。
5. 角色只有一份视觉 JSON，或当前选中的是生效版本时，用户无法删除该视觉资料。

本计划只定义合同、交互、实施顺序和验收标准，不修改业务代码、Project 数据、数据库或用户视觉资料。

## 2. 非目标

- 不调整 NovelAI 最终 Prompt Bundle、模型参数含义、请求间隔或 FIFO 消费顺序。
- 不重新设计角色视觉 JSON 的 15+6 字段结构，不给服装增加持久化 ID。
- 不修改角色原始 Markdown、小说正文、历史图片资产或既有成功任务。
- 不把浏览器本地状态作为任务真相源，也不引入 `localStorage` 双真相。
- 不把“删除视觉 JSON”扩大为删除角色原始档案、历史任务或已生成正文图片。
- 不在自动化测试中调用真实 LLM 或 NovelAI。

## 4. 总体设计决定

### D1：任务状态以 Project Job 为真相，卡片只做投影

“排队中”“生成中”“失败”和“已完成”不能由 NodeView 的生命周期决定。页面进入、章节切换、编辑器重建和整页刷新后，都必须用 `projectRoot + sourcePath + placeholderId` 从现有 Project Job 恢复状态。

### D2：角色主名称和别名均可用于显式角色调用

`cnName`、`enName` 与 `triggerWords` 都进入显式角色引用词集合。其中 `enName` 兼容 `|` 分隔：第一项是主要英文名，其余项是英文别名；每一项独立规范化、去空白和去重。现有包含 `|` 的视觉 JSON 无需迁移即可生效。

正文自动扫描仍保持“显式触发词优先、触发词为空时回退中英文名”的既有边界，避免一次修复意外扩大短英文别名的误命中范围。显式 `${...}$` 角色调用则始终可以使用任一名称或别名。

### D3：保留原有修改链路，纯服装回复进入覆盖／增加确认

不增加新的“新增服装”入口、请求类型或 API。用户仍通过现有“角色服装修改”输入要求并生成预览，服务端继续使用现有 `character-visual.modify-preview` 与 `character-visual.modify-commit`。

解析回复后，如果没有任何 `<人物>` 字段、但存在至少一个完整 `<服装>` 块，则把结果标记为 `outfit_only`。此时不再按 `selectedOutfitIndex` 自动合并；每套返回服装先成为候选，由用户选择：

- 覆盖当前服装；
- 作为新服装增加；
- 不应用。

同一批回复最多一套候选可以覆盖当前服装，其余候选可以增加或忽略。没有当前服装时禁用“覆盖当前服装”，只允许增加或忽略。LLM 回复顺序只决定候选显示顺序，不决定写入动作。

### D4：画风串只有一个持久化保存入口

画风串编辑使用独立草稿。选择画风串只负责加载；新建按钮进入空白草稿；名称、分组和全部模型参数由同一个主按钮保存。重命名就是修改名称后保存，不再保留单独“重命名”按钮；“应用”按钮和页面底部重复保存按钮删除。

连接设置和 Provider 全局提示词替换规则不是画风串内容，继续保留各自明确命名的保存入口，不伪装成画风串保存。

### D5：允许删除生效版本和最后一份视觉资料，但必须先预检影响

删除行为以“当前视觉 JSON”为单位：

- 删除非生效版本：直接移除该版本。
- 删除生效版本且仍有其它版本：在同一事务内先选定回退版本，再删除当前版本。
- 删除角色在当前分组中的最后一份版本：移除该角色的视觉目录和 manifest；该角色只是不再出现在这个视觉分组中。

删除视觉 JSON 不删除角色原始档案、历史任务、正文图片或照片文件。照片清理由独立功能处理，避免删除一份 JSON 时误删仍被其它版本引用的资产。

## 5. 分项施工设计

### Phase 1：统一角色名称与别名合同

#### 5.1 领域解析

在 `character-trigger-words.ts` 增加共享名称解析函数，统一执行：

1. 仅对角色名称字段按半角 `|` 分段。
2. 每段 `trim()`，拒绝或过滤空段，并使用 NFKC + 大小写折叠去重。
3. 保留第一段作为 UI 和 LLM 摘要中的主要英文名。
4. 将其余分段作为明确的英文别名输出，不再把 `Primary Name | Alias` 整串当作单个名称。

`buildCharacterReferenceTerms()` 改为合并：

- 全部规范化触发词；
- 中文名称条目；
- 英文名称及英文别名条目。

`buildEffectiveCharacterTriggers()` 保持当前优先级：有显式触发词时只使用触发词；没有时使用拆分后的中英文名称集合。

#### 5.2 LLM 摘要与编辑提示

正文角色摘要改为清楚表达：

```text
英文主名称：Primary Name
英文别名：Alias A | Alias B
```

避免新模型从未解释的整串英文名中自行截取。角色管理界面在英文名字段下显示“可使用 `|` 添加英文别名；第一项为主要英文名”，并展示规范化预览。

#### 5.3 错误信息

角色资料确实存在但名称未匹配时，错误不再只说“未找到 visual.json”。生成阶段应区分：

- 角色视觉资料不存在；
- 启用视觉资料中没有名称或别名匹配项；
- 同一名称命中多个角色，需消除歧义。

错误中只包含安全角色名称，不输出完整 Prompt、正文或视觉字段。

#### 5.4 回归测试

- `enName = "Primary Name | Alias"` 时，两项都能用于显式角色调用。
- 前后空格、重复别名、大小写与 NFKC 等价形式正确去重。
- `triggerWords` 非空时，显式英文别名仍可解析角色。
- `triggerWords` 非空时，正文自动扫描不因新增英文别名而扩大范围。
- LLM 角色摘要明确区分主要名称和别名。
- 两个角色共享别名时返回歧义，不静默选择第一个。

### Phase 2：恢复图片块的持久化队列状态

#### 5.5 服务端状态投影

新增章节级批量状态接口，输入 `projectRoot + path`，返回该章节所有正文图片 Job 按 `sourceAnchorId` 聚合后的状态。聚合规则：

1. 同一占位符有 `running` 时以 `running` 为当前状态。
2. 否则有 `queued` 时选择最早排队且仍有效的 Job，并返回队列位置。
3. 否则返回最近终态，用于显示失败原因或等待正文替换同步。
4. 已经写回并从正文消失的占位符无需继续渲染卡片；资产和历史仍按原合同保留。

接口只返回卡片所需的安全字段：`placeholderId`、`jobId`、`status`、`queuePosition`、`errorMessage`、`sourceInsertStatus`。不返回 Provider 凭据、最终 Prompt 或正文。

#### 5.6 前端状态注册表

在宿主层建立按以下稳定键索引的运行时投影：

```text
projectRoot + path + placeholderId
```

该注册表不是新真相源，只缓存服务端投影：

- 打开章节或编辑器重建时，批量获取一次当前状态。
- 对 `queued/running` Job 恢复轮询；轮询终止后刷新权威章节版本。
- 页面离开时停止该页面的定时器，但不取消 Job。
- 返回页面后重新批量恢复，而不是依赖离开前的 Promise。
- 多个图片块各自投影状态，不因其中一个生成而禁用其它块。

`TextToImagePrompt` NodeView 改为从宿主订阅状态，不再保存决定 UI 的局部 `generating` 布尔值。局部值只允许用于阻止同一事件循环中的重复点击，不能覆盖服务端状态。

#### 5.7 卡片状态

- `idle`：待生成，按钮“生成图片”。
- `queued`：排队中；有队列位置时显示“前面还有 N 个任务”。
- `running`：正在生成，按钮禁用。
- `failed`：显示可理解的失败摘要，按钮“重新生成”。
- `canceled`：显示已取消，按钮“重新生成”。
- `succeeded + pending/missing`：按既有恢复合同显示“正在写回”或“可恢复已有图片”。

#### 5.8 竞态处理

- 用户刚返回页面时 Job 已成功且占位符已被图片替换：采用服务端章节版本，不短暂重新显示“待生成”。
- 同一占位符重复点击：生成接口继续复用活动 Job，前端合并到同一个 `jobId`。
- 旧页面的迟到轮询结果必须用页面/章节请求令牌丢弃，不能污染新章节卡片。
- 批量恢复接口替代每张卡片挂载时各发一个请求，避免章节图片块越多请求越多。

#### 5.9 回归测试

- 排队后切换工作台页面再返回，卡片仍显示排队状态。
- 生成中切换章节再返回，恢复同一 `jobId` 并继续轮询。
- 整页刷新后从 Project Job 恢复状态。
- 两个图片块同时排队时，各自状态和队列位置正确。
- 失败后返回页面仍显示失败，并允许重新生成。
- 旧章节迟到响应不会覆盖新章节。
- Job 完成并写回后，卡片被图片替换且编辑器接纳权威文件 revision。

### Phase 3：重做角色与服装选择、修改和新增流程

#### 5.10 角色树选择

角色树拆分两个点击目标：

- 点击角色整行：立即选择该角色的当前生效视觉版本；没有生效标记时选择列表第一份有效版本，同时展开版本列表。
- 点击独立的折叠箭头：只展开或收起，不改变当前选择。
- 点击具体 JSON：选择该历史版本。

选中角色后，右侧标题必须立即更新为该角色；服装页重置到该角色第一套服装，若无服装则显示空状态。异步读取使用选择令牌，先发后到的旧角色请求不能覆盖新选择。

#### 5.11 服装编辑布局

服装页采用“列表 + 当前服装编辑器 + 就地 LLM 操作区”：

- 列表头保留明显的“+ 新增空白服装”。
- 当前服装字段直接编辑到草稿；移除额外的“应用服装修改”中间按钮，页面顶部“保存”是手工编辑的唯一提交入口。
- 当前服装编辑器下方紧邻现有“角色服装修改”的输入框和“生成修改预览”主按钮；不增加第二个“生成新服装”入口。
- LLM 只返回服装时，覆盖或增加的选择出现在回复预览中，不要求用户发请求前先判断操作类型。
- 角色详情中的 LLM 修改输入与“生成角色修改预览”按钮放在同一个卡片内，移除页面顶部远离输入框的按钮。
- 角色、服装和照片分别保存自己的临时要求文本，不再共享一个 `userRequirement`。

窄屏下按“服装列表 → 字段 → LLM 修改区”纵向排列；桌面端保持列表与编辑区双栏。

#### 5.12 实际多服装回复案例对合同的修正

已使用一次真实“生成角色的服装”回复通过当前解析与合并入口复现。该回复包含一段标签外自然语言和连续 `3` 个完整 `<服装>` 块，结果如下：

- 解析器可以识别全部 `3` 套服装；标签外自然语言被安全忽略，不是故障来源。
- 当前页面只要默认选中了服装索引 `0`，第 `1` 个返回块就覆盖索引 `0`，第 `2`、`3` 个块因名称未命中而追加。若原来只有 `1` 套服装，最终仍是 `3` 套，但原服装已经丢失。
- 只有把 `selectedOutfitIndex` 设为 `null`，`3` 个返回块才会全部追加，原服装保持不变，最终成为 `4` 套。

因此不能把多服装回复视为格式错误，也不能只取第一套。正确合同是“沿用原修改请求 → 检测纯服装回复 → 解析完整候选 → 用户选择覆盖或增加 → 原子提交”。公开记录只保留结构和数量，不记录用户 Project、角色名或具体服装内容。

#### 5.13 纯服装回复检测合同

保持现有修改预览请求体，不增加 `operation` 字段。服务端在 `parseCharacterVisualDraftPresence()` 之后按解析结果分流：

```ts
const outfitOnly = parsed.characterFields.size === 0
    && parsed.draft.outfits.length > 0;
```

`outfitOnly` 为真时，现有修改预览接口返回 `mode: "outfit_only"` 和按回复顺序排列的候选，而不是提前生成已经合并的服装数组。每个候选至少包含临时 ID、源顺序、完整服装字段和逐块诊断；`selectedOutfitIndex` 只用于告诉预览“当前服装是谁”，不能再触发自动覆盖。

这属于现有接口响应的向前扩展，不新增端点，也不新增用户操作入口。普通人物修改回复继续使用既有角色字段差异预览；只有纯服装回复进入覆盖／增加选择。

解析改为逐个 `<服装>` 块产生候选和诊断。某个块缺少必要名称或关键字段时只跳过该块，其它完整候选继续进入预览；整次既没有完整人物补丁、也没有完整服装候选时才报告阻塞且不写入。

#### 5.14 草稿确认

确认对话框按回复形态显示结果，而不是只显示“服装数量变化”：

- 修改角色：逐字段前后对照。
- 纯服装且只有一套候选：直接提供“覆盖当前服装”“增加为新服装”“不应用”三个互斥选择。
- 纯服装且有多套候选：按回复顺序列出全部候选，每项提供“覆盖当前服装”“增加”“不应用”；同一批最多一项可选覆盖，选择新的覆盖项时自动解除旧覆盖项。
- 没有当前服装：所有候选的“覆盖当前服装”不可选，并解释“当前角色还没有可覆盖的服装”。

候选初始状态为“未选择”，避免用户直接确认时误覆盖或误增加。预览顶部实时给出汇总，例如“覆盖 1 套，增加 2 套，忽略 0 套，尚未选择 0 套”；仍有未选择候选时禁用提交。候选使用解析时分配的临时 ID 或源顺序作为键，不能以服装名称或数组索引充当唯一 UI key。

API 返回的 `warnings`、`changedFields` 和逐块诊断必须进入前端待确认草稿并在对应候选旁展示。当前前端没有接收这两个字段，导致服务端已经给出的“将创建新服装”等警告被静默丢弃；施工时必须补齐 DTO，而不是只在控制台保留信息。

用户完成候选决策后，前端以读取时的视觉 JSON 为基线机械组成最终草稿：覆盖只改写当前服装索引，增加只追加到数组末尾，不应用则完全忽略。之后继续调用现有 `character-visual.modify-commit`；主操作仍为“保存到当前视觉 JSON”，次级操作仍为“另存为新视觉版本”。

#### 5.15 回归测试

- 点击第二个角色整行后，右侧角色和服装都切换到第二个角色。
- 快速连续选择两个角色，只显示最后一次选择结果。
- 切换角色时有未保存修改，继续复用保存/放弃/取消保护。
- 手工修改服装无需再点击“应用服装修改”，顶部保存能够持久化当前草稿。
- 原有修改接口收到只有 `<服装>` 的单候选回复时进入 `outfit_only`，不在预览前覆盖当前服装。
- 单候选分别选择“覆盖当前服装”和“增加为新服装”，得到正确且互斥的结果。
- 收到 `3` 个完整 `<服装>` 块时展示 `3` 个未选择候选；选择全部增加后，原有服装逐字保持，数量从 `1` 变为 `4`。
- 多候选中最多一项可以覆盖当前服装，其余可以增加或忽略；回复顺序不产生隐式写入。
- 当前角色没有服装时，覆盖选项禁用，候选仍可选择增加。
- 标签外自然语言不影响完整 `<服装>` 块解析。
- 一个返回块损坏时只跳过该候选，其它完整服装仍可确认；全部不可用时无副作用阻塞。
- 服务端 `warnings`、`changedFields` 和逐块诊断在预览中可见，不被前端响应类型丢弃。
- 新增服装重名时阻止提交，不覆盖旧服装。
- 修改输入框与触发按钮在同一操作区域，角色/服装/照片要求互不串值。

### Phase 4：精简画风串管理

#### 5.16 顶部管理条

“画风串和模型参数配置”顶部改为：

1. 分组筛选。
2. 画风串选择器。
3. 醒目的“+ 新建画风串”按钮。
4. 当前名称输入框。
5. 更多菜单：删除、移动到分组；只有这些低频动作进入菜单。

新建分组移入“管理分组”对话框。用户只输入分组显示名称，稳定 ID 由程序生成，不再暴露“新分组 ID”输入框。

#### 5.17 草稿和保存

选择画风串时把已保存快照复制到编辑草稿。编辑模型、固定提示词、Vibe 或参考图只标记草稿 dirty，不立即改写保存对象。

页面提供一个随滚动保持可见的主按钮：

- 新建态：“创建画风串”。
- 已有态：“保存画风串”。

该按钮一次保存名称、分组、模型参数、固定提示词和参考图，并将所选画风串设为当前使用。删除以下重复入口：

- “应用”；
- 独立“重命名”；
- 原顶部“保存画风串”；
- 原配置区底部“保存画风串和模型参数”。

切换画风串、Provider、工作台页面或关闭工作台时，如果草稿 dirty，统一使用保存/放弃/取消保护。选择画风串本身不应把尚未保存的编辑内容写进旧画风串。

#### 5.18 其它保存入口的边界

- “保存连接设置”：只保存站点和请求间隔。
- “保存 API Key”：只保存凭据。
- “保存全局提示词替换规则”：只保存 Provider 全局规则。
- “保存画风串”：只保存当前画风串快照及当前选择。

四类按钮按数据归属命名，不能再全部落成没有边界的 `saveStyle()`。

#### 5.19 回归测试

- 顶部始终可见“+ 新建画风串”。
- 页面中只有一个“保存画风串”或“创建画风串”主入口。
- 选择已有画风串不会把未保存表单反写到上一项。
- 新建、改名、移动分组都通过同一个保存入口完成。
- 切换画风串时 dirty guard 的保存、放弃、取消三条路径正确。
- 删除当前画风串后选择确定的回退项；没有剩余画风串时进入明确空状态。
- 新建分组只要求显示名称，内部 ID 稳定且不因改名变化。
- 全局规则和连接设置不会被误存进画风串，也不会随删除画风串消失。

### Phase 5：允许安全删除视觉 JSON

#### 5.20 删除影响预检

删除前新增只读预检，返回：

- 当前文件是否生效；
- 删除后是否还有其它版本；
- 服务端建议的回退版本；
- 删除后该角色是否从当前分组消失；
- 需要更新或移除的固定发送引用数量；
- 当前 JSON 登记的照片数量；
- 预检 revision。

前端使用正式 `Dialog` 展示影响，不再使用 `window.confirm()`。

#### 5.21 原子删除

提交时携带预检 revision 和当前文件 `updatedAt`。服务端在 Project 写锁内重新校验，并一次性完成：

1. 若删除当前生效版本且有其它版本，设置确定的回退版本。
2. 更新指向被删 `visualId` 的固定发送引用；有回退则改指向回退版本，没有则移除该固定项。
3. 从 manifest 移除版本并删除 JSON 文件。
4. 若为最后一份版本，删除空 manifest 和空角色视觉目录。
5. 返回下一选择位置或空状态，供前端直接刷新。

预检后数据变化返回 `409`，要求重新查看影响；不得基于过期预览继续删除。

#### 5.22 照片和历史边界

本轮删除只删除视觉 JSON 及其 manifest 登记，不主动删除图片文件。原因是同一路径可能仍被其它视觉版本、历史任务或用户内容引用。未来需要清理时，应另做“未引用角色照片清理”并执行全 Project 引用检查。

#### 5.23 前端行为

- 只要已选择视觉 JSON 且没有未保存修改，“删除 JSON”就可用；不再因 `active` 或版本数量为 `1` 禁用。
- 对生效版本，确认对话框显示将切换到哪一个版本。
- 对最后一份版本，明确显示“删除后该角色将从当前视觉分组中消失；角色原始档案不会删除”。
- 成功后使用服务端返回的下一选择；若无下一项，显示空状态而不是残留旧表单。

#### 5.24 回归测试

- 删除非生效版本。
- 删除生效版本并原子切换到确定的回退版本。
- 删除最后一份版本后角色从当前分组消失。
- 删除最后一份版本不删除角色原始档案、照片、历史任务和正文图片。
- 固定发送引用有回退时更新、无回退时移除。
- 预检后 manifest 变化返回 `409`，文件不删除。
- 删除失败时前端保留当前选择和可重试状态。

## 6. 实施顺序与提交边界

建议按以下顺序施工，每个阶段可独立回归：

1. **名称合同**：共享解析、编译器、角色摘要、字段提示和测试。
2. **图片块状态**：批量状态 API、宿主注册表、NodeView 投影、页面恢复测试。
3. **角色服装交互**：角色树选择、服装草稿、纯服装回复检测和多候选覆盖／增加确认。
4. **画风串管理**：草稿状态、单一保存入口、分组管理与离开保护。
5. **视觉删除**：预检、事务删除、引用回退、正式确认对话框。
6. **集成验收**：聚焦测试、类型检查、桌面/窄屏静态检查；浏览器与真实模型验收需用户另行授权。

不要把五项压成一个不可审查的大改动。角色服装与视觉删除都修改 `TextToImageCharacterSection.vue`，应顺序施工；图片块状态和画风串管理可以在文件不重叠时独立处理，但最终由同一集成阶段统一验证离开保护和 Project 切换。

## 7. 数据与兼容性

- 不新增 App SQLite 或 Project SQLite 字段；图片块状态直接读取现有 `TextToImageJob`。
- 不修改 `nbook.character-visual/v1` schema；已有英文名 `|` 数据直接按新解析合同生效。
- 不迁移服装数组，不增加修改请求类型或端点；只扩展现有预览响应的候选结构和确认后的合并算法。
- 不改变画风串持久化结构；只把 UI 编辑草稿与已保存配置分离。
- 删除合同改变现有“至少保留一份”的限制，属于有意的行为升级；删除仍需显式确认和 revision 校验。
- 所有错误和诊断继续避免记录 API Key、完整 Prompt、小说正文和视觉字段正文。

## 8. 验证矩阵

### 自动化

- 角色触发词、角色扫描、正文 Prompt 编译聚焦测试。
- 占位符生成、Job 查询、队列运行时、正文写回和 TipTap NodeView 测试。
- 角色工作台点击合同、服装 LLM 合并、修改预览/提交 API 测试。
- NovelAI 设置 normalizer、画风串交互和离开保护测试。
- 视觉库删除、固定发送引用和 API 冲突映射测试。
- `bun run typecheck`；若本机 Bun 启动器仍异常，使用仓库已记录的等价 Node/Nuxt 命令并如实报告。

### 浏览器人工验收（施工后另行授权）

1. 使用含两个英文别名的角色生成正文图片，LLM 返回任一别名都能命中同一视觉资料。
2. 连续提交两张图片，切换工作台页面、章节和主侧栏后返回，状态和队列顺序不丢失。
3. 角色管理中点击不同角色整行，右侧角色和服装立即同步切换。
4. 在原有“角色服装修改”中让模型只返回一套和多套服装，分别选择覆盖、增加和忽略，确认决定前不修改旧服装。
5. 从输入修改要求到生成预览无需上下滚动寻找提交按钮。
6. 新建并保存画风串，只出现一个主保存入口；切换时正确提示未保存修改。
7. 删除非当前版本、当前版本和唯一版本，逐项核对回退、空状态及照片保留。

### 不可用自动化替代的验收

- 真实弱模型是否遵守新增/修改服装提示。
- 真实 NovelAI 长队列跨页面运行时的视觉反馈。
- 桌面与窄屏下角色服装、画风串管理的可发现性和操作距离。

## 9. 完成定义

只有同时满足以下条件才可宣布施工完成：

- 五组问题均有对应的自动化回归，不以手工试一次代替合同测试。
- 图片块状态在页面重建和整页刷新后都来自服务端 Job，而不是本地布尔值。
- 原有修改链路能检测纯服装回复，并在提交前让用户选择覆盖或增加；选中索引和 LLM 回复顺序都不能再造成隐式覆盖。
- 画风串页面只保留一个画风串持久化主入口，新建入口无需展开下拉框即可看到。
- 当前生效或唯一视觉 JSON 均可经过影响预检删除，且不会连带删除角色档案和照片资产。
- 文生图聚焦测试与类型检查通过；未运行的浏览器或真实模型验收明确写入实施记录。
